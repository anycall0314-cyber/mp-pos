# 複審指令範本

規則在 `README.md` 的「複審怎麼做」。填好 `<>` 整段交給 Codex(`-m gpt-6.1-sol -c model_reasoning_effort="xhigh"`,唯讀)。
**只有「完整審查」那一類才找 Codex**;一般與純介面自己檢查、不送。最多兩輪。
紅隊(Grok)只在「完整審查」那一類才跑,而且**只在動手前**跑,用文末那一份(給的是需求與做法,不是 diff)。

## 首輪

```md
你是這個專案的複審。只讀,不要改任何檔案,不要執行會寫入的指令。用繁體中文回報。只審這次的改動,不重新設計功能。

## 審什麼
- 這一件:<一句話;owner 原話>
- 分流:<完整審查 / 一般 / 一輪就好>
- 怎麼讀:`_diff/<名字>.diff` 是這一件全部的改動;需要上下文才開檔案本身。決策在 `docs/decisions.md` 最後一則。
- 驗收:<列出;跑過的測試與結果>
- (完整審查必填)不能被打破的事:<例:作廢之後庫存回到開單前;同一張單不會記兩次>
- 已經知道、這一步刻意不處理的:<列出>

## 規則
- 每一條都要寫:等級(P0–P3)、檔案與大約行號、**怎麼操作(或送什麼資料)→ 會出什麼事**、建議怎麼改(一兩句)。
- **寫不出具體操作步驟的,請自己標成 P2。** 只有 P0 / P1 會擋上線。
- 等級:P0 = 會算錯錢、庫存錯、資料遺失、資安漏洞、當機;P1 = 實務上真的會發生的重大錯誤(主流程走不通、權限繞過、單據重複或漏記);
  P2 = 次要 / 邊界、有替代操作;P3 = 命名、風格、防禦深度、「可以更好」、極低機率。
- 只報這次改動帶進來或直接觸發的問題;原本就有的不報。不要提跟驗收無關的重構。
- **P3 不要寫。P2 最多 3 條、每條一行、不附建議。** 不用追求找到東西,沒有 P0 / P1 就直接說可以上線。
- 通過的報告不超過 10 行。不要開場白、不要總結段。
- 最後一行明確寫:「可以上線」或「還不能上線(P0 / P1 共 N 項)」。

```

## 第二輪起(只查上次的)

```md
這一輪只驗兩件事:
1. 上一輪的 P0 / P1 有沒有修對。
2. 這些修正有沒有直接弄壞別的。

除非你在這次的差異裡發現**新的 P0 / P1**(要附「怎麼操作 → 會出什麼事」),否則:
- 不要擴大到沒有改的地方;
- 不要重提已經接受、或已經記進待辦的 P2 / P3;
- 不要提新的改進或重構。

## 給你的東西
1. 上一輪的問題與處理:<每一項:修了(怎麼修)/ 記待辦 / 不同意(理由)>
2. 上一輪之後的差異:`_diff/since_round<N>.diff`
3. 新增 / 修改的測試:<列出;把修正拿掉會紅的有哪些>
4. 沒處理的與理由:<列出>

## 請回報
- 上一輪每個 P0 / P1:修好了 / 沒修好(附依據)。
- 新的 P0 / P1(沒有重現的不算)。不寫 P2 / P3。
- 最後一行:「可以上線」或「還要修(只限上面列的)」。這是最後一輪,之後不會再送。
```

## 實作前紅隊(只有「完整審查」那一類跑,動手之前)

寫完程式之後**不要**再跑紅隊。紅隊問的是「這個需求本身有沒有想錯」,
那件事測試答不出來;而「假設極端交錯」那一類交給測試與型別檢查。

```md
你站在這家手機店的店員與老闆的立場。還沒有程式,我要你挑這個需求與做法會在實際營業時出事的地方。用繁體中文回報。

## 要做的事
- 這一件:<一句話;owner 原話>
- 誰在用、在哪一步用:<例:門市店員在櫃檯開銷貨單,客人就站在前面>
- 做錯會怎樣:<例:庫存對不上、客人被多收錢、業務佣金算錯>
- 打算怎麼做:<做法兩三句>
- 不能被打破的事:<例:作廢之後庫存回到開單前;同一張單不會記兩次>
- 刻意不做的:<列出>

## 規則
- 只問三件事:(1) 店員照平常的做法操作會在哪裡卡住或做錯;(2) 哪種情況會讓錢、庫存、單據對不上;(3) 需求本身有沒有想錯。
- 每一條要寫「誰在什麼情況下做什麼 → 會出什麼事」。寫不出來的不要列。
- **不要想「兩個人同一秒按」「請求中斷」「注入錯誤」這類極端交錯**,那些交給測試與鎖的規則,不是你的工作。
- 不要寫程式風格意見,不要先寫計畫或開場白,直接給結論。
- **最多 3 條。** 沒有真的會出事的就說「沒有」。
```
