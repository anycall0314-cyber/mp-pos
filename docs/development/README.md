# 開發流程:想法 → 待辦 → 目前任務 → 施工 → 測試 → 複審 → 提交

> owner 2026-10-06 訂的「POS 開發分批執行計畫」的精簡版;2026-10-24 第三版(複審再收、回報與紀錄縮短、文件有大小上限)。Claude / Codex 改程式之前先讀這一頁與 `CURRENT_TASK.md`。前兩版的原文在 `archive/README_2026-10-13.md`。

## 一句話

**想法可以隨時加進來,但不能隨時施工。** 只有 `CURRENT_TASK.md` 裡的那一件才是現在要做的事。

## 六個檔案

| 檔案 | 放什麼 | 代表可以做了嗎 | 大小上限 |
|---|---|---|---|
| `IDEAS.md` | 想法收件匣:還沒確認要做的需求 | 不代表 | — |
| `BACKLOG.md` | 整理過、比較清楚的候選項目(P0–P4)與技術債 | 不代表 | — |
| `CURRENT_TASK.md` | **現在唯一在做的一件事**:目標、規則、可以改 / 不可以改的範圍、驗收條件 | 只有這裡代表 | **只放這一件**;超過 2 萬字就是放了不該放的 |
| `WAITING.md` | 做好了、在等 owner 的(上正式站、實機測、真單、一句話決定);**一件一行** | — | 一件一行 |
| `COMPLETED.md` | 做完、測完、複審過、提交了的 | — | **一筆 10 行內** |
| `DECISIONS.md` | 重要商業決策的索引(全文在 `docs/decisions.md`) | — | — |

規則本身不放在這六個檔:**規則在 `AGENTS.md`(30KB 內,只放全站硬規則與索引)與 `docs/規則/`(一個主題一檔)**;owner 的原話、日期、複審抓到什麼放 `docs/decisions.md`;版型放 `docs/ui-patterns.md`。

## 流程

1. 新想法 → 記進 `IDEAS.md`,不動程式。owner 說「記起來,不要做」:加進去、回報加了什麼,其他都不碰。
2. 想清楚了 → 整理進 `BACKLOG.md`,排優先級:
   P0 資料正確性 / 系統核心 / 阻塞;P1 核心營運流程;P2 管理與效率;P3 操作體驗;P4 未來想法。
3. owner 決定下一件 → 寫成 `CURRENT_TASK.md`(同一時間只有一件;分流結果寫在最上面一行)。
4. 施工:先讀任務 → **先整份讀會動到的主題的規則檔**(`AGENTS.md` 主題索引)→ 看現有程式(資料表、API、畫面、測試、會被影響的地方)→ 列「預計改 / 不會改」→ 沒有明顯風險就動手。
5. 測試 → 複審(照下面分流;先只檢查、不改檔)→ 修 P0 / P1 → 提交(一個可以獨立驗證的小單位一個 commit,訊息寫清楚做了什麼)。
6. 回報 5 行 → 寫進 `COMPLETED.md`(10 行內)→ **從 `CURRENT_TASK.md` 刪掉那一段**;要等 owner 的在 `WAITING.md` 留一行;有新規則改 `docs/規則/` 對應檔(介面小修不寫)。

## 複審怎麼做(2026-10-24 起:第三版)

> 沿革:第一版三輪全審;第二版(2026-10-10)只有五種才外審、最多兩輪、只擋 P0 / P1 —— 但「顯示金額、庫存數字的畫面」也算完整審查,紅隊變成每一件完整審查動手前都跑:10/23、10/24 的 64 件紀錄裡 28 件跑了紅隊,連只動畫面的也有。
> owner 2026-10-24 決定再收:**審「怎麼算、怎麼寫」,不審「怎麼顯示」;紅隊只在新模組第一次設計時跑。** 指令範本在 `REVIEW_PROMPTS.md`,不現場即興寫。

### 先分流(動手前就判,寫進 `CURRENT_TASK.md` 最上面一行)

| 分流 | 什麼算 | 怎麼審 |
|---|---|---|
| **完整審查** | 這一次的 diff 改到「**怎麼算、怎麼寫**」:金額 / 稅 / 成本 / 佣金的算法、庫存加減與序號狀態、現金收支的入帳、付款與結帳、權限判斷(誰能做什麼)、資料庫變更(migration)、鎖與同時操作、對外串接送出去的內容 | 寫完送 Codex 首輪(思考強度 `high`);有 P0 / P1 才第二輪、只查修好沒;**最多兩輪、沒有第三輪** |
| **一般** | 其他:只顯示金額 / 庫存數字的畫面、報表版面與欄位、清單、篩選、查詢、匯入預覽、建檔流程、導覽、文字、顏色、排版、鍵盤與焦點 | **不找外部複審**:自己對 diff + `npm test` / 後端測試 / 型別檢查全過就交付 |

判斷只看一件事:**這一次改的程式有沒有算數字、寫資料**(services、models、migration、權限判斷、送給外部系統的內容)。只是把既有數字拿來顯示、排版的,是一般。有疑慮往上取一級。

### 紅隊

- **只在「新模組第一次設計」跑一次**:新的單據種類、新的錢或庫存的流向、新的對外串接。三個視角對質需求與做法(POS 開發者 = owner 自己、經銷商老闆、經銷商的員工),最多 3 條;挑的是三方立場對不對得起來,不是程式的缺失。批發(賣家)那一塊的標準只有一個:做完一件事要點幾下、打幾個字、換幾個畫面。
- **日常任務不跑紅隊**:既有模組加功能、改畫面、修 bug、全站檢視這一類。實作後也不跑(把關交給測試與型別檢查;紅隊審 diff 會產出沒有上限的極端交錯情境,永遠收不完)。

### 只有 P0 / P1 才擋交付

| 等級 | 定義 | 處置 |
|---|---|---|
| P0 | 會算錯錢、庫存錯、資料遺失、資安漏洞、當機(整個功能不能用) | 必修 |
| P1 | 實務上真的會發生的重大錯誤:主流程走不通、權限繞過、單據重複或漏記 | 必修 |
| P2 | 次要 / 邊界情況、有替代操作 | 複審最多報 3 條、每條一行;順手能修就修,不然記 `BACKLOG.md`;**不因此開新一輪** |
| P3 | 命名、風格、防禦深度、「可以更好」、極低機率 | **複審不准寫**;Claude 自己發現想記的才記 `BACKLOG.md` |

### 硬規則

1. **只有 P0 / P1 擋交付**,不追求零建議。
2. **沒有重現就不擋**:每一條都要寫「怎麼操作(或送什麼資料)→ 會出什麼事」。寫不出具體步驟的自動降成 P2,不用修。
3. **修了要附測試**:每個修掉的 P0 / P1 同一批補一個抓得到它的測試(並確認把修正拿掉測試會紅)。
4. **第二輪只查上次的問題修好沒**:只給上一輪的問題與處理方式、上一輪之後的差異、新增的測試;不重送全部、不重審全部。**最多兩輪。** 第二輪還有 P0 / P1 → 修完停下來問 owner,不自己開第三輪。
5. 複審沒要求的東西,最後一輪之前不要自己加。
6. **報告要短**:通過的報告不超過 10 行;P3 不寫、P2 最多 3 行。
7. **時間上限**:任何一輪(含紅隊)超過 15 分鐘沒結論 → 停,照現狀交付,沒看完的寫進 `BACKLOG.md`。流程不能比功能本身還久。

## 做到一半冒出新想法

不能直接改。記進 `IDEAS.md`,繼續目前任務。**例外**(可以打斷):會掉資料、資料嚴重錯誤、資安問題、現有功能壞掉不能用、目前任務做不下去的底層問題。

發現「這裡架構不好 / 命名不一致 / 重複程式碼」但不影響目前任務 → 記進 `BACKLOG.md` 的「技術債」,不順手改。

## 切工作的方式

沿一條完整的業務流程切(例:二手機 = 收購 → 入庫 → 庫存 → 銷售 → 成本 → 毛利 → 紀錄),不要「今天做五個不相干的功能」。大的畫面重排排在核心商業邏輯穩定之後。

## 每件任務做完要回報(5 行)

1. 做了什麼(一句)。
2. 改了哪些主要檔(一行,只列主要的)。
3. 資料庫:有沒有 migration、編號。
4. 測試:跑了什麼、過了沒。
5. 風險或沒做的(一句;沒有就寫「無」)。

提交後寫進 `COMPLETED.md`:當天日期底下一筆,**同樣五項、10 行內**(第一行帶 commit)。改了哪些檔、審查紀錄、走查細節不寫進去(git 與對話裡有)。規則有變的寫進 `docs/規則/` 對應檔,不寫進 COMPLETED。

## 文件只能這麼大(2026-10-24 起)

- `AGENTS.md` 30KB 內(Codex 預設只讀前 32KB;每一輪對話都整份讀進去,越大越慢)。要加東西先搬東西出去。
- `CURRENT_TASK.md` 只放現在這一件;做完就刪、等 owner 的搬去 `WAITING.md`。
- `COMPLETED.md` 一筆 10 行內。
- **一批一個新對話**:做完一批、提交、COMPLETED 五行,就開新的對話做下一批(同一個對話連做十幾批會越來越慢)。
- **超過 100KB 的資料檔不整份讀**(`inventory.json`、`controls.csv`、匯出的 JSON / CSV 這類),用 grep 查要的那幾行。
- 規則寫規則檔(`docs/規則/`),一個主題一檔;寫規則、不寫日記。介面 / 版面 / 文字的小修不寫進任何規則檔,有新的版型規則才寫 `docs/ui-patterns.md`。

## 永久原則

1. 看到需求不直接施工;先分清楚是想法、待辦、還是目前任務。
2. 一次只集中做一件;不自行擴大範圍;發現別的問題先記下來。
3. 核心商業邏輯先於畫面美化;資料完整先於開發速度。
4. 金額算得出來源;庫存異動追得到;重要交易留操作者;新需求不破壞歷史交易。
5. 改資料表之前確認 migration 與舊資料相容;優先小幅、可驗證、可退回的修改;不做不相干的重構。
6. 每批修改都要能單獨複審。
7. 不同的帳務概念不混成同一個數字(商品營業額、服務收入、佣金收入、成本、毛利、應收、現金流、資金移轉各算各的)。
8. 商業邏輯不確定時不猜,問 owner。
