## 1. 要達成的結果

**一位懂商品、但不懂這套系統的店員，能建立正確商品，並且知道什麼時候應該沿用既有品號。**

店員只需要辨認手上的商品、確認必要規格、判斷候選是不是同件。系統負責搜尋既有資料、帶出正確欄位與管理方式、保護品號身分，以及把結果送回目前作業。

完成後的操作應是：

> 找商品 → 看照片與規格 → 有就沿用；確定沒有才建立 → 接著進貨。

找不到、不確定、資料不足，是三種不同結果。搜尋失敗不能直接被解讀為「一定是新品」。不知道的規格也不能填假資料以通過表單。

本計劃涵蓋日常單筆、手機多規格、配件、無條碼商品、維修零件與服務項目，並說明舊入口、匯入、待確認入庫如何接到共同規則。不是只把七個按鈕收進選單。

## 3. 商品身分：店員需要理解的四件事

| 白話概念 | 意思 | 例子與邊界 |
|---|---|---|
| 一款機型／款式 | 商品的共同身分 | 某款手機；某款無品牌防摔殼。名稱可改，穩定識別不跟著換 |
| 一個可進銷貨的品項 | 規格、單位、品況等會影響交易的組合 | 同機型的不同容量或不同顏色，可分別管理；系統產生品號 |
| 手上的這一件 | 同品項底下的實物 | 每台 IMEI／SN、電池、瑕疵、成本與個別售價 |
| 其他叫法／來源 | 同件商品被不同人或供應商稱呼的方式 | 別名、料號、淘寶商品頁與選到的變體，不必因此新開品號 |

### 必須維持的業務規則

1. 建立商品主檔不增加庫存。數量、成本與序號在進貨或收購成立時才進帳。
2. 每台設備沿用既有 `ProductSerial` 與 `create_serial()`，不同 IMEI 不等於不同商品主檔。
3. 配件可適用多個機型，但同一實物保持一份品號／庫存，不按適用手機容量複製配件。
4. 已拆封可逐台記機況，但不因此改用中古機成本政策。品況、逐台機況與成本政策分開。
5. 既有商品有庫存／交易後，修改描述不能順便改品況、序號管理、單位或會計規則。這類更正須另外定義受控流程。
6. 商品品號由系統產生；日常不要求輸入品號、分類代碼、系列代碼或編碼前綴。

## 4. 何時沿用、何時新增：共同決策表

以下決策必須呈現在操作流程內，也由後端執行；不能只寫在教育文件。

| 看見的情況 | 正確動作 | 系統應怎麼說／做 |
|---|---|---|
| 內部品號或商品條碼明確指向唯一商品，規格無矛盾 | 顯示商品供確認後沿用；既有掃碼快速路徑保留 | 「找到這款商品，確認規格後使用」 |
| 同一供應商的已確認料號／別名對到唯一商品 | 沿用；仍呈現必要規格與照片 | 說明是由哪個已確認對照找到 |
| 不同供應商剛好使用相同料號 | 在各自來源範圍判斷 | 沒指定供應商時不能猜用哪家的對照 |
| 相同機型／款式、重要規格、銷售單位、品況 | 沿用既有品號 | 顯示既有品項，不產生第二筆 |
| 改向別家進貨、進價變動、叫法不同、補照片 | 原則沿用 | 來源、成本、別名分別記錄；先確認品質／規格確實相同 |
| 不同 IMEI、電池健康度、刮痕或這台的售價 | 沿用品項，新增或處理那台設備 | 導向設備資料；不要把單機描述寫成機型 |
| IMEI／SN 已經屬於既有設備 | 顯示那台設備與其狀態，走合法後續作業 | 不重建商品或另一台設備繞過在庫／已售／退回等狀態 |
| 顏色、容量、連線版本、尺寸、功率、材質、包裝單位等身分規格不同 | 先找正確規格；不存在才補一個品項 | 並列差異，例如「既有 1m；這次 2m」 |
| 同一配件適用更多機型 | 確認為同一實物後沿用，補相容關係 | 不按每個相容機型另建庫存 |
| 同一淘寶／阿里巴巴網址，選到不同規格或包裝 | 不憑網址直接沿用 | 同時核對供應商、商品頁、變體、包裝數量 |
| 照片相同，但重要規格不同或未知 | 不能憑圖自動判同件 | 已知不同則補正確規格；未知則待確認 |
| 圖片相似、名字相近、可靠識別不足 | 人工比較 | 提供「就是這款」「不同款」「先待確認」 |
| 搜尋沒有結果，但必要規格不完整 | 待確認草稿 | 不建立可交易品號；指出缺少哪一項 |
| 既有商品零庫存 | 可沿用進貨 | 明確顯示零庫存，不能因此判成新品；銷貨可選規則維持原樣 |
| 找到停用商品 | 顯示既有資料，走管理者恢復／確認 | 沿用不自動啟用，不能用重建品號繞過 |
| 多筆既有商品共用同一可靠識別，或識別與規格矛盾 | 停在衝突處理 | 不選第一筆、不自動轉移別名／條碼、不新建逃避 |
| 完全同名，但實物不同 | 遵守目前同名限制，補可辨識的正式名稱 | 以真實規格或已確認款式區分，不亂加尾碼 |
| 包裝由 10 入改單個販售 | 先確認庫存／銷售單位 | 不直接把 1 包當成 1 個；本計劃不建立隱性單位換算 |

「沒有搜尋結果」只代表這次查找沒找到。應提供調整類別／規格、顯示零庫存與停用候選、待確認選項，而不是立即建立按鈕直達存檔。

## 6. 共用日常流程：三個階段

### 第一步：先看看有沒有

進入時保留來源文字、條碼、供應商與來源頁資料。先用現有辨識引擎搜尋，候選呈現照片、正式名稱、主要規格、品況、銷售單位、啟用狀態與符合原因。

```text
找商品
[名稱／條碼／供應商料號________________] [搜尋]
商品種類 [全部]   適用機型 [不限]   [照片列表]

候選照片  正式名稱與關鍵規格
          為什麼找到：這家供應商曾用這個料號
          與本次不同：長度 1m；你輸入的是 2m
          [看照片與規格] [使用這款商品]

[確定沒有，建立商品]       [不確定，先待確認]
```

輸入的新查詢尚未回來時，不讓舊結果繼續被當成新結果選用；換供應商、種類或規格時亦同。伺服器錯誤和斷線顯示「搜尋未完成」，不能顯示成「沒有商品」。

### 第二步：只填這類商品需要的資料

選擇白話種類：手機／平板、手錶／其他裝置、手機殼／保護貼、充電器／線材／其他商品；更多類型包含維修零件及服務項目。

第一次不展示三個內部性質分類、倉別代碼與會計旗標。種類對應有限範本，帶出正確欄位。使用者只看到「按數量管理」「每件登記序號」等結果；例外放在具名設定並由伺服器驗證。

補規格或照片後，以新資料更新候選；不突然跳頁或清空正在輸入的內容。已確認的規格差異與人工調整須保留。

### 第三步：確認結果

```text
即將建立：USB-C 對 USB-C 充電線／60W／1m／黑
銷售單位：條       庫存：按數量管理
照片：2 張          品名與規格：[修改]
已查看相似商品：既有款為 2m，本款為 1m

[返回修改] [儲存商品]
```

正式名稱由已確認欄位產生可編輯建議；原始供應商品名保留。修改顯示名稱不改商品身分，也不能讓名稱與身分規格互相矛盾。

完成後顯示「已建立商品，尚未入庫」，提供「前往進貨／回商品列表」。若從單據開啟，主要動作為「帶回這張單」。另有「新增下一款」，沿用種類等便利選項時必須明示，不能帶走上一款條碼、照片或身分規格。

## 7. 各商品種類的具體流程與欄位

「是否有容量差異」與「是否逐件記序號」各自判斷，不能互相替代。

| 種類 | 建檔順序與身分規格 | 系統應帶出的行為 |
|---|---|---|
| 智慧手機 | 既有完整機型 → 確認容量／顏色／地區版本／品況 → 選需要的組合 | 通常逐台序號；只新增缺少的已確認組合，不自動全容量全色展開 |
| 老人機／功能型手機 | 完整型號 → 真正會區分商品的顏色／版本／品況 | 容量可不適用，仍可逐台 IMEI；不填 0GB 或假容量 |
| 平板 | 機型 → 容量／顏色／Wi-Fi 或行動網路版本／品況 | Wi-Fi 可只填 SN；不要求不存在的 IMEI |
| 手錶／穿戴裝置 | 型號 → 尺寸／連線版本／材質／顏色等實際身分規格 | 容量僅有需要才出現；序號按範本，不強套手機必填欄位 |
| 耳機／其他有型號裝置 | 品牌與完整型號 → 世代／顏色／版本／販售內容 | 高價或保固需追蹤的按 SN；左右耳／充電盒單賣需不同身分，不能當整組 |
| 手機殼／保護貼 | 種類 → 款式 → 適用機型 → 材質／顏色／規格 → 照片 | 通常按量；一款可多機型相容，查找與庫存都沿用同一商品 |
| 線材／充電器 | 種類 → 接頭／功率／長度／埠數等必要規格 → 品牌或無品牌 → 照片 | 按範本管理；同外觀不同功率不得自動沿用 |
| 無品牌／來源命名混亂 | 先看圖與規格 → 記原來源 → 確認款式 → 系統建議名稱 | 使用既有 `style_code` 能力，不讓店員亂編辨識尾碼；照片僅作核對證據 |
| 維修零件 | 零件種類 → 適用機型 → 品質／版本／顏色等實際差異 | 預設按量；維修用途與對外銷售設定由範本承接，庫存位置仍在進貨時選 |
| 服務項目 | 選已核准服務範本 → 名稱／必要計價資料 | 不建實物庫存；收入／現金／毛利／電信規則沿用各自既有語義 |

### 7.1 新機型與規格組合

- 先搜尋已確認的 `PhoneModel`；店員輸入完整機型名，不必重填系列／世代／後綴。
- 找不到時，提供新機型建議或待確認流程。正式機型的維護仍由有權限的人處理，不從文字猜測便建立全部規格。
- 正式機型字典要先有本次導入範圍可用的資料；未確認的舊命名另外顯示，不能擠進正式型號選單。
- 同機型新增規格，顯示「已存在／將新增／待確認」各列。兩種容量、兩種顏色不一定有四種真實組合；只建立已確認勾選的列。
- 同一機型的新機、拆封與中古，依現有 `Condition` 規則分品項；保固細分是否保留，不在此計劃擅自變更。
- 不為電池 85%、鏡頭黑點或個別成本新增機型。實際收機時才登錄每台設備。

### 7.2 不適用與不知道

| 狀態 | 可否建立可交易商品 | 例子 |
|---|---|---|
| 已確認值 | 可，在其餘條件成立後 | 已確認 1m、60W |
| 範本判定不適用 | 可，不造假值 | 沒有容量差異的功能型手機 |
| 重要規格未知 | 不可，先待確認 | 不知道線材是 60W 還是 100W |
| 非身分補充資料未填 | 可，顯示可補資料 | 沒有背面照片、補充說明空白 |

必填程度由範本決定。不能讓店員把應填規格改成「不適用」來躲過檢核；有合理例外時走明確覆核。

## 8. 照片、別名與來源：沿用現有功能，接到正確位置

### 8.1 照片

- 候選清單顯示縮圖與張數，點品名／照片開核對面板；開圖不等於選用，也不增加單據數量。
- 既有 `PhotoSection`、`ProductPhotoPanel`、手機 `/m/photo` 及圖片處理流程繼續使用。
- 新商品未儲存就能電腦選檔／手機掃碼拍照；切換種類或流程階段保留同一份建檔草稿，不重開另一張失聯的表單。
- 改用既有商品時，告知本次草稿照片不會自動覆蓋既有照片。要補圖另開該商品的編輯作業，沿用現有權限及照片版本檢查。
- 多規格共用照片需要明確指定。不能把黑色照片當成白色品項的確切照片；共用參考圖標示「款式參考」，規格文字仍必須明確。
- 保留凍結上傳、取消、重試、錯誤與照片同交易儲存的現有語義；完整驗收電腦與手機真機，不以入口存在當成功。

### 8.2 別名與來源

- 找到並確認商品後，提供選填「記住這個叫法」，顯示適用供應商或通用範圍。
- 只保留搜尋關鍵字的叫法與已確認可唯一對應的別名分開。模糊字詞不能自動升級為唯一識別。
- 新介面以明確選擇記住叫法，不沿用預先勾選的隱性學習；保存後講清楚是「可直接對照」或「只幫助搜尋」。後來出現相似兄弟款時，原叫法仍可能退回候選。
- 來源商品沿用 `SupplierProduct`：供應商、平台、商品頁、實際變體、料號、原始品名與包裝數量。只存一個淘寶網址不足以認定商品。
- 換供應商不一定換品號；確認實物規格、品質與銷售單位後，將新來源連到原品號。
- 供應商重用料號或來源改版時，產生衝突與人工確認，不默默把舊對照指向新品。原對照歷史保留。
- 商品已成功建立但選填的「記住叫法」失敗，應顯示部分結果並只重試別名，不能重建商品。若某來源對照是本次確認的必要條件，須在提交前定義是否整筆原子保存。

## 9. 待確認：不靠建立錯誤商品來暫放工作

### 9.1 建議資料與狀態

新增輕量「商品建檔草稿／待確認」能力，暫名 `ProductCreationDraft`，屬於本計劃新增項目，不是現有功能宣稱。

狀態：**編輯中 → 待確認 → 已解決（沿用或新增）**；可明確取消。待確認不是已啟用商品，也不分配正式品號、不出現在可銷貨品項、不增庫存。

保存內容：種類與範本版本、已知／未知規格、原始查詢、來源、照片、候選與未解原因、建立人、負責確認者、版本、時間與最終指向商品。進貨情境保留來源單據草稿／行識別，不把商品草稿當成進貨單。

一般草稿由本人續填；建議待確認可交公司管理者處理，具體可見與可修改權限在實作前確認。不同公司不能交叉存取。確認結果回到原來源，不能在背景替使用者成立進貨單。

### 9.2 照片保存不能直接套現有暫存

現有 `PhotoDraft` 是操作者私有的上傳作業，未儲存作業有 24 小時清理期限。跨日或交給主管時，只存它的識別碼會遇到照片到期或權限不符。

本階段必須做到：

1. 將選定照片與待確認草稿一起轉成可持久保存的草稿附件，不為存照片先建立假商品。
2. 草稿附件繼承公司／待確認工作權限；配對手機仍只有限定上傳權限，不因此取得主管權限。
3. 選擇新增時，附件以原子操作附到新商品；選擇沿用時，保留決策需要的來源附件，補既有商品照片仍需明確動作。
4. 新草稿與附件納入公司備份／還原及清理規則；有效待確認不被 24 小時暫存清理刪除。
5. 明確結案／取消後依核准的保存政策清理；保存天數尚待決定，不先設定靜默自動刪除。

### 9.3 與既有待確認入庫的界線

`IntakeBatch / IntakeItem` 已有來源、數量、成本、序號，結束會成立進貨單。即使部分欄位可空白，也不適合直接當所有商品的通用待確認草稿。

來源本來就在 Intake 的，保留 Intake 作業，使用共用商品辨識／建立結果回填該行；一般商品管理的待確認使用輕量草稿，不強迫使用者先建進貨批次。

## 10. 進貨／中古收購串接

1. 商品管理建好或選用後，承接目前 `purchasePrefill` 的「前往進貨」；已有進貨草稿時加入該草稿，不取代。
2. 原開單內的建檔流程以一次性回傳動作帶回商品，保存來源行／草稿識別；重整、返回或重試不能重複增加行或數量。
3. 「選到既有品號」只代表商品身分確認；採購數量、倉庫、供應商、價格與序號仍需在單據中確認。
4. 中古品依既有規則走「中古收購」，區分個人收購與廠商收購；服務／虛擬商品不顯示一般實物進貨動作。
5. 一次結果包含一般品與中古品時，分列下一步與未帶入項目，不靜默略過。超過帶入筆數上限也要列明，不能宣稱全部已帶入。
6. 目前中古收購入口尚不等於已能預填商品；後續需要擴充時，列入獨立驗收項，不寫成已完成。
7. 進貨送出結果不明時，仍遵守現有同一把請求識別重送與單據鎖定規則；不能因回到商品頁建立一次新的進貨提交。

## 11. 畫面與互動規格

- 日常採一個連續工作區，左／上方輸入，旁邊或下方顯示候選；次要設定逐步展開，不堆疊多層彈窗。
- 已知道種類或已有精確候選的人可直接進入該步，不要求每次重新走完教學。
- 沿用既有字級變數：正文 16px、次要資訊至少 14px、控制項約 44px；手機拍照主要按鈕至少 48px。
- 商品詳情與照片按需開啟，關閉後回原位置。進銷貨明細不常駐大型圖片區，保留既有大量品項工作區。
- 搜尋可鍵盤操作，Enter 的選用與提交語義清楚；支援中文輸入法，組字中的 Enter 不送出建檔。
- 「上一步／改種類」保留已填值；不適用欄位提示後排除於提交，不能帶隱藏舊值進新品。身分已改時，原先的候選確認與差異理由需重核。
- 儲存／等待伺服器期間防重複操作；斷線、照片失敗、版本衝突、查重衝突各有可恢復的下一步。
- 既有圖片載入失敗不等於沒有照片；搜尋失敗不等於沒有商品；不適用不等於未知。

## 12. 後端共同建檔規則：先統一結果，再收斂入口

### 12.1 建議新增的最小共用層

新增 `backend/apps/catalog/services_product.py`（建議路徑），承接各入口已存在的建立能力。API 可以分批保留舊路由，由轉接層送入共用服務。

```text
單筆 / 多規格 / 貼上 / Excel / 零件批次 / Intake 建新品
                           ↓
        共用輸入正規化與種類範本驗證
                           ↓
        現有辨識引擎 + 結構化規格比較
                           ↓
        提交時重新查重、權限與並發檢查
                           ↓
        商品 + 品號 + 關聯 + 必要決策 + 照片
                           ↓
        回原作業（建檔本身不動庫存或帳款）
```

服務職責：

1. 將不同入口轉成同一份商品描述，所有權限、機型、分類、品況、來源和照片都限制在公司範圍。
2. 根據種類範本驗證身分欄位、未知與不適用；決定預設庫存模式，但尊重合法人工例外。
3. 使用既有 `find_candidates`／`guard_new_product` 及差異決策紀錄；新增前查找不能取代提交時查重。
4. 寫入一致的機型、品況、容量、顏色、版本與擴充身分規格。不能只拼進 `name/spec` 就宣稱完成結構化。
5. 以商品的同一個交易套用照片與必要關聯；可恢復的錯誤回傳欄位／候選／已成立結果，不丟失草稿。
6. 修改既有商品獨立處理。新建預設不套到既有存貨，也不開放以一般編輯改寫受保護的品況／庫存語義。

### 12.2 種類範本與最小資料擴充

先做有限、由程式驗證的範本，初版不建任意自訂欄位平台。

| 資料 | 建議 |
|---|---|
| 範本 | 穩定代碼與版本、名稱、所需身分欄位、必要／可選／不適用、庫存預設、明確預設品況與可用用途 |
| 既有標準欄位 | 機型、容量、顏色、版本、品況等繼續使用既有欄位，不另存互相矛盾的第二份 |
| 缺少的身分規格 | 建議增加有限 `identity_spec` 物件及範本代碼／版本，承載接頭、長度、功率、尺寸、連線、販售內容與單位等；鍵、型別、單位、必填規則由伺服器白名單驗證 |
| 顯示規格 | 由身分規格生成可讀摘要，補充備註另放；摘要文字不作唯一身分鍵 |
| 款式 | 沿用穩定機型與 `style_code`；新同款多規格的款式歸屬需明確確認，不能只憑圖相同共享 |
| 待確認 | 新草稿模型與附件生命週期；未解決不生成正式可交易商品 |
| 並發與重試 | 補商品建立請求識別、請求內容指紋、結果參照；不可只依有沒有照片草稿判斷 |

精確欄位名稱與 migration 在該批施工前定稿。物件中「未知」不寫成確認值；不適用由範本與明確例外控制。舊商品缺資料保留舊模式，不一次以新必填規則讓全部舊商品無法作業。

現有 `style_code` 在商品層，不等於已有多規格父款式模型。同款多規格如何共享穩定款式身分，須在該批實作時明確定義，不能拿顯示名稱或任意相同款式碼代替關聯。

只有確認完整的身分資料才可計算用於並發防重複的身分鍵。無品牌款式不明、舊資料缺欄位時不能以空值集合認定同件；模糊匹配仍是候選。

## 13. API 與資料流約定

下列新增路徑名稱是建議契約，實作時可依專案風格調整；現有對外入口保持相容。

| 能力 | 使用／新增方式 | 結果要求 |
|---|---|---|
| 搜尋與辨識 | 沿用 `/products/resolve/`，必要時增加種類／結構規格條件 | 保留 existing／candidates／conflict／none 的區分；另附資料完整性，不把 none 直接等同可新建 |
| 候選詳情 | 沿用商品序列化與照片面板 | 主圖／照片數、關鍵規格、差異、停用標記與權限允許內容 |
| 預覽 | 共用服務提供預覽模式；可暫定 `/products/creation-preview/` | 每列穩定識別、將沿用／將新增／待確認／被擋原因；不配號、不建立商品 |
| 提交 | 可暫定 `/products/creation-commit/`，舊入口透過轉接呼叫同服務 | 接收明確決策、草稿版本、請求識別；回傳每列實際商品識別與狀態 |
| 記住叫法 | 沿用既有 remember／alias 能力 | 回已確認、搜尋關鍵字或衝突；不能默默改指 |
| 來源對照 | 沿用 `SupplierProduct` 與既有對照規則 | 核對供應商＋變體，保留舊來源 |
| 商品待確認 | 新草稿讀寫／提交待確認／解決 API | 租戶、操作者／覆核者、版本、附件與狀態檢核 |
| 回到進貨 | 承接目前新增的前端帶入；單據內則回原草稿 | 商品識別與處理結果，不從 URL 信任成本、數量或權限 |

候選選用和新品建立分開：選既有時重新驗證仍可用與規格是否改變，不能因舊的搜尋結果直接使用已停用商品。

可靠條碼／料號命中之後，仍要將使用者已確認的重要規格與商品交叉核對。存在矛盾時回傳衝突供查核，不擅自認定條碼、使用者輸入或舊資料哪一方正確。

預覽後改規格，需重新預覽；提交時無論有無預覽都重新驗證。預覽只是當時狀態，另一位員工可能已經建好或修改。

## 14. 並發、重試、批次與失敗恢復

### 14.1 單筆與同時建檔

- 現有條碼查重已有 PostgreSQL 交易鎖；保留，並檢查完整已確認身分與可靠來源鍵的並發保護。
- 兩位員工同時建相同商品，只有完整、精確相同且目前可用的身分，後到者才可取得「已存在」結果；模糊相似、停用或來源衝突須回候選／衝突供人確認。不因別人先建好，就自動把本次新建草稿照片、別名或來源掛到該商品。
- 一次建檔有穩定請求識別；同識別、同內容重送回同結果，不再配號；同識別不同內容拒絕並提示。
- 斷線不知道是否成功時保留同請求識別與草稿，提供查詢／原樣重送；不能先產生新識別再建一次。
- 收到確定「沒有任何寫入」的失敗結果後，修改內容以新的提交版本／請求識別送出，並保留前一版本結果。不能把提交結果不明當成確定失敗。
- 照片流程現有的重送保護繼續保留，但無照片、批次與不同入口也須有相同保障。
- 保護照片、已確認來源、品號與商品建構的一致性；儲存失敗不能留下半套可交易商品。

### 14.2 批次

- 批次先選種類或逐列指定種類，不能把所有貼上的品項都當成主機。
- 每列有穩定 `client_item_id`，回覆和差異理由依該識別對應，不只依可變動的品名。
- 預覽並列「沿用／新增／待確認／錯誤」，包含同批內的重複，明列哪些項目不會建立。
- 保留外層原語義：現有 bulk 整批失敗回滾、Excel 逐列略過、Intake 最終成立進貨等，不因抽共用服務而私自改變。
- 整批確定回滾：修正後以新版本／請求識別重新提交。逐列部分成功：保留成功列的商品與結果，只把失敗或未執行列以新識別提交，不重送全批重新建立。結果不明：先用原識別查回或原樣重送，尚不能修改後換識別重建。
- 圖片、別名與來源映射必須明確對到每個目標品項；同款參考照共享須明示，不跨列亂掛。

### 14.3 必須看得到的失敗狀態

搜尋未完成、資料不足、可靠識別衝突、候選已變更、照片失敗、草稿版本衝突、儲存結果不明、部分批次略過、進貨未帶入，均各有明確文字與下一步。不能統一顯示「失敗，請再試一次」。

## 15. 舊資料與字典整理

先在本次導入公司抽樣，確認正式機型、常用商品種類、品況與序號策略可用；這是新流程的前置工作。大量歷史整理可後續分批。

- 以只讀清單找出待確認：缺機型關聯、單機描述混進名稱、必要規格缺漏、可靠識別衝突、別名範圍不清、分類混用。
- 保留原品號、原名稱、來源、交易、庫存與舊 POS 對照；補欄位不等於重放庫存異動。
- 品牌、品況、商品種類逐步拆開；分類與序號／中古預設可能有連動，不能靠批次改類別直接修所有資料。
- 新機型選單優先展示確認資料；未確認舊商品仍可按原名稱查到，標出待補，保留既有作業能力。
- 不以照片或近似文字自動合併有交易的品號。真正重複的合併、停售或轉移庫存另立任務與核對步驟。
- migrations 以加欄位／加表為主，先不對所有舊資料套唯一身分約束。新增模型、附件與欄位須檢查公司備份／還原。
- 若試行退回舊介面，新建立的商品仍應能由舊進銷貨讀取。新身分欄位與草稿不可因關閉新入口被刪掉。

## 16. 分批實作計劃與依賴

## 18. 驗收矩陣

### 18.1 業務與資料正確性

| 編號 | 情境 | 必須看到的結果 |
|---|---|---|
| A01 | 已有同款、不同員工換詞搜尋 | 找到並沿用原品號；沒有第二份商品 |
| A02 | 已有商品零庫存 | 仍能找到並進貨；不影響銷貨不可賣零庫存的既有規則 |
| A03 | 同款手機補一個確認的新顏色 | 既有組合沿用，只新增缺少組合 |
| A04 | 老人機沒有容量差異 | 可建立且仍逐台記IMEI；沒有假容量 |
| A05 | Wi-Fi平板／只具SN的裝置 | 不強制IMEI，序號數與數量一致 |
| A06 | 同機型中古機不同電池／瑕疵 | 同品項下登錄不同設備；不多建機型 |
| A07 | 已拆封但非中古成本政策 | 可逐台記機況，成本仍依原政策 |
| A08 | 保護殼適用兩個機型 | 一個配件品號、多個相容關係、一份庫存 |
| A09 | 相同照片不同功率／長度 | 清楚顯示差異，不自動沿用 |
| A10 | 無條碼、不同供應商叫法 | 看圖與規格確認後沿用，正確保存來源範圍 |
| A11 | 同商品頁不同變體／包裝 | 不因同網址或同圖誤配；未決單位不自動換算 |
| A12 | 停用商品或可靠識別衝突 | 不自動啟用、不另建繞過，導向具權限的確認 |
| A13 | 規格重要但未知 | 可待確認，不生成可交易品號 |

### 18.2 可靠性與跨入口

| 編號 | 情境 | 必須看到的結果 |
|---|---|---|
| B01 | 兩人同時建立相同完整身分／同條碼 | 一份商品或明確既有衝突，不建立兩份 |
| B02 | 儲存成功但回應丟失，重送或重整 | 同請求回原結果，不重配號；無照片也成立 |
| B03 | 預覽後他人新增或修改候選 | 提交重新核對，顯示新結果，不沿用過期判斷 |
| B04 | 同請求識別改了提交內容 | 拒絕混用；不把新內容誤認舊成功 |
| B05 | 搜尋慢、斷線、切查詢／供應商 | 舊結果不冒充新結果；失敗不顯示成沒有商品 |
| B06 | 手機還在上傳時儲存／取消／切商品 | 照片狀態可恢復，不漏掛、錯掛或重複 |
| B07 | 待確認隔日由有權限者接手 | 規格、來源、照片可讀；配對權限不擴張 |
| B08 | 待確認選用既有商品 | 不把新照片自動覆蓋舊照片，不成立進貨單 |
| B09 | 公司甲使用公司乙的候選／照片／草稿ID | 伺服器拒絕，所有入口一致 |
| B10 | 單筆、批次、匯入、Intake與直接API建同件 | 身分欄位和防重複規則一致，不可繞過 |
| B11 | 批次有同批重複、部分錯誤或略過 | 每列結果可追溯，保持原子或逐列語義，重試不重建 |
| B12 | 返回有內容的進貨草稿／重新整理 | 原單保留，回傳一次，數量不重複增加 |
| B13 | 既有商品編輯／載入草稿／切種類 | 不意外套新品預設；隱藏舊值與人工調整處理明確 |
| B14 | 公司備份還原含待確認附件 | 有效草稿與照片完整，跨公司權限與對照仍正確 |
| B15 | 建商品後進貨、銷售、作廢／退貨 | 庫存、序號、成本、毛利仍符合現有業務服務，主檔建立本身沒有帳務異動 |

## 19. 新手可用性試行與上線條件

邀請 5 位熟悉商品、未受過這套建檔操作訓練的店員；先用舊流程記錄基線，再用新流程完成 8 個代表任務：找既有手機、補規格、老人機、Wi-Fi平板、無條碼線材、不同叫法沿用、跨機型配件、待確認交接。

避免記憶效應，兩次使用等價但不同的商品樣本。測試中觀察員不逐步教按鈕；只提供實物／來源及任務目標，並記錄求助原因。

建議通過門檻（是目標，不是已測結果）：

- 40 次任務中，至少 36 次無逐步協助完成正確結果。
- 同件誤建新品號、不同件誤沿用、錯誤庫存模式／單位等嚴重錯誤為 0；若任一發生，先修流程再擴大。
- 已存在商品的確認任務，中位完成時間目標 30 秒內；一般單款新品目標 2 分鐘內，拍攝與等待網路時間分開記錄。
- 至少 4 位能用自己的話說出「換叫法／不同進價沿用；重要規格不同找另一款；不確定先待確認」。
- 搜尋性能以實際公司資料量測量，另測 1 萬筆候選資料；建議正常網路 p95 目標 1.5 秒內，不一次載入完整商品庫或所有大圖。

先在測試公司完成寫入與撤銷情境，再選一個具代表性的門市試行。觀察重複建檔、錯誤沿用、待確認件數與結案時間；不把「新建數下降」單獨當成功，否則錯誤沿用也會讓數字好看。

上線紀錄分別記：程式／測試完成、提交、部署、線上實際驗證、店員試行。每批都可退回舊入口，但保留已正確建立的商品與資料，不用回滾資料庫刪新商品。
