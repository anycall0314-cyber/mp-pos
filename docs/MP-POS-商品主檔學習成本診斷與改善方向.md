# MP POS 商品主檔學習成本診斷與改善方向

日期：2026-10-06

## 1. 判斷

**初次使用的學習成本確實偏高。主要原因是：建立一個商品以前，使用者必須先理解系統的分類方式、資料層級和管理規則；不同入口的預設與建檔結構又不完全一致。**

目前比較適合已經理解系統的資料管理者。店員知道手上拿的是什麼商品，卻仍要回答「走哪個入口、這裡的機型是哪一層、品況與狀態有何不同、是否需要規格變體」等問題。

改善應讓使用者依照實物與當下工作回答問題，由系統將答案轉成正確的商品資料。既有的機型、品號、單機、相容關係和成本規則仍需保留。

這是流程與心智負擔的專家檢查，尚未安排新手實際操作測試，因此不宣稱已量到學習時間或錯誤率。

### 特別需要立即修正的兩個例子

**配件序號預設不一致。** 線上一般新增的機型配件勾著序號；專用「新增配件」相同性質則未勾。這不是只靠提示文字能解決的問題，應讓不同入口遵守同一份業務預設。本次未儲存，因此不宣稱已造成實際入庫錯誤。

**手機的「系列」與「後綴」容易重疊。** 本次選 APPLE 後，系列選項看到 `PRO` 與 `PRO MAX`；同頁後綴又以 Pro／Pro Max 為範例。這是當前選項資料與欄位說明共同造成的困惑，需先釐清系列字典，不宜只增加教學文字。

另外，手機精靈第一步提到配件 placeholder SKU，第二步卻明寫不建立配件 SKU。本機建檔服務目前只記錄相容類別，不建立這些配件品號；應統一前一步的舊說明，避免使用者誤判一次操作會建立什麼。

## 4. 保留資料邏輯，降低使用者需要理解的層數

以下例子僅用來說明層級，並非本次新建或已確認的完整商品規格。

| 層級 | 例子 | 使用者應在何時處理 |
|---|---|---|
| 機型 | iPhone 15 Pro | 找商品、選適用機型；通常從既有清單選 |
| 商品品號 | 該機型＋確認的容量／顏色／版本／品況 | 建立可單獨進銷貨的規格組合 |
| 實際一台設備 | 某個 IMEI、這台的電池健康度、瑕疵、成本、個別售價 | 實際進貨／收機時登錄 |
| 配件商品 | 一款已確認規格的保護殼 | 本身一份品號與庫存，可以連到多個適用機型 |
| 別名 | 廠商品名、供應商料號、員工習慣叫法 | 找到既有商品並確認後，明確選擇記住叫法 |

電池健康度或刮痕不應讓使用者再建立一個新的手機機型。相同照片也不能證明容量、顏色、包裝數量或規格相同。

已拆封與中古仍可有不同的成本政策；逐台記機況和逐台成本是兩件事，介面簡化時不能混成同一個勾選。配件適用兩款手機，也不能因此拆成兩份相同實物庫存。

## 5. 建議的新手工作流程

```text
找商品：名稱／條碼／分類／適用機型／照片
  ├─ 找到了 → 看圖與規格 → 使用既有品號
  └─ 確認沒有 → 新增商品
                    ├─ 手機／平板
                    ├─ 保護殼／保護貼等機型配件
                    ├─ 充電器／線材／耳機等一般商品
                    └─ 更多類型：維修零件／服務項目
```

日常找貨與建檔共享同一套搜尋、照片查看與既有商品識別。零庫存商品仍應可查到；停用品以清楚標記提供查核，是否可重新啟用依原有權限處理。

### 手機／平板

1. 先選完整機型，例如直接找到品牌＋機型名稱，不要求店員每次重新拆系列與世代。
2. 選這次需要的容量、顏色、地區版本與品況，先呈現已有的組合。
3. 已有相同組合就沿用品號；缺少才新增。
4. 儲存前清楚列出本次增加幾個品項、哪些已存在，以及是否需逐台記序號。
5. 到貨時再逐台輸入 IMEI／SN、機況與成本；建立商品主檔不等於已增加庫存。

找不到機型時才進入「建立新機型」，依現有權限提供管理或待確認流程。不能用未確認的容量／顏色自動補齊成可交易商品。

這條路徑的前置條件，是先整理本次導入範圍內已確認的機型與系列字典。未確認的舊名稱放在待確認清單，不直接混入正式機型選單；舊商品仍保留原有查找與作業途徑，不能因整理尚未完成而突然無法交易。

「一次建立多種規格」保留給有需要的人，以勾選與可閱讀的組合表取代一開始就全品況勾選。品牌／系列字典、換代順序及批次零件範本由管理工作處理。

### 一般商品與配件

第一輪只問：是什麼商品、怎麼辨識、這次有什麼規格。

- 商品種類：充電線、充電器、手機殼、耳機等；由種類提供適合的欄位與庫存管理預設。
- 名稱與照片：沿用電腦選照片及現有手機拍照入口，手機直傳端到端效果待驗證；先看既有候選再決定新建。
- 關鍵規格：依種類呈現接頭、功率、長度、尺寸、顏色或包裝單位，不給所有商品同一大串欄位。
- 適用機型：需要時才出現；相容多機型使用關聯，不複製庫存。
- 條碼：有就掃，沒有也可建立內部品號；內部品號或日後自印標籤不偽裝成原廠條碼。
- 品牌：可明確選「無品牌／待確認」，不要為了過表單捏造品牌。
- 售價與庫存方式：呈現結果摘要，可依權限調整；重要規格若會影響是否同件，不能當作可隨意略過的選填。

需要多色或多長度時，點「增加規格」再展開。以每列規格、售價與是否建立的表格操作，不要求新人先理解「軸」。不同產品範本的序號預設可不同，例如部分高價耳機仍需逐件追蹤，不能一律把所有非手機序號關閉。

### 維修零件與服務項目

維修零件以名稱、適用機型、零件種類和庫存方式為主；範本批次建立留給大量建檔。

服務費、包膜施工等沒有實物庫存的項目，以具名範本帶出管理規則，具體收入／成本處理由既有業務規則決定，不讓店員自行猜「虛擬商品、計入現金、計入毛利」應如何勾選。若施工同時耗用包膜材料，服務項目與材料庫存仍分別依既有流程處理。

## 6. 現有照片與別名應接到哪裡

本次已確認一般建檔頁和商品基本頁有照片介面，商品別名也有獨立頁籤。建議沿用現成能力，優先補齊三個位置：

1. **搜尋結果**：可快速看主圖與規格，使用者不必先知道唯一的正式品名。
2. **新增前的既有商品候選**：邊找邊確認，不等整張表單填完才發現重複。
3. **提交時的重複候選**：同時看照片、規格與匹配原因；確定同件就沿用，僅名稱相似且規格不同時才依規則繼續新增。

確認後可由使用者明確選擇「記住這個叫法」，保存為既有品號的別名；不要把每一次搜尋文字自動學成別名。

商品查找也需要確認是否實際查到既有別名。本次只驗證別名維護頁存在，未完整驗證各個選品入口的別名搜尋結果，不能視為已全站接通。

這是介面呈現順序建議，不自動新增或剝奪使用者權限。所有寫入仍沿用原有伺服器權限、租戶範圍與檢核。

## 8. 既有資料要另設整理流程

本次機型清單抽查出現如「IP14PM 紫 85% H 三倍黑點」的名稱，其明細容量／顏色空白。這是可見的資料呈現現象，尚未逐筆核對來源，不能據此斷言全部商品資料錯誤。

本機程式可解釋一種成因：已有穩定機型關聯時使用機型主檔；沒有時，先依系列／世代／後綴組合，再退回從品名推算。品名解析會去除部分容量、末尾顏色及中古字樣，沒有完整排除電池、刮痕等單機描述。因此舊命名進入此路徑時，會留下這些字。右側容量／顏色則直接讀結構欄位。本次沒有查該筆資料的完整關聯，這是與畫面相符的可能原因，不是對該筆來源的定論。

建議管理者取得一份待整理清單：可能混入單機機況的名稱、缺規格、同機型不同寫法、分類混用等。每筆保留原品號、舊名稱、原始來源及歷史關係，確認後補機型／規格與單機資料對應。

不要只用字串相似度或同張照片自動合併有庫存／有交易的品號，也不要靠重新建一份乾淨品號把歷史問題藏起來。缺資料可標成待補，現有營運與查核方式須明確保留。

## 9. 建議實作順序與驗收

| 階段 | 改動 | 驗收重點 |
|---|---|---|
| A：先減少建錯 | 修正序號預設、手機入口一致性、狀態命名、矛盾說明；先確認導入範圍的機型與系列字典 | 同商品由不同入口進入，欄位／預設／提交結構一致；普通配件不意外要求逐件序號；已有可用的正式機型清單 |
| B：日常流程收斂 | 一個新增起點、依商品種類分流、手機先選機型、批次移至次要工具 | 新人不需知道系列／軸／SKU即可完成一筆一般建檔；管理者仍找得到批次功能 |
| C：先找再建 | 搜尋照片、規格候選、明確沿用、確認後記別名 | 無條碼且叫法不同的同件商品可以找到並沿用；不同規格不被誤合併 |
| D：資料品質 | 品牌系列與類別對照、舊資料待確認清單、逐筆補齊 | 原始品號與歷史可追溯，沒有自動改動庫存或交易 |

建議找 3–5 位不熟系統的店員，各自完成下列任務，記錄完成時間、求助次數、走錯入口、重複建檔及規格錯誤；這些是待測指標，沒有現成測量結果：

1. 找一款已存在的手機規格，準備進貨，不另建品號。
2. 同機型新增一個已確認、尚不存在的顏色組合。
3. 收一台有電池與瑕疵資訊的中古機，說得清楚哪些填商品、哪些填這台設備。
4. 建立沒有條碼的充電線，加入照片與接頭／長度等辨識規格。
5. 用另一種叫法找到上一位同事建立的同一款商品。
6. 建一款適用兩個機型的配件，確認只有一份實物庫存。
7. 建立少量維修零件，無須先完成全品牌零件範本。
