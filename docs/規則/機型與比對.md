## 規則

### 機型主檔

`PhoneModel`(per-tenant,`code` 可讀 slug + `match_key` 唯一)是「同一款手機」的穩定身分。`Product.phone_model` / `ProductRelation.host_model` FK。`phone_model_key` / `phone_model_name` property 有掛主檔就用主檔,沒掛退回原本算出來的字串。**`host_model_key` 等字串欄位全部保留並同步維護**,既有 key-based 查詢不動。回填只收 `series` 有填的商品(regex 那條路會把配件名解析成機型)

### 相容關係不被刪商品連累

`ProductRelation.host_product` 是 `SET_NULL`(代表 SKU 只供 UI 顯示),邏輯主鍵是 `host_model` / `host_model_key`。**存相容機型(`related_host_keys`)先確認每個新的機型都對得到東西才動資料**(2026-10-09):對得到 = 有啟用中的主機商品,或機型主檔 `PhoneModel` 裡有(關係掛在主檔上、沒有代表商品);對不到的整筆退回(400,講是哪幾個)、舊關係不動 —— 以前是先刪舊的、對不到的默默跳過、照樣回成功。下拉清單(`products/phone-models`)目前只列有主機商品的機型

### 配件 → 相容機型比對

店內配件料號(`IMOS/IP15PM/透`)跟手機主檔(`iPhone 15 Pro Max …`)是兩套寫法,模糊比對跨不過去(實測候選 0 筆)。改用**縮寫查表**:`apps/catalog/accessory_model_match.py` 從該租戶 `PhoneModel` 反推店內縮寫。`+`=Plus / `PRO`=Pro / `PM`=Pro Max / `U`=Ultra;**`P` 的意思看那一代有沒有 Pro**(iPhone 7 沒 Pro 所以 `IP7P`=Plus、11 有 Pro 所以 `IP11P`=Pro),不寫死而是查主檔。指令 `match_accessory_models`(預設 dry-run)。對不到就留著,**不硬湊**。完整實測見 `docs/配件機型比對_試跑結果.md`

### 哪些類別要掛機型

`Category.needs_host_model`(預設 True,類別設定頁可勾)。主機本身(手機/平板/手錶)與整類跟機型無關的(吊飾/支架/家電/包膜/虛擬)關掉。**充電線材與耳機刻意保持 True**:裡面有機型專屬品(`IP5/副廠/2M`),整類關掉會漏

### 機型主檔只建機型不建商品

`import_taiwan_catalog` 會連商品 SKU 一起建,已有自己商品的租戶不能那樣灌。改用 `sync_phone_models`(同一份 JSON,只確保 Brand / PhoneSeries / PhoneModel 存在)。補充清單 `apps/catalog/data/phone_models_extra.json` 只有機型身分、沒有價格顏色,給老機與 JSON 還沒更新的現役機用

### AI 判機型只能出建議

`suggest_accessory_models` 把規則對不到的送 Jev,**只出 CSV、一筆都不寫入**。理由是實測:唯一一筆信心 0.98 的答案是錯的(`SAM/M53` 判成 `Galaxy A 53`,主檔缺 M53 就會高信心指錯),而平板那組答對的信心最高只有 0.86。**信心量的是分佈集中度,不是正確率**,任何門檻都不安全

### 商品叫法比對

`apps/identity/product_match.py`:品名與查詢走同一支 `parse_features()`,拆成型號 / 顏色 / 其他詞再比(`exact` / `covers` / `related`)。進貨搜尋、`?search=`、待確認入庫、新增查重**共用**。特徵比對只出候選;`existing` 只來自條碼 / 廠商料號 / 已確認別名 / 品號。`GET /products/resolve/?q=` 回候選 + 符合原因 + 差異,零庫存與停用都列。**沒寫品牌字首的機型寫法也對得上機型**(2026-10-07,新手商品建檔 R1 第一小包;新手不會打店裡的 `IP11PM`):`11PM` / `13P`、空白隔開的 `11 pro max`、品牌 + 機型被接成一串的 `DAP 13P`、單獨一個數字(`犀牛盾 12 黑`)。**原則只有一條:只會多對上,不會讓原本找得到的變成找不到** —— `words` 完全不變,多記一份 `Features.bare`(寫法 + 它是 words 裡的哪幾個字),比對時拿去問機型主檔(`accessory_model_match.build_index` 本來就收 `11PM`、`11PROMAX` 這種寫法);**主檔認得、而且就是這個商品的機型才算機型對上**,其餘那些字照原本當一般的字比(沒對上的不排除、照舊講「商品沒有」)。所以沒有機型主檔的公司完全不變(**沒有主檔的公司連 `iPhone 16` 對 `IP16` 都對不上 —— 從舊系統搬配件進來的公司要先跑 `sync_phone_models`**)。`DAP 13P` 被原本的規則接成 `DAP13P`:主檔不認得接起來的、而後半就是這個商品的機型才拆回「一個字 + 機型」。**單獨一個數字是很弱的線索**:只在商品真的是 iPhone 那一代時算(`DAP 12` 還要品牌那個字在品名裡),而且**最多列為相關**、差異寫「只寫了數字 12,當成 iPhone 12 來比」,不會變成同一款(不然防重複會把 `某牌/保護貼/12` 跟 `某牌/IP12/保護貼` 互擋),也不能只靠它就成立。品名自己這樣寫的(`11PRO/認證電池`)也算那個機型,但品名已經寫了別的型號就不猜(`GOOGLE/PIXEL-11/11PRO黑` 的 11PRO 是 Pixel 的)。有歧義就不當成有把握:主檔裡不只一個機型叫 `11PRO` 時,商品已指定機型的只認指定的、沒指定的不猜;`DAP 12` 的 12 不查別牌登記的 `12`;只要有靠數字猜的部分就最多相關(旁邊另有講明的機型對上也一樣);`compare(..., plain=True)` = 不認這些新寫法、就是改之前的比法(實測對改之前的版本近百萬組零差異);防重複的對稱比對(`MatchContext.scan`)守兩條:現在的正向有「明確不同」時,反向只認以前的比法(plain);要升成同一款之前,以前的正向(plain)也必須是會做反向比對的那一種 —— 所以原本靠反向成立的同一款不會不見、原本明確不同的也不會被升成同一款。商品的「其他叫法」不替商品猜機型:主品名有寫型號時,比它的其他叫法一律不認沒字首的寫法(`named_elsewhere`)。實測(測試公司 3,003 個真的品名、另外全量 15,313 個,都補了機型主檔;同一批句子改之前 / 改之後):24 句新手會打的,找不到 5 → 0;機型不寫 IP 的 50 句,排第一 3 → 50;其餘 1,200 句(照原樣 / 換空白 / 少打品牌或顏色 / 順序倒過來)沒有一句變差;「可能已經建過」會擋的品名數沒變(500 個裡 143 個)。**沒寫單位的容量也讀得懂**(2026-10-12,交接包 P1;owner 的例子:商品叫 `iPhone 17 256G 黑色 中古機`,店員打 `17 256 中古機`):自己一塊的 64 / 128 / 256 / 512、而且**同一段文字另外有帶數字的機型**(`17`、`IP17`、`S25`)時讀成 `…GB`(`_bare_capacity`)。不認的:16 / 32(分不出是不是型號)、黏著英文 / 數字、後面是 `%` 或單位(`64%`、`64片`;隔一個空白時要整塊就是單位:`64 W` 不認、`256 米霧灰` / `256 M4` 認)、只有品牌字或只有數字(`iphone 256`、`三星 256`、`OTG 128`)。**兩種讀法都比、取比較好的**(`MatchContext.scan`;`parse_features(..., bare_capacity=False)` = 以前的讀法,只有查詢或那個商品「兩種讀法不一樣」時才多比一次)—— 所以以前對得上的一定還在(`IP12P/256G/64 %/藍` 的 64、`MOTO G54/64 殼` = G64;Codex 首輪抓的),不要改成用推的。「容量不同」的比法沒有動。實測三份真實品名 4,185 個(測試公司、正式站 JB、DONDON):既有品名的判讀、照原樣查、原本的防重複**零差異**;有寫 64~512G 的 919 個品名改成不寫 G,判讀跟原本一樣 918 個(剩 `APPLE/OTG/128G`:沒有機型)。

### 別名:已確認 vs 關鍵字

`ProductAlias.verified=True` 才能自動對應且同範圍唯一(通用別名另有 `uniq_alias_generic`);`False` 是搜尋關鍵字,可多筆。籠統 / 只是品名一部分 / 同時符合多款的叫法自動降為關鍵字。已確認的叫法命中時會重看有沒有別款也符合。改指、停用限管理員;`POST /identity/aliases/remember/` 記住叫法

### IMEI 搜尋安全閥

ProductViewSet.`get_search_fields` 動態化:**只有純數字 6 碼以上才把 `serials__serial_no` 加進 search_fields**,避免「18 pro 256」誤命中含 18 的 IMEI

### 搜尋權重(中文 vs 英數)

`get_search_fields` 偵測查詢字串是否含中日韓漢字(U+4E00–U+9FFF):**含中文 → 只搜描述欄 `name/spec/category__name`**(不碰品號/條碼/IMEI,避免「中古 11」被 SKU `AA-000011` 誤帶出);**純英數 → 搜完整代碼欄位**(sku/name/spec/barcode/category),純數字 6 碼以上才再加 IMEI
