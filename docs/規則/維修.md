## 規則

### 維修單手機解鎖

`RepairOrder.unlock_method`(none / password / pattern)必填;密碼存明文於 `unlock_password`、圖形鎖存「1-5-9-6-3」格式於 `unlock_pattern`;**列印收據自動隱藏**這兩欄,僅維修人員可在後台查看

### 維修單返修

`RepairOrder.is_return_visit` 勾選後跳「歷史維修」modal 依客戶 phone 查 `/repair-orders/history-by-phone/`;`previous_repair_order` FK 自己 + `tenant.repair_warranty_days`(SettingsPage 可調,預設 90 天)即時推算保固狀態;`warranty_info` serializer 動態回傳 status / days_since_complete;Banner 在維修單頁頂顯示綠色「保固有效」或橘色「已超出」;`RepairsPage` 加「僅看返修」filter 與標籤

### 維修收據列印

`/print/repair-receipt/:id` A4 直式一式兩聯(客戶收執聯 + 門市存根聯)中間虛線分隔,印門市抬頭/單號/客戶/機型/故障描述/預估報價/八條注意事項條款/簽名區;**手機解鎖密碼欄不列印**;**自修 / 委外不印**(owner 2026-10-24「不需要給客戶知道」;返修與保固照印);「儲存並列印收據」按鈕儲存後自動 open new tab + auto window.print()。**一聯是固定的半張 A4**(2026-10-24 owner 截圖:簽名那一排壓在注意事項上):會員 / 電話 / 收件日期 / 預計完修一排四欄、維修內容的項目與報價並排、故障描述與維修項目最多兩行;注意事項那一塊不可以被壓扁(`.rr-terms` 是 `flex: 0 0 auto`,`lib/repairReceipt.test.mjs` 會擋),簽名排固定在最下面。加欄位要先確定一聯還放得下(最長的情況要量)

### 維修單快速收件

2026-10-19 起(owner:「門市只是負責收件…要檢測才會有細項」)。新開的單(`RepairEntryPage` 的 `intake = !isEdit`)只有:電話、姓名、機型、序號 / IMEI(開不了機勾「取不到」= `serial_unavailable`)、故障描述、解鎖方式、收件預估費用(`intake_estimate`,印在收件單、註明以檢測後報價為準,不進費用毛利)、隨機配件(`accessories`);門市 / 收件人 / 收件日自動帶(收件日用 `localDay`,不是 toISOString)。電話查不到會員存檔時自動建(電話要像電話,`phoneForNewMember`);存檔整段一次只跑一個(`makeSubmitGate`)。規則在 `lib/repairIntake.ts`;序號必填只擋在畫面。存完打開同一張單才有自修 / 委外、項目、零件、費用、狀態。**自家庫存送去整理的單例外**(沒有門市收件、檢測這一段;owner 2026-10-29「沒辦法先選擇機型，領用零件清單也沒有」):一開單就有自修 / 委外、維修項目、領用零件與委外資訊(`fillNow = !intake || isStock`)。

### 維修單與庫存

只有 `complete` / `reopen` 會動庫存,其他入口不能繞過:`status` 唯讀(只能走 `set-status` / `complete` / `reopen`);已完工或已作廢的單不能修改、不能換狀態;已作廢不能完工;已完工要先重開(歸還零件)才能作廢;維修單不能刪除只能作廢。這些判斷都在鎖住單據之後才做(`services.py` 的 `set_repair_status` / `void_repair_order` / `ensure_editable`)。缺料也能完工(帳可能落後現場):領用照實記全部數量(`repair_usage`),帳上不夠的差額另記一筆 `adjust` 入庫(`ref_doc_type="repair_order_shortage"`),庫存數量 = 異動加總。重開歸還的是**異動紀錄裡實際領出去、還沒還的**(`_outstanding_usage`),還到當初領料的門市,不看單上現在寫的門市 / 零件

### 自家庫存送去整理

2026-10-29(owner:收購的中古機機況太差,整理完再賣,自修或外包;整理費加進那一台的成本;「工資先不算」)。開維修單時「送修來源」選**自家庫存**、刷那一台(`RepairOrder.stock_serial`,`GET repair-orders/stock-lookup/?code=` 先查):沒有會員、不收錢(實付一定 0、沒有收款方式,伺服器擋)、不印收件單;機型與序號照那一台帶(機型 key = 那一台商品的 `phone_model_key`,stock-lookup 回 `model_key`、建單沒給也帶,維修項目照它列),收件門市還沒選就帶那一台的門市(零件從收件門市扣;機器一直掛在原門市);**建單之後不能換台**。規則只有 `repairs/stock.py` 一份:
- **建單**:那一台 在庫 → **整理中**(`refurb`):還掛在原門市、算庫存(報表、每日快照、序號查詢)、**算進平均成本**(`COSTED_STATUSES`);不能賣、不能調撥、不能送廠商換貨;盤點不用刷,盤點單另外列「送去整理」(`refurb_rows`)。只收在庫的(已退的先確認可賣);鎖在門市的帳號只能刷自己門市的(鎖住那一台之後才看)。
- **完工**:加進那一台 `purchase_unit_cost` 的金額 = 維修毛利同一套的「零件成本 + 委外費用」(`money_of` 的 parts + outside,**實際成本;工資、內部結算價不算**);商品 `weighted_avg_cost` 照加權平均加(金額 ÷ 帳上台數);回到在庫;金額記在 `stock_cost_added`。中古機賣掉時成本 = 收購 / 進貨 + 整理(銷貨讀那一台的成本);新機賣掉記平均成本,整理費經上面那一步攤進平均(`inventory.models.book_cost`,2026-10-31)。
- **重開**:照 `stock_cost_added` 扣回、回到整理中;那一台已經不是在庫(賣掉、調撥中、又開了一張整理)就擋。**作廢**(未完工):回到在庫、成本不動。
- 每一步寫一筆 `StockMovement`(`refurb`「整理」,`ref_doc_type="repair_order_refurb"`):**不寫門市 = 只是紀錄、不動數量**;備註不寫金額。開盤之後才整理完回到在庫的不算要刷(看這筆異動的時間)。
- 鎖的順序:維修單 → 商品(零件與那一台的商品同一次)→ 那一台 → 零件的庫存餘額。
- **不算維修月報**(`report.completed` 排掉);清單上客人欄寫「自家庫存」、工資 / 實付 / 毛利是「—」;開單頁最下面只有管理員看得到「整理費」。序號履歷:收購 / 進貨的金額 = 現在的成本扣掉整理加的,另列「整理紀錄」。
- 資料庫變更 `repairs.0010`(`stock_serial`、`stock_cost_added` 有 db_default)、`inventory.0023`、`ledger.0003`(狀態與異動種類的選項)。

### 維修單上當場進零件

2026-10-29(owner:「這材料可能只會有一次進貨，要怎麼做到快速進貨加領料」;選「維修單上直接進貨」,客人的單也能用)。領用零件的搜尋框找不到時有「新零件進貨「打的字」」(要有「進貨入庫」;已完成的單沒有),在框下面展開(不開彈窗):品名、廠商、進價(含稅,跟進貨開單預設的應稅內含一樣)、數量、付款(預設未指定,跟進貨開單一樣)。按「進貨加入」= `POST purchase-orders/quick-part/`,規則只有 `purchasing/quick_part.py` 一份,同一個交易:
- **零件**:用名字建一個零件倉商品(`warehouse_type=parts`、不追蹤序號;要有「商品建檔」;過商品防重複關卡,同名 / 很像回 409 列出既有的,畫面按「就用這個」改進那一個 = 帶 `product`)。只收零件倉、不追蹤序號、不是虛擬的。類別 = 公司放最多零件的那一個 → 代碼 RP(舊系統「維修料」)→ 都沒有就建「RP 維修料」。
- **進貨單**:一張只有這一行的進貨單,進到維修單的**收件門市**(鎖在門市的帳號只能進自己門市),備註「維修單當場進貨」,照一般進貨單入庫、算加權平均成本(`commit_purchase_order`);進貨報表、廠商都看得到。
- **鑰匙**:帶 `Idempotency-Key`(範圍 `repair-quick-part`,跟一般建進貨單分開)。畫面送出前把鑰匙與內容記在這個分頁的 sessionStorage(每張維修單的頁面各一格),拿到確定答案才清;沒回應或閘道逾時 = 不確定:只能「再送一次」、不能收起來、重新整理回同一頁會再展開;這段時間維修單不能存、不能完成(存進去會少這個零件)。
- 進好的零件放進零件清單(已在清單的加數量);**維修單照舊要按儲存**,存檔時伺服器照舊抄零件當下的平均成本(= 這次的未稅進價),完工照舊從收件門市扣。整理自家庫存的單,完工時這筆成本加進那一台。

### 維修毛利與維修月報

2026-10-12(owner:「工資是分業績的」)。**維修毛利全系統只有一份算法**:`repairs/services.py::money_of(order)` —— 自修、內轉 = 客戶實付 − 零件成本;委外給外面的維修廠 = 客戶實付 − 委外實際費用。**工資、內部結算價不扣**(只是收件人與技師之間怎麼分,不是公司付出去的錢);每一張都是 實付 − 零件成本 − 委外費用 = 毛利,也 = 個人毛利分解(`compute_personal_margin`)兩個人加起來(有測試釘住)。修法三種 `way_of()`:`in_house` 自修 / `vendor` 委外 / `transfer` 內轉(委外模式、但維修人員是自己公司另一位)。`compute_margin` 只是它的別名;維修單的回應帶 `margin`(唯讀),維修單清單用它;開單頁還沒存檔時即時算的那一份在 `frontend/src/lib/repairMargin.ts`(同一套規則,兩邊各有測試)。以前同一張自修單三個畫面三個數字(清單沒扣零件、開單頁多扣工資)。委外給外廠的單領了自己的零件不算進毛利(原本三個地方就一致)。**零件成本只用每一行自己記的 `RepairOrderPart.unit_cost`**(建單時抄零件當下的平均成本,自修完工時還沒記到的再抄一次);不拿零件「現在」的平均成本來補 —— 成本真的是 0 的零件之後進貨,已經完工的單毛利不能跟著變,而且開單頁算的也是每一行記的這個數字(複審抓到的 P0)。**維修月報**(`repairs/report.py`,`GET repair-monthly-report/?from&to&warehouse&way&page&export=1`;頁面 `/reports/repairs`;取舊歐睿 MNT015):只算**已完成、沒作廢**的維修單,期間看**完工那一天**(店裡的時區);合計(件數、實付、零件成本、委外費用、毛利)、**人員**(每個人收件幾件、維修幾件、分到多少;全部的人加起來 = 合計的毛利;沒填收件人歸「(未指定)」)、逐筆。在伺服器用同一個函式逐張算(不另外寫一份加總的查詢),一次最多一年。權限 `report_repairs`(報表類第十項,既有帳號預設開著;不在 `ALSO_NEEDS`);鎖在門市的帳號只看自己門市收件的。維修收的現金進營業日報(下面「維修收款與營業日報」那一列)。

**業務員成本(2026-10-28 起)**:零件加進維修單時,單位成本(零件當下的平均成本)與同一刻的業務員成本(`RepairOrderPart.staff_unit_cost`,照公司 / 零件的規則從單位成本加,`staff_cost.from_actual`)一起記,之後改規則不影響這一張;完工時單位成本還是 0 的兩個一起重抄,10-28 之前加的(業務員成本空的)完工那一刻補上,沒補到的當成單位成本。`money_of` / `compute_personal_margin` / `compute_in_house_quote` 多一個 `staff=True`:零件照業務員成本算。**不是管理員**看的維修單毛利、個人毛利分解、報價預覽、維修月報(零件成本、毛利、每個人分到多少)都是 `staff=True`;零件的單位成本與存下來的建議報價只有管理員拿得到(規則在 `core/cost_access.py`)。
