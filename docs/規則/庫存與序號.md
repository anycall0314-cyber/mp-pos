## 規則

### 庫存不足(三處同一套)

2026-10-23 起(owner 選「改」):今日總覽、庫存查詢、庫存警示的「庫存不足」只有 `inventory/views.py::alert_rows` 一份(一般商品看安全庫存;機型專屬配件有關聯主機 → 照主機賣多快動態算);清倉中的不列(看清倉壓力)。今日總覽暫存一分鐘(`home-low-stock:公司:門市`),庫存警示頁即時

### 序號生命週期

進貨建單 → in_stock;銷貨 → sold;銷貨作廢 → 回 in_stock;銷退 → returned(已退,在原銷貨單的門市;確認可賣 → in_stock;作廢銷退 → 回 sold);進貨作廢 → void(須全部還在 in_stock 才能作廢)。**作廢的設備不佔碼**:作廢時把它登記的 IMEI / SN 釋放(`release_codes()`),同樣的碼可以重新入庫(打錯整張作廢重開);作廢的那一筆留著 `serial_no` 當紀錄,`serial_no` 的唯一限制不算作廢的,用碼找設備(`find_serial_ids` / `?code=`)也不會找到它。釋放時如果還有一台「沒作廢、主碼去掉符號後相同、卻沒登記這個碼」的設備(舊資料),碼改登記給它(先鎖住那一台再判斷)。Django 後台不能新增 / 刪除設備,狀態與序號唯讀

### 序號退回後續處理

2026-10-23(owner「先標不能賣，確認可賣再點回倉」;同一天稍早做成直接回在庫,紅隊提醒瑕疵機會被賣掉):銷退完成的那一台 = **已退**(`returned`,在原銷貨單的門市;不能賣、不能調撥,可以直接送廠商換貨),**確認可以賣才回在庫**:序號查詢狀態「已退」那幾台旁邊「確認可賣」(按兩下)/「廠商換貨」(帶著碼去廠商換貨頁)。`POST /serials/<id>/release/`(`sales.services.release_returned`:鎖住那一台、要是已退才改在庫,記一筆 `return_release`「退回可賣」異動 —— 不寫門市、不動數量、`ref_doc` = 是哪一張銷退退回來的、備註寫誰按的);**員工帳號「確認可賣」`release_returned`**(分類「商品」,預設開著;紅隊:放行的人老闆要能收回),鎖在門市的帳號只能按自己門市的。今日總覽「需要注意」多「退回待確認 N 台」(`home-summary` 的 `returns_pending`;點了到序號查詢 `?status=returned`)。**盤點也要刷已退的**(紅隊:東西在店裡、算在期末):`expected_serials` 收在庫 + 已退;沒刷到算少、核准標盤虧(`StockCountMissing.was_returned` 記下來),找回時回到已退(不直接變成可以賣)。**已退算進平均成本**(`COSTED_STATUSES`;複審 P0:不算的話退回來之後再進一批,平均被新的那一批拉走)。**已退送廠商換貨再按「標錯了」回到已退**(`VendorExchange.was_returned`;複審 P1:不然沒有「確認可賣」權限的人可以這樣繞過),「已換貨」收回來照舊回在庫(廠商處理過的)。以前(更早)的已退沒有入口轉回在庫,正式站、測試站當時都是 0 台

### 設備兩個碼(IMEI / SN)

一台設備可以登記 IMEI、SN 兩個碼,可以都有、也可以只有一個。`ProductSerial.serial_no` 是**主碼**(有 IMEI 用 IMEI,沒有才用 SN),標籤 / 單據 / 既有畫面照舊讀它;兩個碼各存一列在 `ProductSerialIdentifier`(拍照入庫另外可能有 IMEI2 / EID)。**同一家公司裡一個碼只屬於一台**(IMEI、SN 一起比,比對前去空白 / 破折號 / 點、轉大寫),所以銷貨 / 調撥 / 查庫存刷哪一個碼都是同一台。規則集中在 `apps/inventory/identifiers.py`:**新增設備一律走 `create_serial()`**(進貨、個人收購、舊資料匯入都是;直接 `ProductSerial.objects.create()` 那一台沒登記碼,別台就能再用同一個碼,`test_identifiers.py` 掃全專案把關);用碼找設備走 `find_serial_ids()`(完全相同才算;不找作廢的)。比對一律比**去掉符號後的值**:登記的碼比 `ProductSerialIdentifier.normalized_value`,主碼比 `ProductSerial.serial_key`(`serial_no` 正規化後的值,`save()` 自動算;**改主碼要走 `save()`,不要 `queryset.update(serial_no=…)`**),所以沒登記到識別碼表的舊設備(碼去掉符號後跟別台相同的那種)一樣找得到、擋得住。進貨的 `serial_numbers` 每台是 `{"imei", "sn", …}`;舊格式(純字串、或沒有 `imei` 鍵的 `{"sn"}`)= 沒講是哪一種,15 碼數字且檢查碼正確的放 IMEI、其餘放 SN。有明講就照放,**IMEI 檢查碼不對只在畫面提醒、不擋**。進貨頁刷條碼的分格在 `frontend/src/lib/deviceCodes.ts` 的 `routeCodes`(`npm test` 有測試):盒上有 IMEI、IMEI2、SN 好幾個條碼,**光看碼分不出「下一台的 IMEI」還是「同一台的 IMEI2」**,所以序號側欄有「每台刷 IMEI 與 SN」開關(記在瀏覽器):關 = 一個碼一台;開 = 先補齊這一台,這一台已有 IMEI、還缺 SN 時再刷到 IMEI 不放並提示(多半是 IMEI2)。刷錯格會還原原本的碼;Enter 與 Tab 結尾的條碼槍都走同一套。批次貼上是一個序號一台,個數與數量不一致會擋。搜尋:`/serials/?search=` 比對每一個碼(可打末幾碼),有碼對得上就不走相似度比對 —— 這是給下拉挑序號用的「包含」比對,**刷條碼自動掛序號一律用 `/serials/?code=`(完全相同)**,否則同商品另一台的碼剛好包含這串字時會掛錯實機。銷貨掃碼先 `findDevicesByCode()`:對到兩台以上(舊資料的碼撞在一起)擋下不加、那一台不在這個出貨倉或不是在庫就講出它在哪,只有剛好一台、在庫、在這個倉才自動掛;「只對到一部分」的只在下拉裡由人挑,掃碼不自動掛;`/products/?search=` 對登記的碼只收**完全相同**的(不會像「18 pro 256」那樣誤中別台 IMEI;純數字 6 碼以上比對主碼一部分是原本就有的);庫存查詢頁(`stock-matrix`)原本完全不比對序號,現在收完全相同的碼,純數字 6 碼以上再比對碼的一部分。事後補登 / 修改:`POST /serials/{id}/codes/`(`set_codes()`)——店員只能補空的那一格,已登記的碼只有管理員能改,作廢的設備不能改,鎖倉帳號只能動自己門市的(已售出的 = 自己門市賣出去的;調撥中的只有管理員能動;「在不在他的門市」在鎖住那一台之後才判斷,走 `set_codes(check=…)`);每次改動留一筆 `ProductSerialCodeChange`(只增不改)。拍照入庫照登記時講的種類把 IMEI / SN 交給進貨(不重新猜、主碼一樣 IMEI 優先,不看哪個被標成主識別碼;碼沿用它原本的做法存去掉空白後的值)。既有設備由 migration 0012(主碼補登記)、0013(有 IMEI 的主碼換成 IMEI)、0014(補 `serial_key`、作廢的釋放碼、在用沒登記的補登記)補齊。每日對帳多一項「序號:每一台的碼都有登記」。雙卡機第二組 IMEI 的一般入庫不做(owner 2026-10-04 決定;拍照入庫原本就會存的 IMEI2 照舊)

### 序號防呆(輸入當下就提醒)

owner 2026-10-10:「已在庫的序號不可再入庫第二次」。**存檔時本來就一定擋**(每個會新增設備的入口都走 `inventory/identifiers.py::create_serial()` → `taken()`:IMEI、SN 都比、去掉符號不分大小寫,只要沒作廢就佔著碼 —— 在庫、調撥中、已售、已退、維修中都算;資料庫另有兩條唯一限制),這一條規則沒有動。**多的是輸入當下就講**:`POST /serials/check/ {codes:[…最多 500]}` → 其中已經被用掉的是哪個商品、哪家門市、什麼狀態、`in_store`(還在店裡 = 在庫 / 調撥中 / 維修中);只讀、只看自己公司(鎖在門市的店員也查得到別家門市的)、不回成本;比法 = `taken_details()`,**有測試釘住它跟 `taken()` 說的是同一批**(改其中一邊要兩邊一起改)。畫面:**看的是「這張單上現在有哪些碼」,不是掛在某幾個輸入事件上**(掃的、打的、貼的、批次貼上的、草稿帶回來的都算)—— `api/serialCheck.ts` 的 `useSerialCheck`(停 0.4 秒才問、只問沒查過的、問不到 5 秒後再問、換一張單全部重問),規則在 `lib/serialCheck.ts`。有問題的碼(已經在系統裡 / 這張單裡重複)**不替人拿掉**(紅隊:批次貼三十支被剔三支,單上二十七、手上三十,帳實就對不起來):那一格標紅寫原因、明細上方一條、序號格收起來時那一行標「有問題」、儲存先擋。進貨開單頁的掃碼框本來就會擋(`onScan` → `findDevicesByCode`),這次只加門市。個人收購(`SecondhandPersonalEntry`)兩種講法(紅隊:只講「已經在系統裡」店員會把客人請走):還在店裡 →「同一個序號不會有兩台,請核對實機」;已售 →「是我們賣出去的,賣出去再收回來的功能還沒有,先不要收」。查不到答案(斷線)不當成有問題也不當成沒問題。**沒做**:賣出去的手機收回來(owner 說另外排;現在會被擋);拍照入庫的畫面(登記每一台時伺服器當下就擋)

### 配件庫存

非序號商品(`requires_serial=False`、非 virtual)走 `StockBalance(product, warehouse)`,進貨累計、銷貨扣減、調撥搬移;`Product.weighted_avg_cost` 跨倉聚合

### 配件不足擋下

銷貨單若該倉 balance 不足,`commit_sales_order` 拋錯 400,不允許負庫存

### 調撥

`TransferOrder` 兩階段:`dispatched`(來源倉派發,序號 → in_transit、配件 balance 扣掉)→ `confirmed`(目的倉確認,序號 → in_stock 在目的倉、目的倉 balance 加上)。`unit_cost_at_dispatch` 在派發時快照來源倉成本,確認時用以重算目的倉加權平均(避免後續異動干擾)。`void` 智能回滾,依當下狀態決定

### 整張調撥

進貨單頁「整張調撥」→ 調撥單頁(`/transfers/new?from_po=編號`)自動帶好那張進貨單還留在進貨門市的全部商品與序號,選目的倉就能派發;之後照一般調撥(派發 → 目的倉確認)。內容來自 `GET /purchase-orders/{id}/transferable/`(只讀):序號商品只列「這張單進來、還在進貨門市、在庫」的那幾台,已賣 / 已調走 / 已退的列在 `gone` 並在畫面講出來;配件數量 = 這張單進的數量,但不超過進貨門市現有庫存(配件不分批);同商品多行併成一行;虛擬商品不列;作廢的進貨單回 400。它只是帶出建議內容,**真正能不能調由調撥存檔時鎖住庫存再檢查**

### 先鎖再檢查、再改

`apps/inventory/locking.py`,銷貨 / 銷退 / 進貨 / 調撥 / 維修共用。**每一個會改庫存或序號狀態的動作都照這三步、而且都在交易內**:(1) `lock_document()` 鎖單據自己那一列並重讀,才判斷是不是已作廢 / 已確認 / 已完工;(2) `lock_stock_rows()` 照固定順序鎖這張單會動到的東西:商品(要改加權平均成本時)→ 序號 → SIM 卡 → 庫存餘額(照門市、商品編號);(3) 鎖完才檢查在不在庫、夠不夠扣,才改。不這樣做:同一支 IMEI 會被兩張單各賣一次、庫存會少算一次、同一張單會被確認 / 作廢兩次、明細順序相反的兩張單會死結。商品 / 序號 / SIM 卡用 `no_key=True`(不擋別張單新增指向它的列)。改數量一律經 `locked_balance()`,不要直接 `StockBalance.objects.get()` 再加減

### 每日庫存快照與對帳

### 庫存查詢的搜尋

2026-10-09 起(owner:「還要再帶入通訊的常用語彙,比如 IP=IPHONE, U=Ultra, +=Plus」)。`stock-matrix` 的 `search` = **原本的**(整串字照字面:品號 / 品名 / 規格 / 條碼 / 類別,加上設備的碼)**聯集兩種多的**,只會多找到、不會少找到:(1) **一個字一個字比**(空白 / 斜線 / 逗號拆開),每個字都要在**品名 / 規格 / 類別**裡對得上(品號、條碼不拆字去比 —— 「iphone 17」的 17 會對到條碼裡的 17),每個字可以照字面、也可以是**通訊常用語彙表**裡的另一種寫法,型號中間有沒有空白 / 連字號都算;(2) 跟商品清單同一套共用比對(`find_candidates`:其他叫法、有機型主檔時更準)。**語彙表只有 `backend/apps/catalog/shop_terms.py` 一份**(`TERMS`;從舊系統 15,312 個品名數出來的):`IP` = iPhone(舊系統的 `APPLE-18PM`、`APPLE-I6S` 也算)、`PM` = `PMAX` = `P MAX` = Pro Max、`P` = Pro(接在數字後面;打 Pro 連 Pro Max 也出來)、`+` = Plus、`U` = Ultra、Fold / Flip = Z Fold / Z Flip、`ZF` = ZenFone、`SAM` = 三星 = Samsung = Galaxy、華為 / 小米 / 紅米 / 蘋果 / 谷歌 / 華碩 / 索尼 = 英文、`256G` = `256GB` = 單寫 `256`、`1T` = `1TB`、`黑色` = `黑`。不亂對到的幾條:單獨一個數字要是那個數字(`17` 不對到 `251017`);很短的詞(`U` / `PM` / `IP` / `+`)單獨打只認帶條件的寫法(`UAG` 的 U、`IPAD` 的 IP、`8+256G` 的加號不算);型號從一個字的開頭對起。**要加一個詞:在 `TERMS` 加一筆 + `test_shop_terms.py` 補「打什麼 → 找得到 / 找不到」**;比對式要 Python 的 `re` 與 PostgreSQL 都能跑、意思一樣:`TERMS` 裡照習慣寫大寫 / `\d` / `\s`,交出去之前 `_portable()` 全部寫明(大小寫 `[Ii][Pp]`、數字 `[0-9]`、空白只認列出來的四種),查詢用**分大小寫**的 `__regex`,不靠資料庫的「不分大小寫」(兩個引擎對空白、數字、非英文字母大小寫的看法不一樣;有測試兩邊各跑一次比答案)。它跟共用比對(`identity/product_match`)是兩支:那一支認定「是不是同一個商品」、要準、要機型主檔;這一支只給查詢、要找得到、不替人做決定。**商品清單與開單頁的搜尋還沒用語彙表**(`BACKLOG.md`)
