# 資料底層與自然語言報表：規劃

> 目標(使用者原話整理):**把底層資料庫做到最扎實;報表維度可以讓不同使用者自由組合;
> 未來管理者只要用自然語言就能完成需求 —— 開發者不需要迎合每個人去做各式各樣的報表。**
>
> 跟專案既有原則一致:POS 是帳本,AI 是操作介面;AI 只把人話翻成固定格式,不直接碰資料
> (見 [assistant-command-layer.md](assistant-command-layer.md))。

## 0. 一句話

新的報表需求 = **組合既有的「指標 × 角度 × 條件」**,不是寫新的報表頁。
開發者只負責把「指標」和「角度」定義清楚、把底層資料記完整;怎麼組合交給使用者或自然語言。

## 1. 四層架構

```
 管理者:「上個月湳雅店各品類毛利,跟去年同期比」
        │
 ④ 自然語言層   AI 把句子翻成一張「查詢單」(固定格式),先用白話回報「我理解成…」
        │       不寫資料庫指令、不寫入、看不懂就追問
        ▼
 ③ 語意層       指標 / 角度 / 權限的唯一定義;查詢單在這裡驗證、編譯、套權限
        │       報表畫面(自由組合)與自然語言共用 → 同一個問題只有一種數字
        ▼
 ② 對照層       舊店名 / 舊品號 / 舊業務員 / 舊會員 → MP 的門市 / 商品 / 業務員 / 會員
        │       對不到歸「未對照」,不丟、不猜
        ▼
 ① 帳本層       每一筆業務事件完整、不可改(作廢用旗標)、當下的價格與成本存死
```

另有一條橫向的 **自動對帳**:每天檢查帳本自己是否前後一致,不一致就提醒。

## 2. ① 帳本層

### 2.1 事件清單(每一種事件「一列代表什麼」)

報表的最小單位必須清楚,否則加總會重複或漏算。

| 事件 | 一列 = | 日期 | 主要角度 | 數值 |
|---|---|---|---|---|
| 銷貨明細 | 一張銷貨單的一個商品列 | 單據日期 | 門市、商品、業務員、會員、客戶、付款、電信方案 | 數量、金額、成本(過帳當下)、佣金 |
| 銷退明細 | 一張銷退單的一個商品列 | 單據日期 | 同上(連回原銷貨列) | 數量、金額、沖回成本 |
| 進貨明細 | 一張進貨單的一個商品列 | 單據日期 | 門市、商品、供應商、進貨類別 | 數量、計價數量、金額、到岸成本 |
| 調撥明細 | 一張調撥單的一個商品列 | 派發 / 確認日 | 來源門市、目的門市、商品 | 數量、派發當下成本 |
| 庫存異動 | 一次庫存進出 | 異動日 | 門市、商品、序號、異動類型、來源單據 | 數量 |
| 每日庫存快照(新增) | 某天收店時、某門市、某商品 | 快照日 | 門市、商品 | 在庫數、當時加權平均成本、庫存金額 |
| 收款 | 一張銷貨單的一筆付款 | 單據日期 | 門市、付款方式 | 金額 |
| 雜支 / 現金調整 / 代收話費 | 一張單 | 單據日期 | 門市、類別、經手人、電信商 | 金額 |
| 維修單 | 一張單 | 收件 / 完修日 | 門市、技師、業務、維修項目、外修廠商 | 報價、實收、外修成本 |
| 舊 POS 消費明細 | 舊系統一張單的一列 | 來源交易日 | 經對照的門市 / 商品 / 業務員 / 會員,或「未對照」 | 原始金額、淨額(依單別正負) |

### 2.2 要補強的地方(做「扎實」要先補的洞)

1. **銷貨 / 銷退明細存「未稅金額」與「稅額」**。現在只有含稅或依單頭稅別而定的金額,
   毛利要回推單頭稅別;規則一改,舊報表就變。過帳當下算好存死,既有資料用 migration 回填。
2. **每日庫存快照**。庫存金額、庫齡、週轉天數都需要「過去某一天的庫存」,事後無法從異動
   準確倒推成本。每天收店後由背景程式記一份(只記有庫存或當天有異動的)。
3. **商品的分類屬性**(品類 / 品牌 / 機型 / 新或中古)預設用「現在的分類」報表;
   需要「當時的分類」的指標另外標明,不默默混用。
4. 所有日期一律以台灣時區的營業日為準;金額顯示一律整數(既有規則)。
5. 作廢不刪除(既有規則),所有指標明確寫「排除作廢」或「含作廢」。

## 3. ② 對照層

舊資料要能跟新資料放在同一張報表裡,靠的是對照,不是改寫舊資料。

| 對照 | 從 | 到 | 用途 |
|---|---|---|---|
| 門市 | 舊店名原文(湳雅店、民生店、亞太巨城、維修倉) | `Warehouse` | 十年銷售按門市比較 |
| 商品 | 舊品號 + 舊品名 | `Product` | **庫存搬家與十年商品分析共用同一張表** |
| 業務員 | 舊業務員代號 | `SalesPerson` | 業績十年比較 |
| 會員 | 舊會員精確編號 | `Member` | 會員頁看舊紀錄、會員十年消費 |

共同規則:

- 原文永遠保留;對照是另外一層,可以改、可以撤銷,有確認人與時間。
- 自動只出「候選」(例:電話相同、叫法比對命中),**由人確認**才算數;不確定的進待確認清單。
- 對不到的歸「未對照」,報表上看得到有多少、佔多少金額,不丟、不猜。
- 一個舊代號只能對到一個新對象;一個新對象可以有多個舊代號(例:同一人有兩個舊會員號)。

## 4. ③ 語意層(指標與角度的唯一定義)

### 4.1 內容

- **角度**:門市、日期(日 / 週 / 月 / 季 / 年)、品類、品牌、機型、商品、新機 / 中古、
  品況、業務員、會員、客戶類型、供應商、付款方式、電信商 / 方案、單別、資料來源(新 / 舊 POS)。
- **指標**(第一批):銷售額(未稅 / 含稅)、銷量、毛利、毛利率、銷貨成本、客單價、來客數、
  銷退金額 / 率、進貨金額、庫存數量、庫存金額、週轉天數、庫齡、雜支、代收話費、維修實收、
  舊 POS 原始額 / 淨額。
- 每個指標寫明:來自哪一種事件、算法、是否排除作廢、可以搭配哪些角度、誰看得到。
- **權限跟著定義走**:每個指標 / 角度都寫明誰看得到(例如成本 / 毛利類、只看自己的店、
  含會員姓名電話的明細可遮罩)。目前決定暫時不鎖(見第 8 節),但定義照寫,之後要鎖只要打開。

### 4.2 查詢單(報表畫面與自然語言共用)

```json
{
  "measures": ["毛利", "銷售額_未稅"],
  "dimensions": ["品類"],
  "filters": [{"門市": "湳雅店"}],
  "period": {"from": "2026-09-01", "to": "2026-09-30", "grain": "月"},
  "compare": "去年同期",
  "sort": "-毛利",
  "limit": 50
}
```

- 後端驗證:指標 / 角度都在定義裡、搭配合法、使用者有權限;再編譯成資料庫查詢,
  自動加上公司與門市範圍。**使用者與 AI 都無法送出任意資料庫指令。**
- 筆數、時間有上限;結果附上「實際套用的條件」讓人核對。
- 查詢單可以存成「我的報表」,下次一鍵打開;管理員可以分享給全公司。

### 4.3 自由組合報表頁

一個頁面:選指標、選列 / 欄的角度、選條件與期間、選比較(上期 / 去年同期),出表格與圖,
可匯出。**之後的報表需求在這裡組合,不再寫新頁。** 現有的固定報表(銷貨日報等)保留,
逐步改成用同一套定義計算,確保數字一致。

## 5. ④ 自然語言層

- 管理者打一句話 → AI 輸出**同一種查詢單**(固定格式,不能自由發揮) → 畫面先顯示
  「我理解成:湳雅店、2026 年 9 月、依品類、毛利與銷售額」→ 確認或直接執行 → 出表。
- 看不懂、有歧義(例:「上個月」是自然月還是近 30 天;「手機」是品類還是全部主機)就追問。
- 只讀不寫。寫入類需求(下單、調貨)仍走既有的指令層(先提案、人確認、service 過帳)。
- 每次的問題、AI 的翻譯、使用者的修正都記下來,用來改進翻譯與補指標定義。
- 送到外部模型的只有問題與定義,不送客人個資;含個資的結果在本機遮罩(見 roadmap 的資安段)。
- 模型可以便宜、可以換:錯的翻譯會被語意層驗證擋下,不會產生錯的數字。

## 6. 自動對帳(讓「扎實」長期維持)

每天背景執行,結果存表、異常在管理頁提醒:

- 庫存餘額 = 庫存異動加總(各門市、各商品);序號狀態與所在門市一致。
- 單據合計 = 明細加總;收款合計 = 單據總額。
- 每日庫存快照與當天庫存餘額一致。
- 舊 POS 匯入的筆數與金額 = 封存檔的核對值;待核差異仍在待核。
- 對照層:未對照數量與金額的變化。

## 7. 順序

| 步驟 | 內容 | 完成的樣子 |
|---|---|---|
| 1 | 對照層 + 舊 POS 十年歷史匯入(含對照欄位) | 十年資料在隔離環境完整匯入、筆數金額與封存一致;會員 / 門市 / 業務員 / 商品對照可確認;會員頁看得到舊紀錄 |
| 2 | 庫存期初搬家(用同一張商品對照表) | 舊庫存表試跑:配對結果、待確認清單、配不到的處理;切換日可一鍵寫入期初庫存 |
| 2.5 | 自動對帳 + 帳本補強(未稅金額、每日庫存快照) | 每日檢查上線;既有資料回填(不用等庫存檔,先做) |
| 3 | 語意層 + 查詢單 + 自由組合報表頁 | 第一批指標可任意組合;現有日報數字與新引擎一致 |
| 4 | 自然語言查詢 | 常見問句能正確翻成查詢單;有歧義會追問;只讀 |

每一步都照既有流程:隔離環境測試 → 紅隊 → Codex 複審(最多三輪)→ 你同意才部署。

## 7.1 進度

- 第 1 步(對照層 + 舊 POS 十年歷史匯入):程式完成,真實封存在隔離環境匯入、核對、備份還原都通過
  (見 [舊POS十年會員歷史_匯入與對照手冊.md](舊POS十年會員歷史_匯入與對照手冊.md))。紅隊一輪 +
  Codex 複審三輪已收斂,第三輪的修正未再送審。已 commit,尚未部署;正式匯入到手機玩家新竹店。
- 實測發現:舊品號用量最多的有很多是**帳務項目**(手續費、維修收入、電信續約、收購、獎金、違約金),
  不是商品。第 3 步的語意層要有「商品銷售 / 帳務項目」這個角度,兩者分開看。
- 第 2.5 步(帳本補強 + 自動對帳):程式完成,尚未 commit。紅隊 1 輪 + Codex 複審 3 輪已收斂(第三輪只剩 2 項小問題,已修、未再送審)。
  - 銷貨 / 銷退每一行存死未稅與稅額(整單加總 = 單頭);銷退存沖回成本;既有資料回填。銷貨日報改讀存好的值。
  - 每日庫存快照(門市 × 商品 × 在庫 / 退回待處理 / 維修中 / 調撥中)+ 每日對帳 15 項,
    收店後由備份背景程式自動做,「設定 → 每日對帳」看結果。
  - 在隔離資料庫用本機資料跑:銷貨、銷退、序號、舊 POS 合計全部一致;唯一不一致是 3,763 筆配件
    「有庫存數量、沒有異動紀錄」—— 之前用 `import_legacy_inventory` 鋪的期初數量。
    **所以第 2 步的期初庫存寫入一定要連同「期初」異動一起寫**,對帳才會一致。
  - 複審時發現**銷退與銷貨原本就有的跨公司漏洞**:猜到別家公司的單號 / 門市 / 商品 / 序號編號,
    就能拿來建單(銷退還會改到別家的序號狀態);鎖在自己門市的店員也能在別家門市建單。
    銷貨 / 銷退已修(欄位只認自己公司 + 存檔前再核對 + 補回門市鎖)。
  - 順便修好:**銷退畫面原本一直建不了單**(畫面沒送門市與單價,後端卻要求必填),
    現在由原銷貨單帶入,已在瀏覽器實際建過一張。
  - **同類漏洞在進貨、調撥、雜支、現金調整、代收話費、維修也有**(建單沒檢查門市鎖、欄位接受別家編號),
    要另外一批修,修法已經做成共用元件。
  - 舊的銷退當初沒算成本、也沒有作廢時間,回填用固定規則:目前有效的銷退把一行全部退完時,
    沖回加總 = 原行成本;作廢的只按比例。
- 做 2.5 時看到、還沒處理(牽涉生意規則,要你決定):
  - 銷退的退款金額用「數量 × 單價」重算,原銷貨行如果有打折(實收金額 < 數量 × 單價),會退得比收的多。
  - 配件銷貨成本用「該門市」的加權平均,跟決策紀錄寫的「全公司不分倉」不同;新機(非中古)
    銷貨成本用每台自己的進貨成本,也不是加權平均。哪一個是對的要先定,報表才有唯一答案。

## 8. 已決定(2026-10-04)

1. **新舊並行一段時間**,切換日未定:要先解決條碼列印機與發票列印機。
   並行期間舊系統是帳的正本;MP 的期初庫存在「MP 變成正本那天」才寫入,在那之前只在隔離環境試跑。
   切換當天再補抓一次舊系統的會員消費(見手冊 3.1)。
2. 新機逐支 IMEI 的庫存、含成本(或進價)的庫存:**舊系統可以匯出**,由你匯出後交給開發。
3. 正式機匯入的公司:**手機玩家新竹店**(含湳雅店、民生店、維修倉)。實際匯入前再核對公司代碼。
4. 報表權限**暫時不鎖**:店員也看得到成本與毛利、不限門市。語意層仍把「誰看得到」寫在每個指標的
   定義裡,之後要鎖只要打開,不用改報表。
