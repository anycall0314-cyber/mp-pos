# 舊 POS(歐睿)十年會員消費:匯入與對照手冊

> 對應 `MP_POS_十年會員歷史消費_對接規格.md`(封存包裡的 `specification/`)與
> [資料底層與自然語言報表_規劃.md](資料底層與自然語言報表_規劃.md) 第 1 步。
> 程式在 `backend/apps/legacy/`。本文寫的是「目前程式實際的行為」。

## 1. 這是什麼

舊 POS 十年(2016/10/03–2026/10/03)會員消費的完整封存,匯進 MP 之後:

- 會員頁可以看到那個人在舊 POS 的每一張單、每一筆明細(含負數、零元、空白單價)。
- 舊店名 / 舊品號 / 舊業務員可以對到 MP 的門市 / 商品 / 業務員,十年資料之後才能跟新系統
  放在同一張報表。
- **只供查詢**:不會產生銷貨單、不動庫存、收款、發票、點數,不發通知,也不參與「上次成交價」。
- 金額是舊系統報表值,不等於實收或營收。原始額與淨額(依單別正負)分開。

## 2. 原則

- **原文不改**。會員編號的空白、Tab、前導零、中文;店名、品號、品名、換行備註;帶正負號的
  數量與金額;空白單價(存空值,不補 0)全部照來源。擷取當下的頁面全文與報表列也都存著,
  可以用 SHA-256 重新核對。
- **對照是另一層,由人確認**。電話、名稱、代碼只拿來列候選,不會自動歸到「第一個同電話的人」。
  每一次確認 / 撤銷都有紀錄(誰、何時、為什麼)。
- **待核的不混進已核對**。封存裡有 1 位會員的來源累計(2,400)跟完整明細(1,290)對不上,
  那 2 筆另外存成「待核」,不算進任何合計;會員頁會提示「有待核舊 POS 紀錄」。

## 3. 匯入(主機上的管理指令)

```sh
cd backend
# 1) 試算:核對封存、算出會新增 / 換版 / 不變多少,不寫任何東西(預設就是試算)
python manage.py import_legacy_history --tenant 公司代碼 \
  --archive "/路徑/ten-years-20161003-20261003" --period 2016-10-03:2026-10-03

# 2) 寫入:明確指定公司;封存有來源差異時一定要加 --reconciled-only
python manage.py import_legacy_history --tenant 公司代碼 --archive ... --period ... \
  --confirm --reconciled-only

# 撤回 MP 這邊的某一批(只動那一批帶進來的東西)
python manage.py import_legacy_history --tenant 公司代碼 --rollback 批次編號 --confirm
```

- 一定要指定公司(`--tenant`),不會自動選。期間要等於封存涵蓋的期間。
- 寫入時一律整份封存一起處理(不能只選部分批次)。寫入前先把**全部批次**核對完,任何一項不對,一筆都不寫:
  - 資料庫與每一批匯入內容檔的雜湊、封存版本、來源系統、期間、單別正負規則;
    manifest 每一批只能列一次、檔名要跟資料庫記的一樣;匯入內容檔的格式版本要對;
  - 每一份快照全文雜湊;每一張單的內容雜湊;每一筆明細的**每一個欄位都跟報表列原文對得上**
    (品號、品名、數量、單價、金額、未稅額、點數、店別、日期、業務員、客戶、備註、促銷);
  - 單據、版本、待核都掛在同一位會員、同一批的快照上;會員清單跟快照一一對應;
    每張單的擷取時間要等於它所屬快照的擷取時間(換版靠這個時間判斷新舊);
  - 待核紀錄的原始列也要能讀、單別要認得,金額 / 筆數 / 單據數 / 差額重算一致;
  - **每位會員的明細淨額都自己重算,跟會員清單上的累計原文比**:對得上的不能被標成待核,
    對不上的一定要在待核裡(不只相信封存自己的分類);封存標的待核數也要跟實際一致;
  - manifest 的核對值缺任何一項就拒絕(不當成「不用核對」);報表列日期要正好 8 位數的合法日期;
  - 每一批跟它自己的**匯入內容檔(另一份獨立來源)逐筆比對**,一筆不多一筆不少;
  - 每一批與全部的筆數金額(已核對,以及已核對 + 待核)等於封存核對值;
  - 每一個值都放得下(長度、日期、金額範圍),不會寫到一半才被資料庫擋下。
- 同一張單在同一個擷取時間有兩種不同內容 → 當成衝突拒絕,不靠匯入順序決定(試算就會講)。
- **同一份封存裡同一張單有好幾個版本 → 整份拒絕**:封存只替最新那一版存了逐筆明細,哪一版
  生效不猜。不同時間的擷取要分成不同封存匯入(切換前的補抓本來就是另一份封存)。目前這份
  十年封存沒有這種單。
- 不認得的單別一律擋下(目前認得 E01、E11、E12、E13 為正;F01、F11、F13、FS11 為負)。
- 每位會員一個交易;中斷後重跑,已寫入且內容相同的直接略過,不會重複。
- 公司正在還原時不能匯入;每位會員寫入前都會再確認一次,匯入途中公司被還原過就停下(重跑即可,
  已寫的會略過)。同一家公司同時只能有一個匯入或撤回在跑。
- 寫到一半因為意外中斷(例如主機關機):那一批狀態會停在「匯入中」,重跑同一個指令會從頭比對、
  補完剩下的;或用 `--rollback` 撤回那一批。
- 實測時間:試算約 2.5 分鐘(記憶體高峰約 1.1 GB,主要是讀兩個各約 110 MB 的匯入內容檔);
  寫入約 4–5 分鐘。
- `--report 檔名.json` 可以把完整報告存下來。

### 3.1 切換前的「補抓」

10/3 之後舊 POS 還會繼續有交易。切換當天(舊系統打烊後)再擷取一次「10/4 到切換日、
往前多抓幾天」的新封存,用同一支指令匯入:

- 同一張單內容沒變 → 不變(多留一份版本紀錄)。
- 同一張單被改過、而且這次擷取比較新 → 整張換成新內容,舊內容(含逐筆明細)留在版本紀錄。
- 這次擷取比 MP 裡的還舊 → 只留成歷史版本(含逐筆明細),不覆蓋。
- 撤回某一批時,單據回到「剩下的批次裡擷取時間最新」的那一版;沒有別批就刪掉。
  品名顯示也跟著重算,那個品號已經沒有任何明細就清空。
- 會員姓名 / 電話以最新一次擷取為準。

## 4. 對照(設定 → 舊系統對照,公司管理員)

| 分頁 | 對到 | 怎麼做 |
|---|---|---|
| 會員 | MP 會員 | 「對照會員」看候選(電話 / 姓名相同)或自己搜尋;「建立會員」用舊資料在 MP 建一位(同公司已經有同電話的會員就不建,電話很短也一樣,請改用對照;兩人同時按也只會建一位) |
| 店別 | 門市 | 店名相同的列為候選 |
| 品號 | 商品 | 代碼相同(條碼 / 品號)優先,再用品名做叫法比對;**也是之後庫存搬家用的同一張表** |
| 業務 | 業務員 | 代號或姓名相同的列為候選 |
| 待核 | — | 看原始列與差額;要結案必須寫理由並附上新的來源證據,原始數字不改 |

清單依「用量」排序(舊代號出現在多少筆明細、淨額多少),先處理影響大的。
這一頁只有**這家公司自己的管理員**能用;平台管理員也不行(會員個資與原始證據不從一般網址跨公司給)。
一個舊代號同時只對到一個對象;要改先「取消對照」再重新選,兩次都記錄。

會員頁(會員管理 → 選一位會員)下方的「舊 POS 紀錄」:

- 一般店員:只看得到已確認對照到這位會員的舊紀錄;點開單據時也只能開這位會員名下的。
- 合計(張數、筆數、淨額、原始額)由後端照完整篩選條件算,不是只算畫面上那一頁。
- 可以依日期、店別、單別、單號篩選;點一張單看全部明細。
- 管理員另外看得到「可能是同一人」的舊會員,可直接確認對照;也看得到報表列原文。

## 6. 已知限制

- 同一份封存裡有多版本單據的封存不收(見第 3 節)。跨封存的換版(補抓)會保留舊版明細,可以撤回。
- 撤回不會把會員的姓名 / 電話改回去(那只是顯示用,以最新擷取為準)。
- 用量最多的舊品號很多不是商品,而是帳務項目(手續費、維修收入、電信續約、收購、獎金、
  違約金…)。這些不會對到庫存商品;報表要把「商品銷售」與「帳務項目」分開(規劃第 3 步處理)。
- 正式機要匯進「手機玩家新竹店」(2026-10-04 決定),匯入前先核對公司代碼;
  本手冊本身不授權直接匯入正式資料。
- 格式明顯壞掉的封存(例如欄位型別不對、JSON 結構缺一塊),有些會以技術性的錯誤訊息擋下,
  不是白話說明。一樣一筆都不寫,只是訊息不好懂(後續追蹤)。
