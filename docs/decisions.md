# 設計決策紀錄

> 採用簡易 ADR 風格。每條決策包含日期、選擇、理由、未採用的替代方案。

## 2026-05-17：唯一日常介面是 React,Django admin 退到背後

**選擇**:所有日常作業介面(CRUD / 過帳 / 查詢 / 設定)都在 React app 完成。Django admin 不刪,但只當 dev 階段測資工具與緊急維運 fallback,不引導使用者使用。

**理由**:使用者不想開兩個入口(Django admin + React)做日常作業。Django admin 雖然開箱即用,但 UX 不夠密集、不能像 Excel,且讓使用者面對兩種完全不同介面風格會混亂。

**對應設計約定**:
- 凡是 Django admin 上能做的事,React app 都必須做出對應 UI
- 包括但不限於:商品/類別/倉庫/供應商/客戶/序號 主檔 CRUD、進貨單與銷貨單錄入與過帳、序號狀態維護、單據作廢
- README 不引導使用者打開 `/admin/`
- Phase 5 SaaS 化時,平台跨租戶後台**也用 React 做**,不用 Django admin

**未採用**:用 Django admin 當 Tenant Admin 介面(欲蓋彌彰、體驗不一致)。

## 2026-05-17:UX 模式 — 三種頁面版型而非單一 Master-Detail

**選擇**：新系統 UI 分三種版型，按頁面用途套用：

| 版型 | 用途 | 對應舊系統 |
|------|------|-----------|
| **錄入頁 (Entry Page)** | 開單據（進貨/銷貨/調撥/維修），鍵盤為主，連續輸入 IMEI 與明細 | 後台 ACNI002 風格 |
| **Master-Detail** | 主檔維護（商品/客戶/供應商/類別），左列表 + 右詳情，鍵鼠混用 | 既有設計 |
| **報表頁 (Report Page)** | 查詢報表，上方篩選列 + 中央結果表 + 底部總計 + 匯出（CSV/Excel/PDF） | 前台 100+ 個編號報表 |

**理由**：原本只設計 Master-Detail 一種版型，無法覆蓋舊系統的兩個真實使用模式。錄入頁與報表頁的需求差異大（鍵盤友善 vs 篩選與匯出），不能用同一個元件硬套。

**對應設計約定**：
- 錄入頁必須支援 Tab 自動跳欄、Enter 提交、ESC 取消、條碼掃描連續輸入、F-key 快捷工具列
- 報表頁必須支援多重篩選、匯出（CSV / Excel）、保留舊系統的 MMxxx 編號（建立 command palette 用編號或關鍵字跳轉）
- 三種版型細節寫在 [ui-patterns.md](ui-patterns.md)

**未採用**：用 Master-Detail 通用元件硬套所有頁面（會讓錄入慢、報表查不到）。

## 2026-05-17：版型 — Master-Detail 雙欄

**選擇**：所有業務頁面採左欄列表 + 右欄詳情的雙欄版型，禁用卡片式瀏覽。

**理由**：使用者明確排斥卡片牆造成的滾動成本，要求單頁瀏覽完。3C 進銷存的列表單元多（型號、序號、單據），雙欄能在不滾動的情況下兼顧檢索與細部編輯。

**未採用**：卡片牆、單一大表格 inline 編輯。

## 2026-05-17：技術棧 — Django + DRF + PostgreSQL / React + Vite + TS

**選擇**：後端 Django 5 + DRF + PostgreSQL；前端 React 18 + Vite + TypeScript；monorepo `backend/` `frontend/`。

**理由**：Django 內建 admin/auth/migration 對「表單多、權限細、報表多」的進銷存生產力高；FastAPI 的 async 強項在這個場景用不到。前端用 React + Vite 是最不挑團隊的搭配。

**未採用**：Next.js（不需要 SSR）、Laravel（PHP 生態的工程習慣不在本專案目標）、FastAPI（admin 要從零做）。

## 2026-05-17：序號層級 — Product / ProductSerial 兩層

**選擇**：商品分 `Product`（SKU 型號）+ `ProductSerial`（單台序號）兩層；庫存以序號為單位。

**理由**：3C 業每台 IMEI/SN 都不同，必須逐台追蹤位置與狀態，才能支援保固、維修、調撥、防竄貨。

**未採用**：純 SKU 數量法（無法支援序號生命週期）。

## 2026-05-17：成本法 — 加權平均（同時保留逐台採購成本）

**選擇**：銷貨成本走加權平均；但每台 `ProductSerial.purchase_unit_cost` 仍記錄 landed cost 攤提後的真實採購成本。

**理由**：使用者明確選擇加權平均（帳務乾淨、業務員無法挑批號）；但保留逐台成本只是多一個欄位的事，未來想切換到「逐台實際成本」或做毛利分析，不用回頭補資料。

**未採用**：純 FIFO（與序號追蹤邏輯衝突）、純逐台實際成本（業務員可挑批號衝績效）。

## 2026-05-17：附加費用 — 按金額比例攤到進貨明細

**選擇**：進貨單的運費/關稅/保險等 `extra_cost_total`，按各明細 `qty * unit_price` 占總金額比例攤到每筆明細。

**理由**：landed cost 標準做法，貼合實際成本。按數量平攤會在貨價落差大時失真。

**未採用**：按數量平攤、不入成本（另記費用帳）。

## 2026-05-17：角色架構 — 三層角色，前端單一 SPA

**選擇**：定義三層角色 Platform Admin（系統提供者）/ Tenant Admin（經銷商老闆）/ Tenant User（店員）。Platform Admin 走 Django `/admin/`；Tenant Admin 與 Tenant User **共用同一個 React app**，靠登入角色決定能看到哪些導航項與按鈕，實際資料邊界由 DRF permission 把關。

**理由**：拆兩個前端 app 會代碼重複、部署複雜度倍增。同 app 切換角色是主流 SaaS 做法，安全邊界落在後端 API 才是正解，前端只是 UX 過濾。

**未採用**：拆兩個 React app（Shopify 風格）、把老闆功能也丟到 Django admin。

## 2026-05-17：多租戶 — 預留但 MVP 不啟用 UI

**選擇**：所有業務表自帶 `tenant_id`、queryset 統一經過 `for_tenant()`、middleware 在 MVP 階段把 `request.tenant` 寫死成 `DEFAULT_TENANT_ID=1`。

**理由**：未來轉 SaaS 不用回頭重寫；當前不暴露在 UI 上以免增加認知負擔。

**未採用**：等需要時再加（過去經驗：補 tenant_id 是高風險重構）。

## 2026-05-18:移除進貨「附加費用」+ 「過帳」改一步、改用課稅別

**選擇**:
- 進貨單 `extra_cost_total` 欄位移除,landed cost 攤提改用「課稅別 + 計價數量」實現
- 銷貨、進貨都加 `tax_method`(應稅內含/外加/免稅/零稅)
- `unit_landed_cost` = 未稅單價(含稅時 = unit_price / 1.05)

**理由**:多數通訊行不單列運費,習慣把附加費用直接攤在單價;改用稅別可以更貼近開發票時填的欄位。

**影響**:現有資料 extra_cost_total 已遺失(都是測試資料,可接受)。

## 2026-05-18:進貨明細加 billed_qty(計價數量),處理贈品

**選擇**:`PurchaseOrderItem` 新增 `billed_qty`,獨立於進貨數量(`qty`)。
- 金額 = `billed_qty × unit_price`
- 單台落地成本 = (未稅 billed_total) / qty → 贈品稀釋平均成本

**理由**:廠商常送贈品/試用品,進貨數量 > 計價數量。舊系統做法一致。

**未採用**:直接打折(無法精準對到原進價);零單價輸入(會破壞 weighted_avg_cost)。

## 2026-05-18:銷貨明細 1 對多序號(SalesOrderItemSerial 中介表)

**選擇**:銷貨明細 `qty` 可 > 1,序號改 M2M(透過 `SalesOrderItemSerial` 中介表),允許「同款手機賣 2 支」一行。

**理由**:同一商品多台是日常情境(賣兩支白機給家庭客)。原本一台一行 → 一行最多 1 序號太僵硬。

**未採用**:單一 FK + 限制 qty=1(逼使用者開多行)。

## 2026-05-18:儲存即生效 + 作廢機制(取代兩步式「過帳」)

**選擇**:
- 進貨、銷貨單 POST 成功就 commit(寫序號、寫加權平均、寫異動)
- 不要可改可刪,要取消用「作廢」action `is_void=True`
- 作廢有規則:進貨作廢需所有序號仍在 in_stock;銷貨作廢把序號退回 in_stock

**理由**:舊系統「未過帳/已過帳」兩段式造成大量誤操作。一步式 + 作廢更直觀,責任歸屬也清楚。

**未採用**:可編輯模式(難以維持加權平均一致性)。

## 2026-05-18:商品搜尋 — pg_trgm + 自製 TrigramSearchFilter

**選擇**:升級到 PostgreSQL,啟用 pg_trgm 擴充,寫一個自製 SearchFilter:
1. 先試 `icontains`(子字串)
2. 沒結果且 query ≥ 3 字 → fallback 用 `TrigramWordSimilarity`,門檻 0.35
3. 取代 DRF 內建 SearchFilter,全域生效

**理由**:萬筆級別商品要支援打錯字也能找到(「iphne」找到「iPhone 15 Pro」)。icontains 是常態路徑、trgm 是補救路徑,避免短關鍵字誤判。

**未採用**:純 ILIKE(打錯字找不到)、Elasticsearch(殺雞用牛刀)。

## 2026-05-18:前端下拉一律 server-side ComboBox

**選擇**:所有資源選單(商品、客戶、供應商、序號、方案、SIM 卡、業務員、單別)都用 `ComboBox` 元件 + `api/search.ts` 裡的 `searchXxx`。不再一次抓全表用 `<select>`。

**理由**:萬筆規模 `<select>` 不可用。打字 debounce 200ms 拉 ≤ 20 筆。`payload` 帶完整物件避免後續再 round-trip。

## 2026-05-18:銷貨單發票自動取號(InvoiceTrack 字軌)

**選擇**:在「系統設定」維護發票字軌(AB 12345678–887);銷貨單建單時依 `invoice_form` 從字軌 `SELECT FOR UPDATE` 原子地取下一張號碼,使用者不需手動輸入。

**理由**:法定要求發票號碼連續、避免重號;手動輸入容易出錯且無原子保證。

**未採用**:接 e-invoice 平台(複雜度過高,Phase 3 再說)。

## 2026-05-18:付款方式主檔 + N 筆付款拆分

**選擇**:銷貨單支援 N 筆 `SalesOrderPayment`,`sum(amount) == total` 才能存。付款方式從 `PaymentMethod` 主檔(`tenants.PaymentMethod`)讀,使用者可自由新增(LinePay / 街口 / 全支付 / 匯款 / Apple Pay)。

**分類三類**:
- `cash`:現金 — 影響當日營業現金
- `transfer`:匯款 — 不影響當日現金
- `non_cash`:非現金(信用卡、行動支付)— 不影響當日現金

**理由**:通訊行付款通路多元、且需要區分「真現金」做日報。

**未採用**:固定 enum(無法擴充)、單一付款欄位(無法部分現金部分刷卡)。

## 2026-05-18:結帳成功後不關 modal,改顯示成功狀態 + 列印按鈕

**選擇**:確認結帳 → 後端寫單 → modal 切換為「結帳完成」狀態,顯示單號 / 發票號 / 付款明細 + 「列印收據」「列印發票」「完成」按鈕。完成才關閉 + 跳列表。

**理由**:舊流程「儲存 → 跳列表 → 再點進去列印」太多步;一氣呵成更貼合 POS 操作節奏。

## 2026-05-18:新單草稿持久化 sessionStorage

**選擇**:`/sales/new` 與 `/purchases/new` 自動 debounce 寫 sessionStorage,切到其他分頁回來不會丟資料,儲存成功自動清空,工具列有「清空草稿」鈕。

**理由**:使用者抱怨切分頁會掉資料。sessionStorage 範圍剛好(關掉瀏覽器才丟)。

**未採用**:多分頁同時開新單(像 IDE tab,工程量大,後續可再做)。

## 2026-05-18:自動產生內部 code,UI 隱藏

**選擇**:
- 商品 SKU、電信方案 code、PO/SO no、InvoiceType code、PaymentMethod code 全部系統產生
- 前端**不顯示也不輸入**(僅商品 SKU 顯示在 ComboBox 副資訊與標籤列印)
- PaymentMethod 沒填 code → 後端自動產生 `pm_xxxxxx`(6 字元 hex)

**理由**:使用者只認名稱,不該被迫想代碼。

## 2026-10-02:商品叫法比對 — 從品名拆特徵,各入口共用一支

**選擇**:`apps/identity/product_match.py`。查詢字串與商品品名走同一支 `parse_features()`,拆成三種特徵再比:英數型號(`RENO16`,必須完全相同)、顏色(藍 = 藍色;深藍 / 丁香紫是另一個顏色)、其餘的詞(款式 / 類別 / 品牌 / 規格)。比對結果分 `exact` / `covers`(輸入的都符合,商品另有別的特徵)/ `related`(同機型但有差異)。進貨搜尋、一般 `?search=`、待確認入庫、新增前查重都用它,同一句話在哪個入口問都拿到同一批候選。

**理由**:實測 2,922 筆配件的 `color` / `phone_model` / `style_code` 全是空的,比結構化欄位等於什麼都比不到;舊的逐詞 AND `icontains` 換個寫法就 0 筆(`reno-16`、`側翻藍` 連寫、詞序不同),店員看到找不到就重建品號。同一支函式拆兩邊,拆錯也對稱。

**紀律**:特徵比對只產候選與原因,不替人決定。能直接認定「就是這個」的只有條碼、廠商料號、已確認別名、品號。

**未採用**:靠結構化欄位比(資料是空的);大型模型判斷(`suggest_accessory_models` 實測高信心也會錯);每個入口各寫一套(結果不一致)。

## 2026-10-02:別名分「已確認」與「關鍵字」

**選擇**:`ProductAlias.verified=True` 才有自動對應資格,而且同一作用範圍只能有一筆(含通用別名的條件唯一約束 `uniq_alias_generic`);`verified=False` 是搜尋關鍵字,同一句話可掛多個商品。太籠統(只寫機型 / 類別 / 顏色)、只是品名的一部分、或同時符合多款的叫法,學的時候自動降為關鍵字。已確認的叫法每次命中都重看一次:現在還有別款也符合就退回候選。改指與停用別名限公司管理員。

**理由**:「reno16 藍」在只有側翻款時記成唯一別名,之後進了掀蓋款,同一句話會被舊別名直接帶到側翻款,掀蓋款反而找不到。原本 `supplier` 為 NULL 的通用別名在 PostgreSQL 下唯一鍵擋不住(NULL 彼此不相等)。

## 2026-10-02:停用商品不因選用而恢復

**選擇**:搜尋與候選會列出停用商品(標「已停用」),但選用不會把它啟用。恢復要管理員明確操作(`POST /products/{id}/restore/`、待確認入庫帶 `restore=true`、或編輯商品),一般店員回 403。

**推翻**:先前「人挑了停售商品 = 明確表示要再進貨 → 直接恢復」的做法。

## 2026-10-02:新增商品要過防重複關卡

**選擇**:`apps/identity/dedup.py` 的 `guard_new_product()`,單筆 / 批次 / 型號展開 / 手機型號精靈 / 匯入 / 待確認區建新品 / 直接打 API 都過同一道。條碼相同、或品名整句是別的商品已確認的叫法 → 硬擋(409 `kind=identifier`)。特徵看起來同一款(兩個方向都看)→ 要寫下哪裡不同才能建(409 `kind=similar`,帶 `distinct_reason` 重送),理由存 `ProductDistinctDecision`。批次每列各自說明;匯入不替人決定,列進略過清單。

**理由**:只做在畫面上的話,換個入口或直接打 API 就繞過去了。名稱相似不等於同一個實物(不同材質 / 品牌 / 包裝),所以不強制合併,但不能只按一個沒有理由的忽略鈕。

**未做**:改既有商品品名(PATCH)不過關卡;商品條碼沒有資料庫唯一約束(用 advisory lock 序列化建檔);管理指令與系統自建虛擬商品不過關卡。

## 2026-10-02:公司備份 — 自訂的公司範圍可攜封裝,不用 pg_dump

**選擇**:`apps/backup/`。一次備份 = 一家公司(tenant)全部門市的資料 + 附件,匯出成 zip(每張表一個 jsonl + manifest + 附件),再用加密外殼包起來(`.mppos-backup`)。匯出在一個 `REPEATABLE READ` 唯讀交易裡完成。哪些表要進備份由 `registry.py` **逐張登記**,沒登記的表存在時備份拒絕執行。

**理由**:多家公司共用一個資料庫,`pg_dump` 是整庫工具,切不出單一公司;把整庫產物交給單一店家會把別家資料一起給出去。只掃「有 tenant 欄位的表」會在新增表時靜默漏掉,漏備份要到還原那天才發現。

**未採用**:`pg_dump` + 表名篩選(做不到列層級隔離);每家公司一個資料庫(要重建整套隔離,超出 MVP);讓使用者上傳 SQL 直接執行(不可能安全)。

## 2026-10-02:備份加密與復原憑證

**選擇**:每家公司一組伺服器產生的復原憑證(160 bits,寫成 `MP-XXXX-…`),管理員抄下來跟硬碟分開保管;伺服器存的是用 `SECRET_KEY` 包過的密文,平常備份不用每次輸入。檔案用 HKDF-SHA256 導出金鑰、AES-256-GCM 分塊加密(STREAM 做法),都出自 `cryptography` 套件。

**理由**:備份含會員與維修資料,硬碟遺失不能等於資料外洩;原伺服器壞掉時備份仍要打得開,所以憑證不能只存在伺服器上。伺服器留一份(包過的)是為了讓「按一下就備份」與日後的無人值守備份可行。

**取捨**:伺服器資料庫外洩時憑證也會外洩 —— 但那時資料本身已經外洩了;憑證要防的是「硬碟離開店家之後」。換掉 `SECRET_KEY` 後伺服器讀不出憑證,要管理員重新輸入。

## 2026-10-02:還原 — 整家公司、照搬帳本、新主鍵、號碼只往前

**選擇**:還原單位是整家公司。流程:上傳 → 預檢(不改資料)→ 輸入「還原」確認(**確認當下就上維護鎖**)→ 等寬限時間 → 還原前安全備份 → 在**一個交易**裡:鎖住公司那一列、再比一次資料指紋、刪掉該公司資料、照備份寫回(每列給新主鍵、外鍵照對照表換)→ 逐列核對 → 解鎖 → 提交。工作標成「已完成」、解鎖與資料取代在同一個交易,所以不會有半套,也不會留下解不開的鎖。

- **不重播交易**:庫存餘額、異動、付款、成本快照原樣寫回,不呼叫進貨 / 銷貨的過帳程式。
- **不採信檔案裡的數字 id 與公司 id**:寫到哪家公司由「誰在還原」決定。
- **只能往前的號碼**(客戶 / 會員 / 品號流水、發票字軌、單號)取現況與備份較大者;單號另外用 `DocNumberFloor` 記下已用過的最大號(`apps/core/numbering.py`)。
- **帳號不還原**:沿用現有帳號與密碼;單據的經手帳號用 `UserProfile.account_uuid` 對回「現在還在這家公司的同一個人」,對不回來留空。不用帳號名稱(會改、會被別人拿去用)也不用數字 id(換伺服器就不同)。帳號綁的門市用門市代碼對回新的那一筆,對不回來就留空且維持鎖定。
- **版本要完全相同**(比對每個 app 全部已套用的 migration)才還原,不猜跨版本欄位。
- **寫入屏障分三層**:(1) 維護鎖擋所有經過網頁的請求 —— 一般 API 在登入驗證擋、平台後台照實際要改的那一筆擋、Django 管理後台在任何公司還原時只能看;(2) 上鎖後等滿寬限時間(比網頁伺服器的請求逾時長),上鎖前放行的請求不是做完就是被砍掉;(3) 取代資料的交易對公司那一列下 `FOR UPDATE`,每一筆公司資料新增時資料庫都會對那一列上共享鎖,所以任何來源的新增都要等還原提交。不經過網頁、只修改既有列的管理指令不在這三層內,列為操作限制。
- **「還原有沒有在跑」看鎖不看時間**:worker 執行時握著 PostgreSQL 的 session 層級 advisory lock,行程一死就放掉。只用時間租約的話,跑得久的還原會被誤判成中斷、管理員可能在它還在跑的時候解除維護。

**理由**:共用資料庫下主鍵序列是各公司共用的,不能把備份裡的舊 id 寫回去;單店回溯會讓跨店共用的商品 / 成本 / 調撥失去一致。

**未做**:跨版本還原;單一門市回溯;跨公司合併;固定設備自動備份。


## 2026-10-04:舊系統資料 — 原文不改、對照另一層、只供查詢

**選擇**:`apps/legacy/`。舊 POS(歐睿)十年會員消費封存照原文匯入(會員 / 快照 / 單據 / 版本 /
明細 / 待核),另建「舊店名 / 舊品號 / 舊業務員 / 舊會員 → MP 門市 / 商品 / 業務員 / 會員」的對照表,
由人確認。明細透過不佔欄位的 ForeignObject(公司 + 來源系統 + 原文代號)串到對照,查詢時才連起來。

**理由**:
- 十年資料要能跟新系統一起出報表(門市、品類、業務員、會員),但舊代號跟 MP 的編碼邏輯完全不同,

- 品號對照是庫存搬家與十年報表共用的地基,做一次兩邊用。
- 「電話相同就自動歸戶」會把舊單掛錯人;一律只出候選、人確認、留紀錄。
- 匯入是查詢用資料,不能觸發任何營運副作用;來源金額有差異的另存待核,不混進已核對合計。

**未採用**:擴充既有 `LegacyPurchase`(必須關聯現有商品、數量只收正整數、金額用數量 × 單價重算,

## 2026-10-04:帳本補強 — 每行存未稅 / 稅額、銷退存沖回成本、每日庫存快照與對帳

**選擇**:
- 銷貨 / 銷退明細在存檔當下存死 `untaxed_amount` / `tax_amount`(零頭補在金額最大那一行,
  整單加總正好等於單頭);銷退明細另存 `cost_at_post`(沖回成本:序號 = 退回那幾台的進貨成本,
  配件 = 原行成本按數量比例,最後一次退用餘數,分幾次退完加總等於原行成本)。既有資料用 migration 回填。
- `apps/ledger/`:每天收店後(預設 23:30,`LEDGER_DAILY_AT`)由已常駐的備份背景程式順便拍
  「每日庫存快照」再跑「每日對帳」,結果存表,管理員在「設定 → 每日對帳」看。

**理由**:
- 毛利原本是報表畫面拿金額除以 1.05 回推;稅別規則一改,舊報表數字就變,而且不同畫面可能算法不同。
  存死之後「未稅金額」只有一個答案,之後的語意層 / 自然語言查詢都從這裡取。
- 銷退原本不記成本,毛利報表沒辦法扣回退貨的成本。
- 過去某一天的庫存金額事後倒推不準(成本會被之後的進貨改掉),只能每天記。漏拍的那天不補,只提醒。
- 不新增常駐程式:沿用已在 mini 上常駐的備份背景程式,部署後就會自動開始。

- 既有銷退的沖回成本:舊資料當初沒算過、也沒有作廢時間,不假裝重播當時的存檔;改用固定規則回填
  (目前有效的銷退把一行全部退完時加總 = 原行成本,作廢的只按比例)。
- 每天「拍過了沒」記在 `StockSnapshotDay`(零庫存也有一列);對帳若早於當天的還原就重做;
  同一家公司的快照 / 對帳用 advisory lock 一次只做一個。

**未採用**:另開一支排程(要再設一個常駐項目);快照漏拍時用異動倒推補拍(成本不準,寧可留空);
對帳發現不一致時自動修正(對帳只負責講出來,修正要人決定)。

## 2026-10-04:銷退只能整張退

**選擇**:一張銷退 = 原銷貨單整張退回(每一行、全部數量、每一台)。明細由系統照原單帶入,
畫面不再勾選要退哪幾行。退款 = 原單實收總額。一張銷貨單同時只能有一張有效的銷退。

**理由**:
- 原本可以只退一部分,退款用「數量 × 單價」重算;原行有打折時會退得比實收多。整張退之後,
  退款一定等於當初收的錢,沒有分攤問題。
- 店頭實際作法:要換貨就整張退掉再重開一張。規則單純,帳也單純(毛利、成本一進一出完全對沖)。
- 部分退的分攤(金額、稅額、成本的零頭)全部不需要了。

**未採用**:保留部分退、退款改按實收比例分攤(規則複雜,零頭要再處理一次)。
舊資料裡已經存在的部分退貨不動。

## 2026-10-04:跨公司防護做成共用規則

**選擇**:所有給公司用的序列化器一律掛 `TenantScopedRelatedFieldsMixin`(外鍵欄位只認
`request.tenant`);有門市鎖的建單一律呼叫 `check_create_warehouse()`;兩者各有一支測試掃全系統,
新功能漏掉會紅。過帳邏輯(銷貨、銷退、進貨、調撥、維修完工)再用 `same_company()` 核對一次。

**理由**:DRF 的外鍵欄位預設接受整張表的編號;多家公司共用資料庫時,猜到別家的編號就能把別家的
門市 / 商品 / 序號掛進自己的單,甚至改到別家的庫存。逐支補會漏,所以做成「預設安全 + 測試把關」。

另外三條「不靠送編號也看得到別家」的路一起關掉:
- API 只回 JSON:DRF 內建的 API 瀏覽頁會把篩選與表單的下拉選單整張表列出來(所有公司的客戶、
  供應商、序號)。唯一的畫面是前端,瀏覽頁不需要。
- 外鍵篩選的來源限縮到自己公司(別家編號與不存在的編號同樣回 400,不能拿來試探)。
- 沒綁公司的帳號:只有平台管理員與 superuser 可以指定要看哪一家;其他一律在登入驗證擋下
  (原本任何沒綁公司的帳號都能用 `?tenant=` 切到任何一家,或落到預設公司)。

**未採用**:只在 service 層檢查(欄位仍會接受別家編號,錯誤訊息晚、也容易漏掉沒有 service 的簡單單據)。

## 2026-10-04:改庫存一律「先鎖再檢查、再改」

**選擇**:`apps/inventory/locking.py` 定一套共用規則,銷貨、銷退、進貨、調撥、維修全部照做:
先鎖單據自己那一列並重讀 → 照固定順序鎖這張單會動到的商品 / 序號 / SIM 卡 / 庫存餘額 → 鎖完才檢查、才改。
全部在同一個交易內。

**理由**:庫存數量、序號狀態、單據狀態都是「讀出來 → 判斷 → 存回去」。兩個人同一瞬間動到同一個東西時,
不先鎖就會各自讀到同一個舊值:同一支 IMEI 被賣兩次、庫存少算一次、同一張調撥被確認兩次(庫存加兩次)、
同一張進貨被作廢兩次。平常店裡不容易同時按,但一旦發生,帳就永遠錯下去,只能靠每日對帳事後發現。
- 上鎖順序固定(單據 → 商品 → 序號 → 卡 → 餘額,各照編號):明細順序相反的兩張單才不會互相等到死結。
- 商品 / 序號 / 卡用不擋外鍵的鎖:別張單只是新增一列指到它時不用等。

維修完工原本沒有包在交易裡,缺料時庫存只扣到 0、異動卻記全部數量(重開又加回全部,等於憑空多出庫存)。
改成:領用照實記全部,帳上不夠的差額另記一筆盤點調整入庫 —— 行為不變(缺料仍可完工),但帳對得起來、看得到。

維修單另外補上入口限制(原本一般的修改就能把狀態改成「已完成」而不扣料、完工後還能改門市與零件、
作廢與完工互不相干):狀態唯讀,只有完工 / 重開會動庫存;已完工或已作廢的單不能改;重開依異動紀錄
歸還實際領出去的零件。規則跟畫面原本的行為一致(已完工的單畫面本來就鎖住,只有管理員能重開)。

**未採用**:用資料庫的原子加減(`F("qty") + n`)取代上鎖(加權平均成本要先讀再算,而且「夠不夠扣」的檢查
仍然需要鎖);缺料時直接擋下不給完工(會改變現場流程,帳上數量常常落後現場)。

## 2026-10-04:報表只有一套定義(指標 × 角度),不再一張報表寫一次

**選擇**:`apps/analytics/catalog.py` 是指標與角度的唯一定義;報表畫面(報表 → 自由組合)與之後的自然語言
都只能送「查詢單」(要哪些指標、怎麼分組、期間、條件、要不要比較),由 `engine.py` 照定義驗證、查詢、合併。
新的報表需求 = 在定義裡加一個指標或一個角度,不是寫新的報表頁或新的查詢。

**理由**:每張報表各寫各的查詢,同一個「毛利」在不同頁面會算出不同數字,而且每個新需求都要開發者動手。
把「怎麼算」收在一個地方之後,組合由使用者自己選;AI 也只能產生同一種查詢單,翻譯錯了會被驗證擋下,
不會產生錯的數字,也碰不到資料庫指令。

幾個寫死在定義裡的規則:
- 「銷售」類指標只算**計入毛利**的明細。收購二手那一類(只算現金、不算毛利)不是營收,另外一欄
  (不計毛利金額)看。這樣 銷售額 − 成本 = 毛利 是同一批明細,三個數字對得起來。
- 毛利有兩種:銷貨毛利(未扣銷退,對得上銷貨日報)與毛利(扣銷退)。銷退記在退的那一天。
- 庫存不能跨日加總:一段期間的庫存 = 期間內最後一次快照;按月看就是每個月最後一次。
  「最後一次是哪一天」看的是那天有沒有拍過快照(`StockSnapshotDay`),跟條件無關:數量是 0 的商品在快照裡
  沒有明細,如果用「篩完之後還有明細的最後一天」去找,賣到歸零的東西會一直報最後一次有貨的數量。
- 一個指標背後有好幾張事實表時(淨銷售額 = 銷貨 − 銷退),條件與分組要每一張都支援才能用;
  不支援就明講(例如「收款」不能按商品分),不默默給 0。
- 舊 POS 只用跟封存核對過的金額(原始額 / 淨額)。舊系統的「未稅額」欄位多數等於金額、少數是金額 ÷ 1.05,
  退貨類又自帶負號,語意不一致,不採用。門市 / 商品 / 業務員沒有人確認過對照的,歸「未對照」。
- 合計另外算,不是把列加起來:不受筆數上限影響,銷貨單數也不會因為按商品分而重複算。
- 代碼型的角度(付款方式、課稅別…)條件只接受列得出來的代碼;清單是空的就是全部不接受,不是不檢查。
  付款方式主檔可以刪,但收款 / 退款的單據上還留著當時的代碼,所以可選的代碼 = 現在的主檔 + 單據上用過的
  (主檔已刪的顯示「代碼(已刪除)」)。只看主檔的話,刪掉一個用過的付款方式,那些錢就篩不到、存好的報表也打不開。

存起來的報表,條件存的是那筆資料的**代碼**(門市代碼、品號…),不是資料編號:還原備份後每一列都換新編號,
照編號存會查錯對象而且看不出來。打開時換回現在的編號;代碼找不到(資料被刪、付款方式沒用過就刪掉)就把那個值拿掉並講出來,
不悄悄變成「全部」。內容形狀不對的(條件那一欄不是物件、值是空清單)整份標成壞掉,不當成「沒有條件」。

**權限**:目前不鎖(2026-10-04 決定):店員也看得到全公司與毛利。每個指標的定義留了「誰看得到」,
之後要鎖填那一欄,不用改報表。
存起來的報表預設只有自己看得到,管理員也看不到別人私下存的;要全公司共用由管理員自己存一份並勾共用。
共用的報表能不能改,看的是**現在**是不是管理員,不是看當初是誰存的。

**進貨金額**用的是記進庫存的成本(未稅單位成本 × 數量),跟庫存金額、加權平均成本同一個數字。
單位成本存到分,有贈品或除不盡時,跟進貨單頭的未稅小計可能差幾分錢。之後要完全一致,
進貨明細要像銷貨一樣把每行未稅金額存死(後續追蹤)。

**未採用**:讓 AI 直接寫資料庫查詢(數字沒有唯一定義、會讀到別家公司或個資、錯了看不出來);
買現成的 BI 工具接資料庫(同樣沒有唯一定義,權限與公司隔離要另外再做一次)。

## 2026-10-04:一台設備兩個碼(IMEI / SN),刷哪一個都是同一台

**背景**:手機有 IMEI,有些店家(與沒有 IMEI 的平板 / 手錶 / 耳機)記的是 SN。原本每台只有一個 `serial_no`,
入庫時只能擇一,之後拿另一個碼刷不到。

**選擇**:
- 每台可以登記 IMEI、SN 兩個碼:可以都有,也可以只有一個。`serial_no` 留著當**主碼**(有 IMEI 用 IMEI,沒有才用 SN),
  標籤、單據、所有既有程式照舊讀它,不用跟著改。
- 兩個碼各存一列在既有的 `ProductSerialIdentifier`(原本只有拍照入庫在用)。**同一家公司裡一個碼只屬於一台**,
  IMEI 與 SN 一起比(一台的 SN 不能等於另一台的 IMEI),比對前去掉空白 / 破折號 / 點、轉大寫。
  資料庫的唯一限制在識別碼表上,所以「每一台都有登記」是前提:新增設備只有 `create_serial()` 一個入口
  (測試掃全專案),既有設備由 migration 補登記,漏掉的由每日對帳講出來。
- 沒講是哪一種的單一個碼(舊格式、匯入、拍照入庫的主序號):15 碼數字且檢查碼(Luhn)正確的當 IMEI,其餘當 SN。
  畫面上明講放哪一格的就照放;IMEI 檢查碼不對**只提醒、不擋**(有些設備的碼本來就不合規)。
- 進貨頁每台兩格,刷條碼自動分格(`frontend/src/lib/deviceCodes.ts` 的 `routeCodes`,有測試)。
  手機盒上通常有 IMEI、IMEI2、SN 三個條碼,IMEI2 也是檢查碼正確的 15 碼,**光看碼分不出「下一台的 IMEI」
  還是「同一台的 IMEI2」**。原本想做成不用設定(每個碼放到往下第一個空格),紅隊指出同一支手機連刷
  IMEI、IMEI2、SN 會被拆成兩筆庫存而且存得進去。所以改成序號側欄一個開關「每台刷 IMEI 與 SN」(記在瀏覽器):
  關 = 一個碼就是一台;開 = 先把這一台補齊,這一台已有 IMEI、還缺 SN 時再刷到 IMEI 就不放並提示。
  刷在種類不對的那一格會還原原本的內容;游標當下就移到下一個空格;條碼槍結尾送 Enter 或 Tab 都一樣。
- 銷貨掃碼只在「碼完全相同、整家公司剛好一台、在庫、在這個出貨倉」時自動掛那一台。對到兩台以上
  (舊資料去掉符號後撞在一起)擋下來;那一台已賣出或在別的門市就講出它在哪,不加一行空的讓人挑同款別台。
  下拉用的「包含」比對不拿來自動掛:同商品另一台的碼剛好包含這串字時會賣錯實機。
- 用碼找設備:序號搜尋(挑序號的下拉、庫存查詢)比對每一個碼,可以打末幾碼;商品搜尋只收**完全相同**的碼
  (避免「18 pro 256」誤中含 18 的 IMEI 那一類問題),刷到的那一台的商品排最前面。
- 事後補登 / 修改:空的那一格誰都可以補;已經登記的碼只有管理員能改;作廢的設備不能改;
  鎖在自己門市的帳號只能動自己門市的。每次改動留一筆 `ProductSerialCodeChange`(誰、何時、從什麼改成什麼)。
  改碼等於改這一台「是哪一台」,沒有紀錄的話換機查不出來。

**未採用**:
- 在 `ProductSerial` 上加 `imei` / `sn` 兩欄:要在兩個欄位之間互相擋重複,資料庫做不到一個唯一限制管兩欄;
  而且識別碼表已經存在(拍照入庫用),兩套並存會對不起來。
- 把 `serial_no` 改成正規化後的值:既有資料、單據快照、測試都用原文,改了會對不起來;正規化只用在比對。

**不做**(owner 2026-10-04 決定):雙卡機第二組 IMEI 的一般入庫。一台就記 IMEI 與 SN 兩個碼;開著「每台刷 IMEI 與 SN」時刷到 IMEI2 會擋下不放。
(識別碼表有 IMEI2 的位置,拍照入庫原本就會存,那部分照舊。)

**還沒做**:調撥 / 銷貨單據上同時印兩個碼。

**作廢的設備不佔碼**(owner 2026-10-04 決定):進貨單打錯整張作廢重開是常見情境,以前 `serial_no` 在公司內唯一、
不看狀態,作廢過的碼永遠不能再入庫。現在作廢進貨單時把那幾台登記的碼釋放(`release_codes()`),`serial_no` 的唯一限制改成
不算作廢的(migration 0014,既有作廢設備的登記一併拿掉)。作廢的那一筆留著 `serial_no` 當紀錄:用關鍵字查序號清單還看得到(狀態是作廢),
但用碼找設備(刷條碼)不會找到它,所以重新入庫之後刷同一個碼只會對到現在那一台。

**主碼多存一份去掉符號後的值(`ProductSerial.serial_key`)**:主碼 `serial_no` 存原文,以前比對主碼只能拿輸入的幾種寫法
(原文 / 大小寫 / 去符號)去碰,舊設備當初寫成 `AB--12` 這種就比不到 —— 這個洞在複審被不同模型以不同樣子指出好幾次
(擋不住重複、刷條碼只找到其中一台、釋放作廢的碼時連在用那一台的保護一起拿掉)。改成每台存 `serial_key`(存檔時自動算),
找設備與檢查重複都比這一欄,不再猜寫法。沒有在這一欄上加唯一限制:舊資料可能有兩台在用的設備碼相同,加了升級會失敗;
這種資料用碼找會兩台都回來(畫面不自動挑),每日對帳會列出來。

**釋放時的接手**:釋放的碼如果還有一台在用的設備(主碼去掉符號後相同)沒登記到,碼改登記給最舊的那一台。
作廢一開始就把「這張單的設備」和「可能接手的設備」(`twin_ids()`)交給 `lock_stock_rows` 照編號順序一次鎖住,
在改任何設備之前(兩張作廢單的設備互為對方的接手者時才不會互相等到死結);鎖住之後才看現況:
碼還登記在別台身上就不交接,沒有人登記才交給最舊的那一台。

**複審**(作廢釋放 + `serial_key`):紅隊 1 輪(Grok)+ Codex 3 輪,第三輪結論「可以上線」(無 P0 / P1)。
後續追蹤(不急):`release_codes()` 的前提(同一家公司、都已作廢、呼叫端已鎖)只寫在說明裡,函式本身沒有檢查,
現在唯一的呼叫點符合;migration 0014 一次把全部識別碼讀進記憶體、一次寫入,資料量大的環境要改成分批。

**複審**(雙序號 + 整張調撥一起審):紅隊兩輪(deepseek、Grok)+ Codex 三輪。第三輪沒有 P0,但還有 3 項 P1,結論仍是「不可上線」。
其中兩項已修(掃到某一台之後只能加那一台、商品不能賣就講;畫面上是哪一個碼的順序固定 + 拍照入庫同一台同一種碼只能一個),
**這兩項修正沒有再送審**。第三項(批次貼上沒貼序號也要擋)沒有照改:批次貼上可以只帶商品與數量、序號回主畫面再刷,
沒刷齊存檔時本來就會擋。
owner 要求加審第四輪:第三輪五項全部確認處理好,沒有 P0;新提 1 項 P1(以前拍照入庫、SN 被標成主碼的設備,升級後主碼沒換成 IMEI)
→ 加 migration `0013_main_code_prefers_imei`(正式機沒有這種資料,會是空跑;隔離測試庫跑過,46 台沒有變動)。**這支 migration 沒有再送審**。

**後續追蹤(不急)**:
- 前端的分格測試(`npm test`)要 Node 22.6 以上才跑得起來;Mac mini 是 Node 20,只影響跑測試,不影響建置與部署。
- 銷貨下拉手打「只對到一部分」的自動掛,只看查回來的前 10 筆;選項上會寫出那一台的碼,由人挑。
- 整張調撥帶好之後可以把配件數量改得比這張進貨單多(照一般調撥檢查庫存),不會再提醒多的是別批的貨。

## 2026-10-04:整張進貨單一次調撥到分店

**背景**:總部進貨後要把整批貨調到分店,原本要在調撥單逐筆挑商品、逐台挑序號。

**選擇**:進貨單頁「整張調撥」→ 開一張已經帶好內容的調撥單,選目的倉就能派發。之後完全照既有調撥
(派發 → 目的倉確認 → 可作廢),沒有新的庫存異動路徑。
- 帶出來的內容由 `GET /purchase-orders/{id}/transferable/` 算(只讀):序號商品只列這張單進來、現在還在進貨門市且在庫的;
  已賣 / 已調走 / 已退 / 作廢的不帶,並在畫面上講出來是哪幾台。配件不分批,數量 = 這張單進的數量但不超過進貨門市現有庫存。
- 它只是「建議的內容」。帶出來到按下派發之間東西可能被賣掉,真正能不能調由調撥存檔時鎖住庫存再檢查(既有規則)。

**未採用**:按一下就直接建立調撥單(不經過調撥單頁)。少一個畫面,但使用者看不到哪些被略過,也不能先拿掉某一行;
而且會多一條建立調撥單的路徑,要另外維護一次權限與鎖。

## 2026-10-05:工作台版型 — 調撥、庫存查詢改成「一個畫面、掃一下加一行」

**背景**:owner 在舊系統上自己做的瀏覽器套件(Ored 快速工作台)用了一段時間,明講比較習慣那個介面。
跟原本錄入頁的差別:原本是「清單頁 → 按新增 → 另一頁 → 按新增明細 → 在那一行裡找商品 → 序號到右邊側欄逐格挑」;
套件是「一進來就是空白單、游標在掃碼框、掃一下加一行(新的在最上面)、序號列成小標籤直接點」。

**選擇**:加第四種版型「工作台」,先用在調撥與庫存查詢;進貨、銷貨之後照同一套改。**只換畫面,後端規則一行都沒動。**
- 共用零件在 `frontend/src/components/workbench/`:`ScanBox`(掃碼框)、`toast`(畫面下方的訊息條,可帶「復原」)、
  `ArmButton`(兩段式按鈕)、`errors`;樣式全部收在 `styles.css` 的 `.wb` 底下,不影響其他頁,日 / 夜間模式各一組顏色。
- **不開彈出視窗**:要確認的動作(入庫、作廢)第一次按只換字成「再按一次」,4 秒內再按才真的做;
  移除一行、清空明細不問,改成訊息條上給「復原」。清空之後又掃了新的,復原就不動(不拿舊的蓋掉新的)。
- 掃碼框一格同時收條碼與手打品名。條碼槍打得比搜尋快:按下 Enter 當下輸入框就清空,刷進來的碼排隊一個一個處理,不會漏也不會黏在一起。
  **只有「品號 / 條碼完全相同剛好一筆」才自動加入**;其他的把字放回去、列出來給人挑,不替人猜
  (人看著下拉按 Enter 才是取反白那一筆)。套件原本是一律取第一筆,這裡刻意比較保守:相似度搜尋的第一筆不一定是刷的那個。
- 調撥:刷到設備的碼 → 走 `findDevicesByCode`(完全相同才算);對到兩台以上擋下,不在調出分店 / 不是在庫就講它在哪。
  序號商品把調出分店在庫的每一台列成小標籤(後 6 碼),只有一台就直接選起來。清單、新增、待確認三個畫面併成一頁:
  下面的「最近調撥」點一列展開明細,待入庫的直接在列上按入庫。`/transfers/編號` 會展開那一張。
- 調撥的「直接入庫」(只有不鎖倉的帳號看得到,預設不勾,勾了會記住)= 送出後接著按一次入庫,是原本兩個動作連著做,沒有新的規則。
- 庫存查詢:點一列就地展開每家分店在庫的每一台(原本是點數字跳視窗);點分店、點類別直接重查;常用類別可以釘起來(記在瀏覽器)。

## 2026-10-06:金額一律整數元、四捨五入(顯示、輸入、存檔都是)

**背景**:owner 在維修單看到費用帶兩位小數(1500.00),要求全站金額都是整數、四捨五入。清查後發現不只是顯示:

- 後端的小計 / 稅額 / 總額算到分,而且 `Decimal.quantize` 預設是「四捨六入五成雙」(4.5 → 4),不是四捨五入。
  **應稅外加時總額會出現 115.50**,畫面只收整數,付款 116 對不上、這張單存不進去(小計不是 20 的倍數就會中)。
- 營業日報的加總用 `int()`,是無條件捨去。
- 順帶發現:維修單編輯頁改任何一格都會立刻被存檔的內容蓋回去(載入用的 effect 依賴了每次都是新物件的 `defaultWh`),既有的單在這一頁根本改不了。

**選擇**:
- 規則各一份:後端 `apps/core/money.py`(`round_money` 整數元、`ROUND_HALF_UP`;`money_int` 給報表加總;`money_text` 給訊息),
  前端 `frontend/src/lib/money.ts`(`roundInt` / `money` / `intStr` / `splitTax`)。前端先收到小數六位再進位,
  擋掉 1.255 × 100 = 125.49999999999999 這種差一點點的一半。
- **單據金額存檔就是整數**:明細金額、未稅小計、稅額、含稅總額(銷貨 `_calc_tax`、進貨 `_calc_doc_tax`、每行的未稅 / 稅額、個人收購金額、維修建議報價)。
  含稅:未稅 = 加總 ÷ 1.05 四捨五入、稅額 = 總額 − 未稅;外加:稅額 = 加總 × 5% 四捨五入、總額 = 未稅 + 稅額。跟發票上的算法一樣。
- **成本照舊算到分**(落地成本、加權平均成本、銷貨當下成本):那是平均值,收成整數會越算越偏;只在畫面上顯示成整數。
- **以前存的單不回頭改寫**。`_calc_tax(..., unit=CENTS)` 保留舊算法只用來「認得」舊單:每日對帳走 `matches_tax_rule()`(新舊符合一種就一致),
  `split_tax_by_line` 先看單頭是照哪一套算的、每行就照同一套分。migration 0016 的回填本來就帶一份凍結的舊算法,不受影響。
- 前端:所有金額顯示換成 `money()`(30 幾個檔);金額輸入框換成 `components/MoneyInput`(26 格:小數點打不進去、貼上帶小數的會四捨五入、
  資料庫的 "1500.00" 顯示成 1500、拿掉上下箭頭);表單載入與送出都過 `intStr()`;開單頁的試算改用 `splitTax()`,跟伺服器同一套算法;
  營業日報與自訂分析的 CSV 匯出也是整數。舊系統(歐睿)的金額存的是「分」、原文不改,只有顯示收成整數元。
- 維修單編輯頁的 effect 依賴改成編號 / 名稱,既有的單可以改了。

## 2026-10-06:商品照片(圖片備註)與手機掃 QR Code 拍照直傳

**背景**:同一個配件被不同人用不同名字重複建檔(淘寶 / 阿里巴巴來的貨沒有條碼,只能靠品名)。owner 給了規格
`MP-POS-商品圖片備註與手機拍照直傳規格.md`:建商品時附照片(電腦選檔,或手機掃 QR Code 現場拍),之後查詢、進貨、銷貨選品時
點品名看照片,確認是同一件就沿用既有品號。這一版做規格的 A / B / C 階段。

**決定**:

1. **照片先掛在「這一次編輯」上,商品存檔的同一個交易才掛到商品。** `PhotoDraft`(照片作業)+ `PhotoUpload`(暫存)→
   存檔時畫面把定下來的清單(`photos: {draft, items}`)跟商品欄位一起送,`apply_to_product()` 在同一個交易裡建 / 改 / 刪 `ProductPhoto`。
   理由:新增商品還沒有品號也要能先加照片;「取消」要真的不留痕跡(規格:不能介面說取消、照片卻已經永久改了);
   存檔失敗整筆退回、可以原樣重送(同一份作業重送回同一個商品,不建第二個品號)。
2. **手機那一端不登入,只認 QR Code 的憑證。** 憑證只能做一件事:對「這一份作業」傳照片 —— 看不到別的商品、金額,改不了品名。
   伺服器只存雜湊;放在網址 `#` 後面(不進伺服器紀錄);3 分鐘沒掃失效;綁第一支掃到的手機;閒置 10 分鐘 / 最長 60 分鐘結束。
   配對綁的是作業、不是商品也不是登入的人:電腦存完 / 取消 / 重新產生,舊手機就傳不進來,遲到的照片不會掛到下一筆商品。
   不要求手機登入整套 POS 是規格的要求(現場隨手拿一支手機拍)。
3. **每張照片有自己的識別**(畫面產生的 uid):同一張重試不會變兩張;取消過的留著「已取消」的紀錄,上傳晚到也不會復活。
4. **存檔前先停收**(`freeze`):電腦按儲存 → 作業不再收新照片 → 確認沒有還在路上的、沒有畫面上還沒看到的,才送商品;
   失敗就 `unfreeze`。這樣「提交期間不會偷偷多一張」。
5. **照片檔用帶簽章的網址**(`/api/v1/photo-file/<簽章>/`,7 天有效):`<img>` 帶不了登入的 Token。簽章只發給看得到那個商品的人。
6. **伺服器一律重新處理圖片**(Pillow:驗證真的是圖、轉正、去掉 EXIF、縮到長邊 2400、另存縮圖;HEIC 靠 `pillow-heif`)。
   瀏覽器上傳前先縮一次只是為了省流量,不當成可信的處理。
7. **看照片的入口不佔開單頁的版面**:明細的品名本身可以點、有照片的多一個 32px 小縮圖(不撐高列);搜尋下拉有照片的那一筆多一顆「照片 N」。
   下拉點品名仍然是「選用」(原本的手感不變),看照片是另一顆;看完「使用此商品」才加入、「返回繼續找」回到原本的搜尋。
8. **清理不另外排程**:有人開新的照片作業時順手清掉過期的作業與暫存檔(放 24 小時沒存、或結束 1 小時以上)。
   測試站沒有背景程式,這樣兩邊行為一樣。

**本機驗證時抓到、一起修的**:

- 手機問狀態的網址每次配對都一樣(憑證在標頭)。瀏覽器對 410 預設永久快取 → 那支手機看過一次「已結束」,之後每次新配對一問狀態就拿到舊的
  「已結束」。→ 照片端點全部 `never_cache`,手機端的請求再加 `cache: "no-store"`。
- 手機把一張照片移除,電腦那邊沒有跟著消失(存檔會帶到一張已經取消的)→ 跟著拿掉。
- 主圖標記會留在沒傳成功的那一張上 → 主圖永遠指著一張還在、傳好的照片。
- 新增商品「存成草稿先離開」再回來:上一次沒傳完 / 沒傳成功的那幾張又冒出來、而且卡住儲存 → 接回來時把它們取消。
- 編輯商品存檔的回應帶的是存檔前的照片張數與主圖 → 回應改用現查的。

**紅隊(Grok)抓到、一起修的**:

- 還原公司備份時,編輯到一半的照片作業(不備份、卻指到商品)沒有清 → 刪商品被外鍵擋住,**只要有任何一份照片作業在,還原就做不完**。
  → 還原時先清掉這家公司的照片作業與暫存檔(`registry.CLEARED_ON_RESTORE`);`check_registry()` 多一條:不備份的表指到公司資料就要登記在那裡。
- 新增商品時開的作業(沒綁商品)可以被拿去存到既有的商品上,那個商品原本的照片會被整批換掉 → 新增開的作業只能用在這一次新建的商品,編輯只收為這個商品開的。
- 表單關掉再開,上一次編輯還沒回來的請求(開作業、上傳、配對)會併進下一筆 → 每一次編輯有自己的編號,對不上的回應丟掉、晚到才開好的作業請伺服器取消。
- 商品原本的照片載入失敗時還能加照片,存下去原本的會被整批移除 → 沒載到就不能加、不能存照片,給「重試」。
- 只加了照片、欄位沒填就「存成草稿先離開」,回來沒有「載入草稿」可以按 → 有記著照片作業就出現(標「只有照片」)。
- 兩個分頁都接回同一份草稿:後存的那一頁被當成「重送」,拿到別人建的商品 → 品名不同就不算重送,擋下。
- 手機重新整理之後看不到剛才傳好的,會再傳一次 → 清單照伺服器講的補回來。無痕模式重新整理被當成另一支手機 → 識別退到分頁自己的儲存。
- 點明細品名之後游標留在品名上,條碼槍的 Enter 會再按一次品名、那一槍不會進單;從下拉看照片時游標還在掃碼框,刷進來會多加一行
  → 面板開著時背後停用、游標放在面板本身;品名不進 Tab 的順序;關掉之後游標回掃碼框。
- 手機拿得到憑證就能一直送「取消」灌資料列、可以取消或蓋掉電腦傳的那幾張 → 一份作業最多 80 筆;手機只能動手機自己傳的。
- 整份取消之後暫存檔要等清理才刪;存好之後沒放進清單的也是 → 當下就刪。資料沒存成但檔案已經寫到硬碟 → 一併刪掉。
- 純電腦上傳不會更新作業的「最後有動靜」時間,開著超過一天會被當成過期清掉 → 上傳時更新。失敗的照片佔名額 → 不佔。
- 大圖解碼吃記憶體 → 畫素上限降到 6400 萬(4800 萬 / 5000 萬畫素的手機原圖收得下)、JPEG 解碼時先縮、不另外複製整張原圖。

**Codex 複審第一輪抓到、一起修的**:

- 兩個人同時開同一個商品的表單,後存的那一張(舊的清單)會把前一個人剛加的照片當成「移除」刪掉 → 存檔帶 `seen`(開表單時看到哪幾張),
  跟商品現在的照片不一樣就整筆退回、請他重開表單。
- 沒傳成功的照片重試時狀態還是「失敗」,存檔不會等它;同一張另一次傳比較晚才失敗,會把已經傳好的蓋成失敗 → 重試回到「上傳中」;只有「上傳中」的能被標成失敗。
- 電腦重新產生 QR Code、換另一支手機連上之後,舊手機還在路上的請求照樣寫得進來、還能把新手機的配對結束掉 → 手機的每個動作鎖住作業之後再核對一次是不是同一次配對。
- 新增商品的草稿:欄位與照片分開記在兩個地方,兩個分頁會湊出「這一頁的欄位 + 那一頁的照片」→ 照片那一份放進表單草稿、同一筆一起存。
- 儲存中還按得到「還原」(畫面看起來還原了,送出去的清單卻已經定了)→ 儲存中照片區每一顆都鎖住,載入 / 捨棄草稿也是。
- 剛動過照片(改主圖、說明、移除)、照片作業還沒開好就按儲存,送出去的是「照片沒動」→ 存檔前等作業開好,開不成就不給存;上次的照片還在接回來時也先等。
- 手機把還在傳的那一張移除,晚到的回應被當成整次拍照結束 → 「這一張取消了」跟「這次配對結束了」分成兩種回應。
- 大張的透明 PNG / WebP 先鋪底再縮,吃記憶體 → 先縮再轉正、鋪底。照片編號收到 true 會被當成 1 → 只收真正的整數。

**Codex 複審第二輪抓到、一起修的**:

- 同一張照片有兩個請求在路上,一個先失敗會把狀態改成「失敗」,另一個還在處理;這時候存檔不會等它,正常那一次做完卻被拒絕、照片沒掛上。
  → `add_upload` 改成登記 → 處理圖片 → 落檔**整段握著作業的鎖**:同一張的另一次傳、取消、重新配對、存檔都排在它後面,交錯不會發生。
  (代價:同一份作業一次只處理一張;有用兩條連線的測試證明。)失敗重試也要有名額。
- 載入草稿之前先在表單上加了別的照片:欄位回到草稿的,照片卻是剛才加的 → 載入草稿時照片整個換過去(`switchTo`),原本那一份丟掉。
- 接回照片時斷線:草稿裡的照片識別被清掉、還可以直接存檔(照片全部漏掉)→ 沒接回來時記著是哪一份,照片區出現「重試 / 不要了」,
  這段時間不能加照片、不能存檔、也不會把草稿裡的照片記錄清掉。
- 系統說可能重複、填了差異按「繼續新增」之後,等照片停收的那一小段還按得到「就是這個」→ 兩個動作共用同一把鎖。
- 用「某一個顏色當透明」的 PNG 轉成 JPEG 會變黑 → 也鋪白底。

**Codex 複審第三輪**:後端「可以上線」。畫面剩 1 項:上次的照片還在接回來的時候按了儲存、接著接回失敗,存檔前的檢查讀到的是
還沒更新的「沒有失敗」而放行 → 「沒接回來」這個記號改成當下就寫(不等畫面更新)。修之前同樣的步驟商品會不帶照片存出去,修之後被擋下。

**取捨**:

- 手機頁沒做網頁內即時相機(`getUserMedia`),用系統的相機 / 相簿選檔:各家手機都支援、不用處理權限畫面。代價是每拍一張要按一次「使用照片」。
- 電腦這邊每 2 秒問一次有沒有新照片(配對中才問),不是即時推送:不用多架一套連線,慢 2 秒可以接受。
- 新增商品「存成草稿」時,照片的順序 / 說明 / 主圖記在瀏覽器(照片檔在伺服器,24 小時內回來接得上);換一台電腦接不回來。
- 改用既有商品時,這次加的照片直接丟掉(規格:不能自動掛到既有品號)。要補圖得到那個商品去加。
- 商品管理清單點品名仍然是「選那一列、右邊看詳情」(詳情裡有照片列),看照片面板的入口是小縮圖 —— 沒有把點品名改成開面板,避免改掉原本的手感。

**沒做**:規格 D 階段(依分類 / 適用機型瀏覽的照片列表、新增商品前的相似候選帶照片);進貨的「勾選商品」「批次貼上」兩個面板裡還不能看照片;
真機(iPhone / Android 掃碼、HEIC)要上到測試站由 owner 實測;每日的資料庫備份只有資料庫,不含照片檔(公司備份才含)。

## 2026-10-06:門號合約到期的名單與提醒

**背景**:2026-10-06 起銷貨明細會記門號合約的到期日。owner 要「到期的統計與提醒」:知道哪些客人的合約快到期、該聯絡誰。
owner 的決定:提醒只在系統裡(不推通知);到期前 3 個月開始列(可以改);聯絡過的要記;上線前就辦的舊客戶先不管。

**決定**:

1. **不另外建「合約」這張表。** 一筆合約就是一行有方案、有到期日的銷貨明細;規則寫成一個查詢(`apps/sales/contracts.py` 的 `contracts()`),
   名單、今日總覽的筆數、報表都從它出發。銷貨單作廢、整張銷退、改續約日,名單自然跟著變,不用同步第二份資料。
   「被退掉」看的是**那一行**有沒有銷退明細(舊資料有只退其中幾行的:沒退的那個門號還是合約)。
   代價:上線前的舊客戶沒有銷貨明細,進不了名單(owner 選「先不管」;之後要補登或匯入,再考慮另外一張表)。
2. **「已續約」是算出來的,不是人標的**:同一個門號在**另一張單**上有起算日更晚的合約,舊的那一筆就算已續約。門號比對去掉符號
   (`0912-345-678` = `0912345678`;函式索引 `soi_msisdn_digits`)。新約被作廢 / 退掉,舊的那一筆會回到名單上。
   **起算日同一天的另一張單不算**(Codex 抓到的:原本同一天就看誰比較後面建的,結果同一天開的兩張單 —— 打重複沒作廢、
   或一個門號兩份不同月數的合約 —— 先到期的那一筆被蓋成已續約、漏提醒。現在兩筆都留著,頂多重複提醒)。
   另外兩個不算:同一張單上重複的門號(打重複、或一個門號兩個方案)不互相算續約;去掉符號後不到 6 位數字的門號
   (舊單上的「-」「無」)不拿來比 —— 不擋的話這種單會全部互相蓋成已續約,該打電話的客人一個都不出現。
3. **聯絡紀錄另外一張小表**(`ContractFollowUp`,一筆合約最多一筆):已聯絡 / 不續約 + 一句備註 + 誰標的。
   **狀態可以是空的**:打了沒人接,先記一句「無人接聽」,人還留在待聯絡(沒有狀態的紀錄不算處理過)。
   按「未聯絡」回到待聯絡時備註留著;狀態與備註都空的才把紀錄拿掉。
   不放在銷貨明細上 —— 那是帳,存了就不改;聯絡到哪了是作業上的註記。沒有歷史(只留現在的狀況),要追每一次聯絡再加。
4. **待聯絡 = 還沒處理,而且到期日在「今天 + 設定的月數」以內**;已經過期還沒續的一直留著(那是最該打的)。標「不續約」才離開。
5. **提醒只是一個數字**:今日總覽「需要注意」多一列「門號合約 N 筆待聯絡」,點了到名單。
6. **統計放進自由組合報表**(加一張事實表「門號合約」、指標「到期門號數」、三個角度),不寫新的報表頁。
   日期是合約到期日,所以多了兩個往後看的期間(未來 3 個月 / 12 個月)。
7. 門市範圍照報表的規則:鎖倉店員只看得到、只標得到自己門市賣出去的。分頁上的數字跟著選的門市與電信業者走,不跟搜尋走。
8. **畫面先防標錯人**(紅隊找到的):
   - 畫面上的名單不是現在要的那一份時整份鎖住(換分頁 / 篩選 / 翻頁時先墊著的上一份、搜尋的字還沒查、標完還沒重抓回來)。
   - 標完的那一列**留在原地**(變淡、顯示現在的狀況),用伺服器回來的那一筆換掉它;不抽掉 —— 抽掉的話下面的往上跳,
     手指再點同一個位置會標到下一個人。展開的那一列標完也不自己收起來(收起來下面一樣會跳)。
     換分頁 / 篩選 / 翻頁,或再點一次同一個分頁(會重抓)才放掉。留著的那一份只屬於「那一次名單」(`epoch`):
     條件換過再換回來是新的一次,舊的那一份不會被搬出來蓋住新抓的名單;標記送出去到回來之間換了名單,回來的結果也不蓋上去。
   - **每一列三顆按鈕位置固定**(未聯絡 / 已聯絡 / 不續約),現在的狀況那一顆亮著、不能按:標完同一個位置還是同一顆,
     連點兩下不會變成按到旁邊那一顆(原本是「已經是那個狀況的那一顆不出現」,標完按鈕會換位置)。
   - **翻頁用游標(接在哪一列後面)不用頁碼、也不用第幾筆**:`?after=到期日,編號` / `?before=`。名單上的人被標掉 ——
     自己標的、**別的店員同時標的** —— 就離開這個分頁、後面的往前遞補;用頁碼或筆數翻下一頁會剛好跳過遞補上來的人
     (第一版用頁碼,紅隊之後改成「第幾筆開始、扣掉自己這一頁走掉的」,Codex 指出別人同時標的扣不到)。
     接在畫面最後一列後面拿,前面少了誰都不影響;翻過去是空的回最前面。規則在 `lib/contractList.ts`。
     「還有沒有上一頁 / 下一頁」看的是**畫面上的第一列 / 最後一列**(`hasPrevPage` / `hasNextPage`),不是伺服器剛重抓的那一頁:
     這一頁的人標掉之後,伺服器會把前面或後面的人補進同一頁、或整頁變空(空頁時伺服器照實講另一邊還有人) ——
     不這樣比,畫面上留著剛標完的那幾列、翻頁鈕卻不見了,還沒處理的人就回不去(Codex 第二輪抓到的)。
   - **名單不留快取、不在背後自己重抓**(`gcTime: 0`、不因為連線恢復重抓):換回看過的條件 / 那一頁一定重新抓
     (留著的話會先拿出剛剛的那一份,上面的人別人可能已經標過了);人正要按的時候名單不會自己換、列不會跳。
   - 每一列的備註草稿各自留著;打了還沒存的在那一格標「未存」(按那一列的按鈕會一起存);送出之後又補打的字不會被清掉。

**取捨**:

- 門號被電信公司收回、再發給別人,之後那個人來辦:舊客人的那一筆會被算成「已續約」。機率低,而且那時舊約早就過期很久。
- 同一位客人換了門號(攜碼出去再回來)系統認不出來,舊門號那一筆要人標「不續約」。
- 名單一次回 100 筆、可以翻頁;沒有匯出(要名單可以用自由組合報表匯出統計,明細匯出之後有需要再加)。
- 續約 / 攜碼沒填起算日的單(畫面會擋,別的入口才送得進來)沒有到期日:它自己不會被提醒,也不會把舊的那一筆蓋成已續約 ——
  舊的那一筆會繼續留在待聯絡。方向是「多提醒」不是「漏提醒」;補上日期(銷貨單清單的「改日期」)就正常。
- 「到期門號數」這個指標含已續約的(看的是「那個月有幾份合約到期」);要看還沒續的,加「合約處理狀況」這個角度。

**沒做**:推通知(Discord / LINE)、舊客戶補登或匯入、簡訊 / 撥號整合、每一次聯絡的歷史。

## 2026-10-06:條碼列印機(Argox OS-2130D)—— 商品標籤用瀏覽器列印,條碼照印表機的點數畫

**背景**:門市要用 Argox OS-2130D 印商品標籤,Mac 與 Windows 的 Chrome 都要能印。
owner 的決定:標籤紙 50 × 30 mm;進貨單整張印、單一商品補印、中古機逐台印都要;標籤上印品名、條碼、售價、序號末 5 碼、品號、進貨單號與日期;
印表機已經有、接在 Windows。

原本就有一頁「進貨單整張印標籤」,但它有兩個問題:條碼是把圖拉寬到貼滿標籤(線寬不是印表機的整數點,熱感印出來是糊的);
紙張尺寸被全站樣式裡後面的 `@page`(A4)蓋掉,其實不是照 50 × 30 送印。

**決定**:

1. **用瀏覽器列印,不直接對印表機下指令。** 原廠有 Windows 與 macOS 的驅動,兩種電腦同一套做法,不用另外裝程式、不用處理 USB 權限。
   代價:每台電腦要裝一次驅動、設一次紙張;每次列印要在 Chrome 的列印視窗按一下。
   直接下指令(PPLB,經 USB 或另外裝的小程式)可以免驅動、免按那一下,但要多維護一支裝在門市電腦上的東西,先不做。
2. **「要印什麼」只有後端一份規則**(`apps/inventory/labels.py`),畫面只負責排版與畫條碼。進貨單、幾台設備、一個配件 + 張數,回的都是同一種「一張標籤」。
   售價、成色、條碼內容、哪一張單進來的,都在那裡決定(畫面原本自己從進貨單資料湊,中古機的個別售價與成色湊不出來)。
3. **條碼自己照點數畫**:熱感一個點 0.125 mm、只有黑跟白。一個單位固定整數個點(3 點放不下用 2 點)、起點也落在點上、兩邊各留 10 個單位空白。
   編碼(哪個字對哪種黑白樣式)交給 jsbarcode,畫不交給它。IMEI(15 位數字)用 2 點是 38.5 mm,50 mm 的標籤放得下。
4. **放不下的碼不印糊的條碼**:原廠條碼太長 → 改印品號的條碼(刷品號一樣找得到);序號太長 → 只印文字(換成品號就刷不到那一台了)。列印頁上面會講。
5. **紙張尺寸用有名字的頁面**(`@page label`):不跟全站其他列印頁的 `@page` 互相蓋。
6. **標籤尺寸不做成設定**:只寫在 `lib/labels.ts` 與樣式裡。目前只有這一種紙;別家公司要用別的尺寸再加(要一起改排版,不是只改兩個數字)。
7. **系統設定有「列印測試標籤」**:一張四邊有框線(看有沒有被切)、一張真的樣子。我接不到實機,裝好之後要靠這一張讓 owner 確認。

8. **列印頁不能自己亂印**(紅隊找到的):
   - 自己跳列印視窗只在資料第一次到的那一刻決定一次(100 張以內、沒有提醒)。那一刻沒跳,之後把提醒弄不見、把張數改小都不會突然印起來;
     人自己按「列印」會取消還在等的那一次,不會同一批印兩份。有提醒(少印了幾台、條碼印不下)時不跳:列印視窗會把那一排提醒蓋住。
   - 一筆最多 500 張、整批超過 1000 張不畫也不印;一張進貨單超過 300 台不給印(請分批)。少印了、張數被壓到上限,後端在 `notes` 裡講,畫面顯示。
   - 配件補印按 Enter,印的是框裡現在看到的數字(打了範圍外的數字不送),每次打開從 1 張開始。
   - 條碼跟下面的字一定是同一個字串(頭尾空白只去一次、兩邊共用);有換行 / Tab / 全形字的碼不編條碼。
   - 每一張的高度 29.5 mm(比紙矮一點)、換頁寫在「第二張起每一張之前」:驅動回報的可印高度常比紙小一點點,剛好 30 mm 會每張多吐一張空白。
   - 個別售價是 0 或負的 = 沒填,印建議售價:跟銷貨開單帶價同一條規則(紅隊認為 0 應該不印價錢;沒有照做 —— 標籤上的價錢要跟結帳帶出來的一樣)。
9. **Codex 第一輪抓到的三件**:
   - 進貨單某一行是不是逐台印,看「這一行底下有沒有設備」,不看商品現在的「需追蹤序號」:進貨之後有人改了商品設定,
     原本照現在的設定判斷,那一行的每一台會全部印成同一個商品條碼。
   - 碼中間連續的空白要照原樣印(`white-space: pre`):瀏覽器預設把兩個空白併成一個,條碼編的是兩個、字只剩一個,又不是同一個碼了。
   - 列印頁放在全站的外框裡,外框不能捲:配件行數多的時候「列印」按鈕與提醒被擠出畫面、也捲不到。改成這一頁自己捲,
     第一排固定是張數 / 列印 / 關閉,配件的張數清單限高、自己捲。

**取捨**:

- 我驗得到的只有「每一張是 50 × 30 mm、一張一頁」(用 Chrome 輸出 PDF 量)與條碼的黑白樣式;**印出來的位置、濃度、槍刷不刷得到只能實機驗**。
- 瀏覽器經過驅動把畫面轉成點陣:縮放不是 100% 或驅動自己縮放時,線還是會糊。安裝文件裡寫了要選「邊界:無、縮放:預設」。
- 英數混合超過 12 碼左右的序號印不出條碼(2 點也放不下)。要解就得換 QR Code 或更寬的標籤紙,先不做。
- 配件補印沒有進貨單號(不知道是哪一批);同一張進貨單的配件一行最多 500 張。

**沒做**:直接對印表機下指令、每家公司自己的標籤尺寸、QR Code、外箱條碼對應商品、發票 / 收據列印機(另一件)、Mac 的實機設定。

## 2026-10-06:商品主檔學習成本,階段 A —— 各入口的預設一致、用詞各只有一個意思

**背景**:owner 交了一份 Codex 做的診斷(`docs/MP-POS-商品主檔學習成本診斷與改善方向.md`):新手要建一個商品之前,得先懂系統怎麼分類、哪個入口建什麼、
「狀態」在不同頁是不同意思。它建議分四個階段;owner 選「從階段 A 開始」(先減少建錯),B / C / D 記在 BACKLOG。
這是專家檢查,沒有找新手實測。

對照程式與資料庫之後:
- 文件說「APPLE 的系列有 PRO、PRO MAX,跟後綴重疊」只發生在測試站的測試公司(測試資料);正式站 JB 公司的系列是對的、已有 115 個機型。
  → 不用改程式,owner 同意把測試公司那兩筆清掉(沒有商品或機型掛在上面)。
- 一般「新增商品」的機型配件預設勾著「需追蹤序號」、專用的「新增配件」卻沒勾 —— 兩個資料庫目前都還沒有配件因此被設成追序號,現在修是預防。
- 「商品狀態」這個詞有三個意思(商品表單的主力 / 停產、設定選單裡其實是品況主檔的那一頁、手機精靈的品況)。

**決定**(1~4 是 owner 選的):

1. **一般表單新增時選「主機」→ 帶去「新增手機型號」**,不在一般表單新建手機。我多留了一條「留在這裡建立」:
   手機精靈要求至少一個容量、一個顏色,老人機、手錶這種沒有這些之分的機種它建不了;不留這條路,這些機種就沒有地方建。
2. **手機精靈的品況只預選「全新」**(原本全部勾起來,一按就是 4 種品況 × 容量 × 顏色)。
3. **主力 / 換代 / 停產 / 清倉叫「販售狀態」**;全新 / 已拆封 / 中古機一律叫「品況」(主檔頁改叫「商品品況」,舊名字留給功能搜尋)。
4. **序號預設只有一份**(`lib/productDefaults.ts`):主機逐件、配件按數量;一般新增與新增配件共用。
   一般表單換商品性質時那一格跟著換,但編輯既有商品、人自己動過、被虛擬商品 / 中古機定住時不替他改。
5. 畫面上的工程用語換成白話(SKU → 品項、wizard → 這一頁、placeholder / `is_secondhand=True` / PROTECT 這類直接拿掉)。
6. 「中古機」的勾選移到看得到的「屬性」。

**取捨**:

- 沒有動後端、沒有資料庫變更、不改既有商品。預設只影響之後新建的。
- 「批次貼上」沒有商品性質可選,預設仍然勾著追序號(它等於一律當主機建)—— 要解得讓它能選性質,那是階段 B。
- 「型號展開」也能選主機、直接建一批手機(不經過手機精靈);這個入口要不要收掉也是階段 B。
- 一般表單的草稿:載入草稿時,如果當時填過主機的欄位,視為已經選了「留在這裡建立」;那一格跟預設不一樣,視為人動過。
- 零件倉的東西沒有商品性質可選(那一排看不到):一律按數量、也不擋「要走手機精靈」。自己重看時抓到的 —— 先選主機再切到零件倉,原本會變成不能存、畫面上又看不出為什麼。

- 紅隊抓到、已修的:
  - 載入草稿會把「主機要走手機精靈」自己解開(品名尾端的數字會被自動填成世代,載入時又拿「有世代」當成按過「留在這裡建立」)。
    → 「按過留在這裡建立」直接記在草稿裡(`phone_here`),不拿別的欄位去猜;主機欄位沒打開時不自動填世代;離開主機就收回。
  - 勾過又取消「虛擬商品 / 中古機」之後,「需追蹤序號」停在被連動改掉的值上(主機勾過虛擬再取消 = 不追序號的手機;
    編輯既有的配件勾過中古再取消 = 被改成逐件記)。→ 取消時回到該回的地方(`requiresSerialAfterUnpin`:新增沒動過回預設,其他回到勾之前的值)。
  - 被定住時去按「需追蹤序號」(按了不會變)也被當成「人改過」。→ 值真的變了才算。
  - 被擋住不能存時沒有講原因。→ 講,儲存鈕上也有。
  - 「新增配件 / 型號展開」換商品性質會蓋掉人自己勾的序號。→ 跟一般表單一樣,人動過就不改;再點同一種不重設。
  - 手機精靈一個品況都沒勾時看不出來要勾。→ 那一格底下出現「請勾選品況」。
- Codex 第一輪抓到的:上面那幾項修正在同一次操作裡是對的,但「人動過序號沒有」「勾虛擬 / 中古之前的值」放在畫面元件自己的記憶裡,
  **存草稿再載回來就沒了**,載入時只能拿「現在的值跟預設一不一樣」去猜 —— 普通配件勾了中古機、存草稿、載回來取消中古機,那一格還是停在逐件。
  → 這兩件事改成放在表單狀態裡(`serial_touched`、`serial_before_pin`),跟草稿一起存、不送到後端;
  動作整個搬進 `lib/productDefaults`(`withNature` / `withWarehouse` / `withPin` / `withSerialByHand`),測試是整段操作、中間真的經過一次存草稿再載回來。
  「新增配件 / 型號展開」的「人動過」也存進它的草稿。
- 按「新增手機型號」離開時,一般表單上打好的品名 / 照片留在「新增商品」的草稿,不會帶到下一頁(回來按「載入草稿」還在);離開時會跳一句提示。
- 「留在這裡建立」的適用範圍直接寫在按鈕旁邊(「沒有容量、顏色之分的機種才留在這裡」):只放在滑鼠提示的話觸控看不到。

**沒做**(階段 B / C / D):七個入口收斂成一個起點、手機先選既有機型、依商品種類給不同欄位、搜尋與重複候選看照片、舊資料(混進機況的機型名稱、缺規格)的整理。

## 2026-10-07:商品管理搬到「進貨入庫」;建好品號帶著商品去進貨

**背景**:owner 實際操作商品主檔階段 A 之後說:「商品管理我覺得把它放在進貨那裡比較合適,建立品號後按進貨」。
建商品的下一步多半就是進貨;原本商品管理在「商品庫存」底下,建完要換入口、到進貨開單頁再搜尋一次剛建的商品。

**決定**:

1. **導覽**:「商品管理」分頁與「商品設定」選單(品牌系列 / 產品類型 / 商品品況)搬到「進貨入庫」,排在「進貨單」後面。
   「商品庫存」只剩 庫存查詢 / 庫存警示 / 調撥作業。網址一條都沒改,功能搜尋照舊。
2. **帶商品去進貨用網址**(`/purchases/new?add=編號,…`),不用另外的暫存:重新整理、開新分頁、從訊息條按都是同一個做法,
   而且進貨開單頁只多「打開時先放幾個商品」這一件事,掃碼 / 送出的規則都沒動。
3. **帶過來的配件數量是 0,不是 1**。一開始做的是 1(跟刷到一件一樣),紅隊指出:帶過來之後店員把每一件都刷一次,就多進一件
   —— 而且不管「帶」跟「刷」誰先到都一樣會錯。那個 1 沒有人說過,是系統替人填的。改成 0 = 還沒說進幾件:
   刷一件變 1、打數量就是那個數量、沒填存不了(數量框是紅的,儲存講「數量要大於 0」)。
   考慮過「記一個旗標,第一次刷到不加 1」:會算錯另一種人(看到已經有 1、只刷剩下的),而且要動刷條碼、批次貼上、勾選商品三條路。
   序號商品不用改:本來就是一個空位,刷到序號才算一台。
4. **草稿裡已經有的商品什麼都不改**。刷條碼的「再刷一次 = 多一件」是對的,但「帶過來」再按一次不該多一件。
   所以帶過來走自己的 `carryIn`,不走刷條碼的 `addProduct`。
5. **沒加進去的留在明細上方那一條**(按「知道了」才消失),不是幾秒就消失的訊息條:
   人以為都帶到了、其實少了幾項,存下去就是少進貨。找不到的要講幾個。
6. **做完才把參數從網址拿掉**(一開始是一讀到就拿掉):還在查的時候人離開,先拿掉的話這次就是沒帶、也沒講;
   後拿掉的話回到這一頁會再帶,而第 4 點保證再帶一次不會多。**儲存等帶過來的做完**:不然慢回來的商品會掉進存完之後的下一張空白單。
7. **中古機**:一般進貨單本來就不收。商品詳情的「進貨」對中古機是帶去「中古收購」(那一頁不預先帶商品:個人收購是一台一台填、廠商收購是另一張草稿)。
   手機型號同時建了全新與中古:「前往進貨」只帶一般的,**另外一顆「中古收購」**—— 不會只帶一半又不講。**虛擬商品、停用的商品沒有「進貨」這顆**。
8. **手機型號建完的按鈕字數一致**:再建機型 / 商品列表 / (中古收購) / 前往進貨(原本是「再建另一支機型」「去看商品列表」)。
   這次建的一般品項全部帶過去;沒進到的那幾行按 ✕ 拿掉 —— 序號沒刷的行本來就存不了,不會悄悄存成進了貨。
9. **一次最多帶 60 個**;帶不完的不能當沒這回事:網址多帶 `more=幾項`,開單頁講出來。
10. **帶過來是晚一點才回來的,要跟人手上的事排好順序**(Codex 複審第一輪抓到的四個交錯):
    - 還在處理的掃碼先做完才動明細與「正在刷序號的那一行」—— 不然刷進來的序號會進到被這裡換掉之後的那一行(別的手機多一台)。
    - 沒加進去的提醒自己一條(`carryNotice`),**只有人按「知道了」才消失、沒按不能儲存**:原本跟勾選商品 / 批次貼上共用一條,會被換掉;
      按了儲存才等到的結果,人還沒看到就送出去了。
    - 儲存等帶過來的做完;等的時候人離開了就不送(帶過來的那一段因為離開沒做,送出去是少了那幾項的單)。
    - 這一頁開著的時候也會收到新的「進貨」(訊息條是全站的,9 秒內都還按得到):網址上帶的內容每換一次就做一次,排隊做;
      清網址之前先看網址還是不是自己那一份。
    查一個商品最多等 15 秒,逾時當作查不到、講出來(不然儲存會一直等)。
11. **帶過來的不搶「正在刷序號的那一行」**(複審第二輪):原本有在刷的那一行,而且從收到這一次帶入到現在掃碼框被動過(打字、刷條碼)、
    或框裡還有沒送出的字 —— 那些字是要進原本那一行的,所以不換;帶過來的照樣加進明細,要刷它再點那一行。
    原本沒有在刷的那一行(剛開的單)、或人什麼都沒碰,才換成帶過來的那一個(他剛剛按的就是它的「進貨」)。
    考慮過「有在刷的那一行就一律不換」:那樣每次帶手機到一張進行中的單上,都要先點一下才刷得進去,沒點就是刷進別的手機。
12. **這張單正在儲存、或已經送出還不知道結果:帶過來的不加,當下就講、留著**(不等查回來 —— 那時候可能已經存好換頁了,就變成沒帶也沒講)。
    儲存按下去之前就在查的,儲存會等到佇列不再變才定稿;帶過來的新的一行一定是還沒填完的(配件 0 件、手機一個空位),所以那一次儲存一定會被擋下來讓人看到。
13. **沒加進去的那一條不會把「知道了」擠到畫面外**:同一種狀況只寫一行(停用的也是,最多寫三個品名 + 總共幾項),內容超過高度自己捲、按鈕固定在右上;
    提醒一個帳號一份(同一個分頁換人登入看不到上一個人的)。
14. **網址永遠寫著「所有還沒做完的批次」**(複審第三輪):連按兩個商品的「進貨」、都還沒查完就重新整理,原本只剩後面那一批(網址被後一次換掉了)。
    改成排隊(`carryQueue`),新的一批進來就把前面還沒做完的併回網址,做完一批拿掉一批;一批做完先把明細存進草稿、提醒寫好,才從網址拿掉。
    自己改寫網址的那一筆帶記號,不會被當成人又按了一次「進貨」;剛打開這一頁的那一次不看記號(重新整理之後記號還在瀏覽器的紀錄裡,那時候正是要再帶一次)。
    考慮過另外把還沒做完的批次存一份在 sessionStorage:網址本來就在、重新整理 / 上一頁都跟著走,多存一份要多管一份同步。
15. **「人有沒有在操作」看整個畫面,不只看掃碼框**(複審第三輪):等的時候點了別行的「已刷」要刷那一行,原本只看掃碼框有沒有被動過,帶過來的還是會把目標搶走。
    改成從收到這一批開始,任何點按 / 按鍵 / 輸入都算動過;再加上「正在刷的那一行換過了」「游標在序號格子裡」。寧可不換(人再點一下),不要換錯(序號進別的商品、而且存得過)。

## 2026-10-07:找得到 —— 沒寫品牌字首的機型寫法也對得上(新手商品建檔 R1 第一小包的第一步)

**背景**:owner 交了 `docs/MP-POS-新手商品建檔與既有品號沿用_完整改善計劃.md`,R1 太大、同意切成四小包,第一包是「找得到 + 先找再建」。
開工前先量(有真實資料就先量,不靠想像):
- 用店裡的寫法找(60 個真的配件 × 6 種打法)—— 都找得到。
- 新手的寫法(手寫 24 句)—— 10 句完全沒有候選。原因有兩個:
  (1) 測試公司沒有機型主檔(0 個),「iPhone 16」跟「IP16」對不起來 —— 這是資料,補上主檔就好(10 → 5);
  (2) 沒寫字首的機型(`11PM`、`13P`、`11 pro max`)被當成一般的字,不會去對機型 —— 這是程式。
如果不先補,「先找再建」會讓新手看到「找不到」然後建出重複的品號,跟計劃要解決的事相反。

**決定**:

1. **原則:只會多對上,不會讓原本找得到的變成找不到。** 拆字的結果(`words`)完全不變,只多記一份「沒字首的寫法」(`Features.bare`);
   比對時主檔認得、而且就是這個商品的機型才算機型對上,其餘照原本當一般的字。
   第一版不是這樣寫的:把 `11 PRO MAX` 真的接成一個字、沒對上的當成「機型對不上」直接排除。Grok 紅隊指出兩件事 ——
   `10C` 這種字有歧義(紅米 10C,也可能是在講 Type-C),排除會讓原本找得到的不見;沒有機型主檔的公司結果也跟著變了。所以整段照這條原則重寫。
2. **不另外做一套同義詞**,沿用機型縮寫表(`build_index`):它本來就把 `11PM`、`11PROMAX`、`13P` 收進去了(為了認 `IP13P/13PM` 這種接續寫法),
   只是比對時沒有拿「沒字首的字」去查。P 是 Pro 還是 Plus、主檔補了新機要不要改,都跟著原本那一份走。
3. **品牌 + 機型被接成一串**(`DAP 13P` → `DAP13P`;原本的規則把「英文 + 數字」接成型號,是為了 `RENO 16`):
   只在後半就是這個商品的機型時才拆;不是的話照原本的(這個型號沒對上)。
4. **單獨一個數字是很弱的線索**(`犀牛盾 12 黑`、`DAP 12 全覆蓋 粉`):店裡這樣講的是 iPhone 那一代,但數字太容易是別的意思(12 片、12 入)。
   所以:只在商品真的是那一代時算;`DAP 12` 還要品牌那個字在品名裡;**最多列為「相關」並寫明「只寫了數字 12,當成 iPhone 12 來比」**,
   不會變成同一款(紅隊的例子:`某牌/保護貼/12` 會跟 `某牌/IP12/保護貼` 在防重複互擋);不能只靠它就成立;分數比「同品牌、別的機型」高一點,所以排在前面。
5. **品名自己沒寫字首的**(`11PRO/認證電池`)也算那個機型;但品名已經寫了別的型號就不猜。
   `11PRO` 可以是 iPhone 也可以是 Pixel;實測 3,003 個真的品名有這種寫法的 9 個:沒有別的型號的 6 個都對,有別的型號的 3 個裡 2 個會猜錯。
6. **有歧義的寫法不能當得太有把握**(Codex 複審第一輪用實例抓到的四件事,都收緊了):
   - `11PRO` 在主檔裡同時是 iPhone 11 Pro 與 Pixel 11 Pro 時,不能把兩個都算成商品的機型(原本會讓 `PIXEL11PRO/電池` 跟已經指定是 iPhone 的 `11PRO/電池` 變成同一款)。
     商品已經指定機型的只認指定的那一個;沒指定、又不只一個機型叫這個的,不猜。
   - `DAP 12` 的 12 只能是「iPhone 那一代的弱線索」:不查主檔裡別牌登記的 `12`(Reno 12、小米 12),不然 `DAP 12 黑` 會跟 `DAP/RENO12/黑` 變成有把握的同一款。
   - **只要有靠數字猜的部分,就一律最多列為相關**,旁邊另有講明的機型對上也一樣(`某牌/IP11PM/保護貼/12` 對 `某牌/IP11PM/IP12/保護貼`:IP11PM 對上不能證明 12 也是機型)。
   - 防重複的對稱比對:正向因為新認得的寫法冒出一個「相關(顏色不同)」時,原本靠反向成立的同一款不能因此不見。
     第一次修是「這個結果用到新認法(`via_new`)就照樣做反向比對」—— 第二輪指出放太寬:`犀牛盾/11PM/透/黑` 對 `犀牛盾/11PM/黑` 以前就是「相關、顏色明確不同」
     (11PM 照字面就對得上),卻因此被反向比對升成同一款。「用到新認法」不等於「以前沒有這個結果」,用推算的分不出來。
     改成**直接問**:`compare(..., plain=True)` 就是改之前的比法(不認這些新寫法);對稱比對遇到「相關 + 明確不同 + 用到新認法」時,
     用 plain 再比一次,以前會做反向比對的(以前沒有結果、或只是資訊不足的相關)才做。
     第三輪再指出兩條還是會錯的路,照它的建議把規則講死成兩句:
     **(1) 現在的正向有「明確不同」時,反向只認以前的比法(plain)** —— 不然 `11PM/透/黑` 對 `IP11PM/黑` 會在反向被新認法認成同一款,
     而寫成 `IP11PM/透/黑` 時明明是顏色不同的兩個東西;**(2) 要升成同一款之前,以前的正向也必須是會做反向比對的那一種** ——
     主品名顏色明確不同、現在只是被某個「其他叫法」的結果蓋過去的,不能升。
   - **商品的「其他叫法」不能替商品猜機型**(第三輪):主品名 `GOOGLE/PIXEL11PRO/電池`(主檔還沒有這一支)、叫法 `11PRO/電池`,
     比叫法的時候看不到主品名寫的型號,會把 11PRO 猜成 iPhone 11 Pro。主品名有寫型號時,比它的其他叫法一律不猜(`named_elsewhere`)。
     實測(全量 15,313 個品名):拆字改之前 / 改之後零差異;`plain=True` 對改之前的 `compare` 994,200 組零差異(其中 4,122 組有結果);
     開著新認法,同樣 994,200 組裡等級變低或「明確不同」變了的 0 組;防重複 1,500 個品名,改之前會點名的一個都沒少,
     多點名的 26 個逐筆看過都是同機型同規格、只是寫法不同(`IP12PM/128G/藍` ↔ `12PM/128G/藍`、`iPhone6s-64G/金` ↔ `APPLE/6S/64G/金`)。

**量測**(測試公司 3,003 個真的品名、另外 owner 當天給的全量檔 15,313 個,搬到本機隔離庫、補機型主檔、在交易裡做完就復原;同一批句子改之前 / 改之後各跑一次):

## 2026-10-07:先找再建 —— 按「新增商品」先找一次;上面那一排收成兩顆(新手商品建檔 R1 第一小包的第二步)

所以「要改得動」的第一步反而是把**不能亂改的**先擋住 —— 不然改得動等於改得壞。

**決定**:

1. **用過的商品,這三個屬性不能改;擋下來、講原因、講出路**(owner 2026-10-07 在三個做法裡選的;另外兩個是「讓改、系統帶著轉」「只提醒不擋」)。
   帶著轉(數量制 ↔ 序號制當場補序號)之後可以做,它要動庫存與成本的規則,不是這一步。
2. **「用過」= 還有可能被作廢 / 退貨 / 確認的東西指到它**:沒作廢的進貨 / 銷貨 / 銷退 / 調撥 / 維修單明細、還沒過帳也沒取消的待確認入庫、沒作廢的序號、不是 0 的庫存。
   **賣到 0 也算**(那張銷貨單還在);**作廢的單不算** —— 把相關的單作廢、庫存歸零就可以改,這是改錯的出路,訊息裡直接講。
   沒有把「曾經有過任何異動」算進去:那樣建錯屬性的品號永遠救不回來。
3. **比的是存檔之後實際的值**,不是表單送來的那三個勾:換到「中古機類別」會連帶變成中古機、中古機一定追蹤序號。
   把這段連帶規則抽成一份(`flags_after_save`),`Product.save` 與存檔前的檢查用同一份 —— 兩份各寫各的,遲早一邊忘記。
4. **類別勾「中古機類別」一起擋**:它用 `.update()` 把底下所有商品一次改掉,不經過商品自己的存檔。底下有用過、會被改到的就不能勾,講是哪幾個、共幾個。
   「用過沒有」這裡一次查完(每一種單一個查詢),不逐個商品查(類別底下可能幾千個)。
5. **檢查只有一份,放在模型的 `save()`**(畫面、批次修改、匯入、指令、後台都過同一道);序列化器只負責把它講成 400 與一句話,批次修改逐個商品回報、整批復原。
   一開始在序列化器另外先擋一次,Codex 第一輪之後模型那一層要鎖著類別、重讀類別現在的設定才比得準,序列化器那一次變成多餘的(拿掉它測試一個都不會紅)→ 拿掉,只留一份。
   只在「這次存檔會寫到這三欄或類別」時才鎖、才查:進貨更新加權平均成本那種只寫別欄的存檔不多一個查詢。
6. **錯誤一律放在 `detail`**:畫面的錯誤訊息只認這一格;放在欄位名底下,類別那一頁會顯示成「400 Bad Request」。
7. **表單一打開就鎖起來**(另一個只讀的端點問「用過沒有」),不是等按儲存才被退回;但以伺服器為準 —— 沒問到就先不鎖,存檔照樣擋。
8. 品名 / 規格 / 條碼 / 類別(不連帶中古機的)/ 售價 / 販售狀態不受影響。改類別品號不跟著變(已經印出去的標籤要能繼續刷)。
9. 動之前唯讀查過正式站(1,142 個商品)與測試站(4,145 個):沒有三個屬性互相矛盾的商品(中古機卻不追序號、在中古機類別底下卻不是中古機…),
   所以「存檔時把屬性整理成一致」不會意外去改到用過的商品。

10. **紅隊(Grok,一輪)**:沒有找到漏算的「用過」、繞得過去的路、或會誤擋的存檔;它擔心「鎖住之後換商品性質 / 倉別還是會改到需追蹤序號」
    查過不成立(編輯既有商品時那兩個控制本來就不動那一格,`requiresSerialAfterNatureChange` 的第一行)。收了三個小的:
    只有匯入的庫存 / 序號、沒有單可以作廢時,訊息不能叫人「先把這些單作廢」(改成跟著情況講);
    模型那一層看的是「資料庫裡有沒有這一筆」而不是「這個物件是不是剛 new 出來的」;沒用過的商品不回「怎麼辦」。
    (它還提「各門市庫存一正一負加起來是 0」:庫存數量資料庫本來就不准是負的,不會發生。)

11. **Codex 第一輪(必修 2、建議 2)**:
    - **類別的檢查與連動之間有空檔**:甲把一個類別勾成中古機類別,檢查完「底下沒有用過的商品」;這時乙把一個**本來就用過**的商品移進這個類別(類別還不是中古機類別,放行);
      甲接著用 `.update()` 連帶改 —— 那個用過的商品就被改成中古機了。這不需要「同時開第一張單」,所以不在我原本說不處理的那一類。
      → 兩邊拿同一把類別的鎖(`FOR NO KEY UPDATE`:不擋別人新增指到這個類別的商品),鎖到之後重讀類別現在的設定再檢查;「看以前是不是 → 檢查 → 存 → 連動」在同一個交易裡。
      鎖的順序兩邊都是「類別 → 商品」。只寫別的欄位的商品存檔(進貨更新成本)不拿這把鎖。
    - **只存部分欄位時比錯了**:`save(update_fields=[…])` 沒列到的屬性不會被寫進去,卻被拿來跟資料庫比,記憶體裡改過就被擋;`update_fields` 照位置給的被當成「全部都寫」;
      類別只存名字也會進連動的檢查。→ 只比這一次真的會寫進去的那幾個。
    - 建議兩項也做了:「用過沒有」比人的操作晚回來時,鎖上的同時把那三格放回原本的值;「怎麼辦」直接寫在畫面上(平板沒有滑鼠提示)。

12. **Codex 第二輪(必修 2、建議 1)**:第一輪的兩項都確認解掉了;新的兩項是第一輪的修法帶出來的。
    - **鎖的順序不一致,會互等到死結**:第一輪的修法是「既有商品每一次存檔都拿它類別的鎖」。批次修改照品號一個一個存,
      兩批各含 A、B 兩個類別的商品就可能一批先拿 A 再等 B、另一批先拿 B 再等 A(只改售價也會);
      類別連帶改用的 `.update()` 鎖商品列的順序不固定,跟進貨照編號鎖商品也可能各拿一半。互等的那一筆會變成 500。
      → **類別的鎖只留給真的需要它的兩件事**:把類別改成中古機類別、把既有商品**移進**這個類別(看資料庫裡現在的類別跟要存的一不一樣)。
      沒有換類別的存檔不拿(類別現在的設定照樣重讀)。這樣一個交易最多只拿一把類別的鎖,類別之間沒有先後可以排錯。
      **順序固定:先類別、後商品,商品照編號** —— 跟庫存那一套(`lock_stock_rows`)同一個方向、同一種鎖(`FOR NO KEY UPDATE`):
      類別連帶改先照編號把商品鎖好(這一輪只鎖要改的那幾列;第三輪改成鎖整個類別,見第 13 點);批次修改要換類別時,動任何商品之前先拿好那個類別的鎖,商品改成照編號一個一個來。
    - 拿掉「每一次存檔都鎖類別」之後,要另外擋住一件事:沒換類別的存檔讀到連帶改**之前**的屬性、等對方改完,又把舊的值寫回去
      (商品留在中古機類別裡卻不是中古機;之後它一用過,整張表單就存不了)。→ 存檔先鎖住商品自己那一列再讀,「有沒有變」比的是鎖到的那一份。
      這把鎖存檔本來就會拿(寫入那一下),只是提早到讀之前;連帶改也先鎖那幾列,所以兩邊排隊:誰先誰後結果都一致。
      為了維持「先類別、後商品」,要不要拿類別的鎖得在鎖商品之前決定,所以先不鎖讀一次類別;
      讀跟鎖之間剛好被別人移走的(同一個商品三個人同時改才會)鎖到之後補拿 —— 這是唯一一處順序反過來的地方,寧可那一下可能等,也不要漏掉檢查。
    - **`update_fields` 給產生器會壞**:我為了知道「這次寫哪幾欄」把它看過一次,產生器就空了,原樣交給 Django 變成「一欄都不寫」而出錯。
      → 整理成一份(`save_arguments`),商品與類別的存檔都把**整理過的那一份**往下傳(關鍵字、照位置都是)。
    - 建議那一項也做了:批次修改被退回時,畫面只有一句「部分商品失敗,已全部復原」,看不到是哪一個、為什麼(owner 選的是「擋下來,講原因」)。
      → 逐個講「品名:原因」(`lib/bulkErrors.ts`)。批次修改的畫面本來就會送「需追蹤序號」,所以這一條擋得到的地方人看得到原因。
    - 查過「新增手機型號」:它只建新商品,新商品不拿這裡的任何一把鎖;它自己取品號時先主機類別、後零件類別的順序是原本就有的,這一步沒有動。

13. **Codex 第三輪(最後一輪;必修 2)**:第二輪的互等它逐對重走過,確認兩個交易的情況下已經沒有;批次修改逐個講原因也確認可以。新的兩項:
    - **連帶改只鎖「要改的」不夠**:第二輪的修法讓類別連帶改只鎖還不是中古機的商品。但底下一個**本來就是中古機**(沒用過)的商品,
      可能正有人在存檔把它改成不是 —— 那一邊鎖著它、讀到類別還不是中古機類別、還沒提交。連帶改沒把它算在內,不會等,先提交了;
      那一邊接著把「不是中古機」寫進去。結果類別是中古機類別,底下卻有一個不是。
      → 連帶改之前照編號把這個類別底下**全部**的商品鎖住(`lock_category_products`),等所有正在存檔的做完;鎖完才看哪些用過、哪些要改,只改還不是的。
      改之前正式站就是整個類別一起 `.update()`(每一列都會被鎖到),所以鎖到的範圍跟原本一樣,只是現在順序固定、而且在檢查之前。
    - **位置與關鍵字同時給的 `save()`**:`save(False, False, None, ["name"], update_fields=None)` Django 只寫 `name`,我的判斷卻看關鍵字、當成全部都寫 → 誤擋;
      那個位置給的是產生器時一樣會壞。→ `save_arguments` 改成照 Django 自己的規則把位置參數對回名字(關鍵字是預設值就用照位置給的;重複給、超過四個丟 `TypeError`),
      往下傳一律換成關鍵字;測試裡拿 Django 自己那一段(`Model._parse_params`)對 56 種組合,答案要一樣。
    - **這一類問題三輪都是「同時做」才會發生的**,只看發出去的查詢驗不到「真的有等」。所以補了四個真的用兩條連線的測試
      (`TwoPeopleAtOnceTests`,照 `inventory/test_locking.py` 的做法:另一條連線鎖住、改掉、停一下才提交):
      連帶改等正在存檔的商品(就是這一輪這一項);存檔等連帶改、不把舊的屬性寫回去;移進類別等類別改完(第一輪那一項);類別要改等正在移進來的商品。
      每一個都確認過:把對應的鎖拿掉,它就會紅。
    - 照約定三輪為限:這兩項修完沒有再送第四輪,停下來問 owner。

14. **Codex 第四輪(owner 同意加的一輪,只看第三輪之後改的):可以上線。** 兩項都判定已修好;兩種先後、對上進貨 / 批次修改 / 單一商品存檔 / 另一個類別連帶改都重走過,沒有新的互等;
    位置與關鍵字的對法它另外用 20 萬多種組合跟 Django 對過,一致。兩個不擋上線的建議都是關於那四個兩條連線的測試夠不夠穩(記在 `BACKLOG.md`,沒有在這一步改):
    另一條連線是「停 0.8 秒就提交」,這一邊如果剛好慢了超過 0.8 秒,拿掉鎖的版本也可能碰巧通過;另一條連線出錯不會讓測試失敗、等它結束也沒有期限。
    (`inventory/test_locking.py` 原本的做法也是這樣,要改就一起改。)

**還沒解的**:改屬性與「對這個商品開出第一張單」同時發生時,兩邊都會成功(單據那一邊沒有鎖商品這一列;檢查的那一刻還看不到對方沒提交的單)。
要補得讓進貨 / 銷貨 / 調撥在動庫存前先鎖住商品這一列,是那幾支服務的規則,這一步不碰;記在 `BACKLOG.md`。

**沒做**(都在 `IDEAS.md`):改動紀錄與復原、合併重複的品號、刪除沒用過的品號、品況重分類、改品名時舊品名自動留成其他叫法、帶著轉。

## 2026-10-07:拖拉排序 —— 放開就換、背景存、最後只重抓一次(類別、供應商)

**背景**:owner 在測試站試的時候回報「類別無法拖拉排序」「供應商那邊也是」:電腦 Chrome、拖得動、放開之後順序沒變。
查測試站的紀錄:每一次放開,伺服器都收到並存成了(全部 200,資料庫裡的順序真的變了),所以不是存不進去,是**畫面沒有跟著變**。
原本的寫法(很早就有,不是這幾天改壞的):放開 → 每一列各送一個 PATCH → **每一個 PATCH 成功就重抓一次清單**(類別還會連商品清單一起重抓,那一個比較慢)→ 畫面只認最後那一次重抓。
紀錄裡看得到:18 個類別拖一次是 18 個 PATCH,接著 4~13 秒內每秒約 3 個 GET;5 個供應商是 5 個 PATCH + 2 秒的 GET。這段時間畫面完全沒有變化。
owner 隔 3~6 秒又拖一次(16 秒內拖了 5 次),每一次都是照畫面上那一份舊順序算的、又把 18 列整份重存 —— 所以不只「沒變」,還越拖越亂,測試站留下兩個類別同一個編號。
本機沒有網路延遲,看不出來;把頁面的 `fetch` 包一層(每個請求等 300 毫秒、一次最多兩個)就重現:只動 3 列也要 1.5 秒畫面才換。

**決定**:

1. **放開的當下畫面就換**(直接改清單的快取),不等存檔。
2. **存檔在背景做,只存編號有變的那幾列**;**一次拖動存完才存下一次** —— 下一次拖動是照畫面上已經換過的順序算的,兩次的 PATCH 交錯的話,比較晚到的舊編號會蓋掉新的。
3. **全部存完才重抓一次**(類別另外重抓一次商品清單),不是每存一列抓一次。
4. **沒存成要講,而且看得到**:清單上面一句話(以前類別的錯誤訊息放在右邊的類別詳情裡,沒選類別時根本不會出現),重抓伺服器現在的順序;後面排隊的不存。
   這之後、重抓回來之前再拖:畫面上是沒存成的那個順序,伺服器並沒有 → 每一列都存(存完一定是畫面上那個順序)。
5. 規則抽成一份(`lib/reorder.ts` 的 `moveRow` / `changedRows` / `createReorderQueue`,不碰 React,有測試);`hooks/useReorder` 只負責把它接到快取與 PATCH。商品管理的類別清單與供應商頁共用。
6. **沒有另外做一支「整份順序一次送」的端點**:那樣最乾淨(一個請求、一個交易),但要動後端兩個地方;這次的問題是畫面等太久,先用最小的改法解掉。記在 `BACKLOG.md`。
7. 舊的獨立類別頁(`pages/inventory/CategoriesPage`,導覽已隱藏)沒有動:它本來就先換畫面(自己留一份清單),沒有「看起來沒變」的問題,只是一樣會多抓很多次。記在 `BACKLOG.md`。

8. **紅隊(Grok,一輪)抓到四點**:
   - 佇列放在畫面元件裡:存到一半切到別頁再回來,會開第二條佇列,把畫面上「還沒存完的順序」當成伺服器已經有的,兩條的 PATCH 交錯。
     → **一份清單只有一條佇列,放在模組裡、不跟著畫面走**(這一點我送審之後自己也改了)。
   - 同一次拖動裡有一列先失敗、其他還在路上:原本馬上去重抓,晚到的 PATCH 在重抓之後才寫進伺服器,重抓到的是舊的。→ 等每一列都有結果(`Promise.allSettled`)才往下。
   - 沒存成、重抓也沒成時訊息寫「已重新載入」。→ 訊息分三段:一沒存成就講「排序沒存成,重新載入中」;重抓回來「…已重新載入」;重抓也沒成「…請重新整理頁面」。
     人在這段時間又拖了就不再講上一輪的(那個順序還在畫面上,新的這一次會整份存進去)。拖回同一列(什麼都沒做)不會把訊息清掉。
   - 「放開時剛好有重抓在路上,畫面會被蓋回舊順序」:查過這一版(`@tanstack/query-core` 5.100.10)取消時的回復是當場做的、不是晚一拍,實際操作也沒有被蓋回去;
     還是改成更保險的順序(先寫進快取、再取消、取消完核對一次被換掉就補寫),不靠函式庫內部的先後。
   - 它另外指出三個測試沒有驗到名字說的事 → 改名 / 補上真正的斷言。

## 2026-10-09:庫存查詢聽得懂通訊行的寫法(通訊常用語彙表)

**背景**:owner:「庫存查詢系統不夠強大,還要再帶入通訊的常用語彙,比如 IP=IPHONE, U=Ultra, +=Plus」。
查了程式:庫存查詢(`products/stock-matrix`)的搜尋是「整串字原樣出現在品號 / 品名 / 規格 / 條碼 / 類別裡」才算。
測試站 3,043 個商品實測:`iPhone17`、`17 pro max`、`16 plus`、`S25 ultra`、`IP17 256 黑` 都是 0 筆;`iphone 17` 只找到品名真的寫「iPhone 17」的,寫成 `IP17` 的配件與中古機都不在裡面。
「商品管理」的搜尋早就接了共用比對(`identity/product_match`),庫存查詢沒有接;而且共用比對要公司有機型主檔才認得簡寫,`IP17 PM`、`S25 U`、`S25 plus`、`IP17 256 黑` 連它也找不到。

**決定**:

1. **庫存查詢的搜尋 = 原本的 + 兩種多的,三者聯集;只會多找到,不會少找到。** 原本那一條(整串字照字面,六個欄位)一個字都沒動。
2. **多的第一種:一個字一個字比,每個字可以是店裡的另一種寫法**(`backend/apps/catalog/shop_terms.py`,新檔)。
   把打的字用空白 / 斜線 / 逗號拆開,每個字變成一條比對式,**每一條都要在品名 / 規格 / 類別裡對得上**(品號、條碼不拆字去比:
   「iphone 17」的 17 會對到每一個條碼裡有 17 的 iPhone;碼是整串在比的,原本那一條會比)。每個字對得上 = 照字面出現,或用語彙表裡的另一種寫法出現,
   型號中間有沒有空白 / 連字號都算(`IP17PM` = `iPhone 17 Pro Max` = `IPHONE17 P MAX`;`X200` = `X 200`)。
3. **語彙表是從舊系統 15,312 個品名數出來的,不是猜的**:
   `IP` = `iPhone`(字首 3,419 次 / 486 次;舊系統的新機還寫成 `APPLE-18PM`、`APPLE-I6S PLUS`,APPLE 後面直接接數字也算);
   `PM` = `PMAX` = `P MAX` = `Pro Max`(709 次);`P` = `Pro`(接在數字後面,938 次);`+` = `Plus`(949 次);`U` = `Ultra`(253 次);
   `Fold` = `Z Fold`、`Flip` = `Z Flip`;`ZF` = `ZenFone`(182 次 —— 這家店的 ZF 是 ZenFone,不是 Z Fold);
   品牌 `SAM` = `三星` = `Samsung` = `Galaxy`(2,005 / 609 次)、`華為` = `Huawei`、`小米` = `Xiaomi`、`紅米` = `Redmi`、`蘋果` = `Apple`、`谷歌` = `Google`、`華碩` = `ASUS`、`索尼` = `Sony`;
   容量 `256G` = `256GB` = 單寫 `256`(品名寫 `G` 的 4,239 個、`GB` 120 個,新機常寫「灰256」),`1T` = `1TB`;顏色 `黑色` = `黑`(單寫一個字 3,462 個)。
4. **為了不亂對到的幾條**(都是拿真實品名量出來才加的):
   - 單獨一個數字要是「那個數字」:打 `17` 不對到日期碼 `251017`、打 `256` 不對到 `2560`;
   - 很短的詞(`U`、`PM`、`IP`、`+`)單獨打的時候只認「帶條件的」寫法:`U` 要接在數字後面(`S25U`),`UAG` 的 U 不算;`IP` 後面要接數字 / X / SE,`IPAD`、`FLIP` 不算;
   - 單獨打 `plus` 時,`8+256G`(記憶體 + 容量)的加號不算;只認容量會有的數字當容量(`5G` 是網路);
   - 型號從一個字的開頭對起:`A17` 不對到 `2.4A 17W`。
   這些限制只管「另一種寫法」那一半;**照字面的那一半每個字都留著**(原本找得到的照舊)。整串字一模一樣的更有第 1 點那一條保底。
5. **多的第二種:跟商品清單同一套共用比對**(`find_candidates`,只收每一項都對得上的):用「其他叫法」叫的、公司有機型主檔時更準的那一種。庫存查詢找得到的不會比商品清單少。
6. **語彙表跟共用比對是兩支、不共用規則**:共用比對是「認定是不是同一個商品」用的(防重複、進貨比對),要準(`IP17` ≠ `IP17PM`)、要機型主檔;
   語彙表只給查詢用,要找得到(打 `IP17` 連 `IP17PM` 也出來 —— 字面本來就會)、不需要機型主檔、不替人做任何決定。沒有動共用比對。
7. 比對式在資料庫裡跑(PostgreSQL),測試在 Python 跑,**兩邊的意思要一樣**。語彙表照習慣寫大寫、`\d`、`\s`,交出去之前 `_portable()` 把它們全部寫明:
   大小寫變成 `[Ii][Pp]`(比對時**分大小寫**:`~` / `__regex`,不開「不分大小寫」)、數字變成 `[0-9]`、空白變成列出來的四種(半形空白、Tab、不斷行空白、全形空白)。
   人打的符號一律當成字面(跳脫),字太多(超過 8 個字)或太長(一個字超過 40 個字元)就不用這一套、只照字面找。空字元先拿掉(原本會讓整個查詢出錯)。
   有一個測試把每一條比對式拿到資料庫與 Python 各跑一次(2,000 組以上,含各種空白、別的文字的字母與數字)、答案要一樣。
8. 複審照 2026-10-09 起的輕量版,分流「一般」(只是查詢,不動單據、金額、庫存數字):Codex 一輪 + 只查修正的一輪。
   **第一輪 P1 一項**:比對式原本靠兩個引擎自己認空白 / 數字 / 大小寫(`\s`、`\d`、不分大小寫),而它們認的不一樣 ——
   品名中間是 U+0085 的 `IP17…PM`,Python 說找得到、資料庫找不到;`İIP17`(土耳其文的 İ)相反。測試跑的是 Python,等於測試與實際查詢可能相反。
   → 就是上面第 7 點的做法(原本是 `~*` 加不分大小寫)。實務上會遇到的是全形空白與網頁貼上的不斷行空白,這兩種明列為可以隔在型號中間的空白。
   其餘它確認沒問題:原本的搜尋條件完整保留、只看得到自己公司、庫存加總與篩選 / 分頁沒有被動到。
   **第二輪(只查這一項):可以上線** —— 它自己在 PostgreSQL 跑了 19,732 組比對,全部跟 Python 一致;`_portable()` 對這一支會組出來的比對式沒有改錯意思;沒有新的 P0 / P1。

**沒做(記在 `BACKLOG.md` / `IDEAS.md`)**:商品清單與開單頁的搜尋還沒用這張語彙表(只有共用比對);語彙表寫在程式裡,還不是每家公司可以自己加的設定;
老 iPhone 的 `IP7P`(= 7 Plus)對不上拼成「Plus」的品名(機型主檔有的公司靠共用比對對得上);`IP8+64G` 這種加號後面直接接容量的,單獨打 `plus` 找不到;類別的說法(平板 = PAD / TAB、手錶 = WATCH)沒放。

**驗證**:這一組 33 個測試(逐條改壞 82 條都會紅;後端整套 795 個,只有照片那一組原本就會跨秒失敗的那一個紅了一次、單獨重跑過;語彙表每一條「打什麼 → 找得到 / 找不到」、照字面的一定找得到、怪符號、太長;庫存查詢 API:owner 講的三種寫法、一個字一個字比、
