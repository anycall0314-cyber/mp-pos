# 設計決策紀錄

> 採用簡易 ADR 風格。每條決策包含日期、選擇、理由、未採用的替代方案。

## 2026-05-17：唯一日常介面是 React,Django admin 退到背後

**選擇**:所有日常作業介面(CRUD / 過帳 / 查詢 / 設定)都在 React app 完成。Django admin 不刪,但只當 dev 階段測資工具與緊急維運 fallback,不引導使用者使用。

**理由**:使用者不想開兩個入口(Django admin + React)做日常作業。Django admin 雖然開箱即用,但 UX 不夠密集、不能像 Excel,且讓使用者面對兩種完全不同介面風格會混亂。

**對應設計約定**:
- 凡是 Django admin 上能做的事,React app 都必須做出對應 UI
- 包括但不限於:商品/類別/倉庫/供應商/客戶/序號 主檔 CRUD、進貨單與銷貨單錄入與過帳、序號狀態維護、單據作廢
- README 不引導使用者打開 `/admin/`
- Phase 5 SaaS 化時,平台跨租戶後台**也用 React 做**,不用 Django admin

**未採用**:用 Django admin 當 Tenant Admin 介面(欲蓋彌彰、體驗不一致)。

## 2026-05-17:UX 模式 — 三種頁面版型而非單一 Master-Detail

**選擇**：新系統 UI 分三種版型，按頁面用途套用：

| 版型 | 用途 | 對應舊系統 |
|------|------|-----------|
| **錄入頁 (Entry Page)** | 開單據（進貨/銷貨/調撥/維修），鍵盤為主，連續輸入 IMEI 與明細 | 後台 ACNI002 風格 |
| **Master-Detail** | 主檔維護（商品/客戶/供應商/類別），左列表 + 右詳情，鍵鼠混用 | 既有設計 |
| **報表頁 (Report Page)** | 查詢報表，上方篩選列 + 中央結果表 + 底部總計 + 匯出（CSV/Excel/PDF） | 前台 100+ 個編號報表 |

**理由**：原本只設計 Master-Detail 一種版型，無法覆蓋舊系統的兩個真實使用模式。錄入頁與報表頁的需求差異大（鍵盤友善 vs 篩選與匯出），不能用同一個元件硬套。

**對應設計約定**：
- 錄入頁必須支援 Tab 自動跳欄、Enter 提交、ESC 取消、條碼掃描連續輸入、F-key 快捷工具列
- 報表頁必須支援多重篩選、匯出（CSV / Excel）、保留舊系統的 MMxxx 編號（建立 command palette 用編號或關鍵字跳轉）
- 三種版型細節寫在 [ui-patterns.md](ui-patterns.md)

**未採用**：用 Master-Detail 通用元件硬套所有頁面（會讓錄入慢、報表查不到）。

## 2026-05-17：版型 — Master-Detail 雙欄

**選擇**：所有業務頁面採左欄列表 + 右欄詳情的雙欄版型，禁用卡片式瀏覽。

**理由**：使用者明確排斥卡片牆造成的滾動成本，要求單頁瀏覽完。3C 進銷存的列表單元多（型號、序號、單據），雙欄能在不滾動的情況下兼顧檢索與細部編輯。

**未採用**：卡片牆、單一大表格 inline 編輯。

## 2026-05-17：技術棧 — Django + DRF + PostgreSQL / React + Vite + TS

**選擇**：後端 Django 5 + DRF + PostgreSQL；前端 React 18 + Vite + TypeScript；monorepo `backend/` `frontend/`。

**理由**：Django 內建 admin/auth/migration 對「表單多、權限細、報表多」的進銷存生產力高；FastAPI 的 async 強項在這個場景用不到。前端用 React + Vite 是最不挑團隊的搭配。

**未採用**：Next.js（不需要 SSR）、Laravel（PHP 生態的工程習慣不在本專案目標）、FastAPI（admin 要從零做）。

## 2026-05-17：序號層級 — Product / ProductSerial 兩層

**選擇**：商品分 `Product`（SKU 型號）+ `ProductSerial`（單台序號）兩層；庫存以序號為單位。

**理由**：3C 業每台 IMEI/SN 都不同，必須逐台追蹤位置與狀態，才能支援保固、維修、調撥、防竄貨。

**未採用**：純 SKU 數量法（無法支援序號生命週期）。

## 2026-05-17：成本法 — 加權平均（同時保留逐台採購成本）

**選擇**：銷貨成本走加權平均；但每台 `ProductSerial.purchase_unit_cost` 仍記錄 landed cost 攤提後的真實採購成本。

**理由**：使用者明確選擇加權平均（帳務乾淨、業務員無法挑批號）；但保留逐台成本只是多一個欄位的事，未來想切換到「逐台實際成本」或做毛利分析，不用回頭補資料。

**未採用**：純 FIFO（與序號追蹤邏輯衝突）、純逐台實際成本（業務員可挑批號衝績效）。

## 2026-05-17：附加費用 — 按金額比例攤到進貨明細

**選擇**：進貨單的運費/關稅/保險等 `extra_cost_total`，按各明細 `qty * unit_price` 占總金額比例攤到每筆明細。

**理由**：landed cost 標準做法，貼合實際成本。按數量平攤會在貨價落差大時失真。

**未採用**：按數量平攤、不入成本（另記費用帳）。

## 2026-05-17：角色架構 — 三層角色，前端單一 SPA

**選擇**：定義三層角色 Platform Admin（系統提供者）/ Tenant Admin（經銷商老闆）/ Tenant User（店員）。Platform Admin 走 Django `/admin/`；Tenant Admin 與 Tenant User **共用同一個 React app**，靠登入角色決定能看到哪些導航項與按鈕，實際資料邊界由 DRF permission 把關。

**理由**：拆兩個前端 app 會代碼重複、部署複雜度倍增。同 app 切換角色是主流 SaaS 做法，安全邊界落在後端 API 才是正解，前端只是 UX 過濾。

**未採用**：拆兩個 React app（Shopify 風格）、把老闆功能也丟到 Django admin。

## 2026-05-17：多租戶 — 預留但 MVP 不啟用 UI

**選擇**：所有業務表自帶 `tenant_id`、queryset 統一經過 `for_tenant()`、middleware 在 MVP 階段把 `request.tenant` 寫死成 `DEFAULT_TENANT_ID=1`。

**理由**：未來轉 SaaS 不用回頭重寫；當前不暴露在 UI 上以免增加認知負擔。

**未採用**：等需要時再加（過去經驗：補 tenant_id 是高風險重構）。

## 2026-05-18:移除進貨「附加費用」+ 「過帳」改一步、改用課稅別

**選擇**:
- 進貨單 `extra_cost_total` 欄位移除,landed cost 攤提改用「課稅別 + 計價數量」實現
- 銷貨、進貨都加 `tax_method`(應稅內含/外加/免稅/零稅)
- `unit_landed_cost` = 未稅單價(含稅時 = unit_price / 1.05)

**理由**:多數通訊行不單列運費,習慣把附加費用直接攤在單價;改用稅別可以更貼近開發票時填的欄位。

**影響**:現有資料 extra_cost_total 已遺失(都是測試資料,可接受)。

## 2026-05-18:進貨明細加 billed_qty(計價數量),處理贈品

**選擇**:`PurchaseOrderItem` 新增 `billed_qty`,獨立於進貨數量(`qty`)。
- 金額 = `billed_qty × unit_price`
- 單台落地成本 = (未稅 billed_total) / qty → 贈品稀釋平均成本

**理由**:廠商常送贈品/試用品,進貨數量 > 計價數量。舊系統做法一致。

**未採用**:直接打折(無法精準對到原進價);零單價輸入(會破壞 weighted_avg_cost)。

## 2026-05-18:銷貨明細 1 對多序號(SalesOrderItemSerial 中介表)

**選擇**:銷貨明細 `qty` 可 > 1,序號改 M2M(透過 `SalesOrderItemSerial` 中介表),允許「同款手機賣 2 支」一行。

**理由**:同一商品多台是日常情境(賣兩支白機給家庭客)。原本一台一行 → 一行最多 1 序號太僵硬。

**未採用**:單一 FK + 限制 qty=1(逼使用者開多行)。

## 2026-05-18:儲存即生效 + 作廢機制(取代兩步式「過帳」)

**選擇**:
- 進貨、銷貨單 POST 成功就 commit(寫序號、寫加權平均、寫異動)
- 不要可改可刪,要取消用「作廢」action `is_void=True`
- 作廢有規則:進貨作廢需所有序號仍在 in_stock;銷貨作廢把序號退回 in_stock

**理由**:舊系統「未過帳/已過帳」兩段式造成大量誤操作。一步式 + 作廢更直觀,責任歸屬也清楚。

**未採用**:可編輯模式(難以維持加權平均一致性)。

## 2026-05-18:商品搜尋 — pg_trgm + 自製 TrigramSearchFilter

**選擇**:升級到 PostgreSQL,啟用 pg_trgm 擴充,寫一個自製 SearchFilter:
1. 先試 `icontains`(子字串)
2. 沒結果且 query ≥ 3 字 → fallback 用 `TrigramWordSimilarity`,門檻 0.35
3. 取代 DRF 內建 SearchFilter,全域生效

**理由**:萬筆級別商品要支援打錯字也能找到(「iphne」找到「iPhone 15 Pro」)。icontains 是常態路徑、trgm 是補救路徑,避免短關鍵字誤判。

**未採用**:純 ILIKE(打錯字找不到)、Elasticsearch(殺雞用牛刀)。

## 2026-05-18:前端下拉一律 server-side ComboBox

**選擇**:所有資源選單(商品、客戶、供應商、序號、方案、SIM 卡、業務員、單別)都用 `ComboBox` 元件 + `api/search.ts` 裡的 `searchXxx`。不再一次抓全表用 `<select>`。

**理由**:萬筆規模 `<select>` 不可用。打字 debounce 200ms 拉 ≤ 20 筆。`payload` 帶完整物件避免後續再 round-trip。

## 2026-05-18:銷貨單發票自動取號(InvoiceTrack 字軌)

**選擇**:在「系統設定」維護發票字軌(AB 12345678–887);銷貨單建單時依 `invoice_form` 從字軌 `SELECT FOR UPDATE` 原子地取下一張號碼,使用者不需手動輸入。

**理由**:法定要求發票號碼連續、避免重號;手動輸入容易出錯且無原子保證。

**未採用**:接 e-invoice 平台(複雜度過高,Phase 3 再說)。

## 2026-05-18:付款方式主檔 + N 筆付款拆分

**選擇**:銷貨單支援 N 筆 `SalesOrderPayment`,`sum(amount) == total` 才能存。付款方式從 `PaymentMethod` 主檔(`tenants.PaymentMethod`)讀,使用者可自由新增(LinePay / 街口 / 全支付 / 匯款 / Apple Pay)。

**分類三類**:
- `cash`:現金 — 影響當日營業現金
- `transfer`:匯款 — 不影響當日現金
- `non_cash`:非現金(信用卡、行動支付)— 不影響當日現金

**理由**:通訊行付款通路多元、且需要區分「真現金」做日報。

**未採用**:固定 enum(無法擴充)、單一付款欄位(無法部分現金部分刷卡)。

## 2026-05-18:結帳成功後不關 modal,改顯示成功狀態 + 列印按鈕

**選擇**:確認結帳 → 後端寫單 → modal 切換為「結帳完成」狀態,顯示單號 / 發票號 / 付款明細 + 「列印收據」「列印發票」「完成」按鈕。完成才關閉 + 跳列表。

**理由**:舊流程「儲存 → 跳列表 → 再點進去列印」太多步;一氣呵成更貼合 POS 操作節奏。

## 2026-05-18:新單草稿持久化 sessionStorage

**選擇**:`/sales/new` 與 `/purchases/new` 自動 debounce 寫 sessionStorage,切到其他分頁回來不會丟資料,儲存成功自動清空,工具列有「清空草稿」鈕。

**理由**:使用者抱怨切分頁會掉資料。sessionStorage 範圍剛好(關掉瀏覽器才丟)。

**未採用**:多分頁同時開新單(像 IDE tab,工程量大,後續可再做)。

## 2026-05-18:自動產生內部 code,UI 隱藏

**選擇**:
- 商品 SKU、電信方案 code、PO/SO no、InvoiceType code、PaymentMethod code 全部系統產生
- 前端**不顯示也不輸入**(僅商品 SKU 顯示在 ComboBox 副資訊與標籤列印)
- PaymentMethod 沒填 code → 後端自動產生 `pm_xxxxxx`(6 字元 hex)

**理由**:使用者只認名稱,不該被迫想代碼。

## 2026-10-02:商品叫法比對 — 從品名拆特徵,各入口共用一支

**選擇**:`apps/identity/product_match.py`。查詢字串與商品品名走同一支 `parse_features()`,拆成三種特徵再比:英數型號(`RENO16`,必須完全相同)、顏色(藍 = 藍色;深藍 / 丁香紫是另一個顏色)、其餘的詞(款式 / 類別 / 品牌 / 規格)。比對結果分 `exact` / `covers`(輸入的都符合,商品另有別的特徵)/ `related`(同機型但有差異)。進貨搜尋、一般 `?search=`、待確認入庫、新增前查重都用它,同一句話在哪個入口問都拿到同一批候選。

**理由**:實測 2,922 筆配件的 `color` / `phone_model` / `style_code` 全是空的,比結構化欄位等於什麼都比不到;舊的逐詞 AND `icontains` 換個寫法就 0 筆(`reno-16`、`側翻藍` 連寫、詞序不同),店員看到找不到就重建品號。同一支函式拆兩邊,拆錯也對稱。

**紀律**:特徵比對只產候選與原因,不替人決定。能直接認定「就是這個」的只有條碼、廠商料號、已確認別名、品號。

**未採用**:靠結構化欄位比(資料是空的);大型模型判斷(`suggest_accessory_models` 實測高信心也會錯);每個入口各寫一套(結果不一致)。

## 2026-10-02:別名分「已確認」與「關鍵字」

**選擇**:`ProductAlias.verified=True` 才有自動對應資格,而且同一作用範圍只能有一筆(含通用別名的條件唯一約束 `uniq_alias_generic`);`verified=False` 是搜尋關鍵字,同一句話可掛多個商品。太籠統(只寫機型 / 類別 / 顏色)、只是品名的一部分、或同時符合多款的叫法,學的時候自動降為關鍵字。已確認的叫法每次命中都重看一次:現在還有別款也符合就退回候選。改指與停用別名限公司管理員。

**理由**:「reno16 藍」在只有側翻款時記成唯一別名,之後進了掀蓋款,同一句話會被舊別名直接帶到側翻款,掀蓋款反而找不到。原本 `supplier` 為 NULL 的通用別名在 PostgreSQL 下唯一鍵擋不住(NULL 彼此不相等)。

## 2026-10-02:停用商品不因選用而恢復

**選擇**:搜尋與候選會列出停用商品(標「已停用」),但選用不會把它啟用。恢復要管理員明確操作(`POST /products/{id}/restore/`、待確認入庫帶 `restore=true`、或編輯商品),一般店員回 403。

**推翻**:先前「人挑了停售商品 = 明確表示要再進貨 → 直接恢復」的做法。

## 2026-10-02:新增商品要過防重複關卡

**選擇**:`apps/identity/dedup.py` 的 `guard_new_product()`,單筆 / 批次 / 型號展開 / 手機型號精靈 / 匯入 / 待確認區建新品 / 直接打 API 都過同一道。條碼相同、或品名整句是別的商品已確認的叫法 → 硬擋(409 `kind=identifier`)。特徵看起來同一款(兩個方向都看)→ 要寫下哪裡不同才能建(409 `kind=similar`,帶 `distinct_reason` 重送),理由存 `ProductDistinctDecision`。批次每列各自說明;匯入不替人決定,列進略過清單。

**理由**:只做在畫面上的話,換個入口或直接打 API 就繞過去了。名稱相似不等於同一個實物(不同材質 / 品牌 / 包裝),所以不強制合併,但不能只按一個沒有理由的忽略鈕。

**未做**:改既有商品品名(PATCH)不過關卡;商品條碼沒有資料庫唯一約束(用 advisory lock 序列化建檔);管理指令與系統自建虛擬商品不過關卡。

## 2026-10-02:公司備份 — 自訂的公司範圍可攜封裝,不用 pg_dump

**選擇**:`apps/backup/`。一次備份 = 一家公司(tenant)全部門市的資料 + 附件,匯出成 zip(每張表一個 jsonl + manifest + 附件),再用加密外殼包起來(`.mppos-backup`)。匯出在一個 `REPEATABLE READ` 唯讀交易裡完成。哪些表要進備份由 `registry.py` **逐張登記**,沒登記的表存在時備份拒絕執行。

**理由**:多家公司共用一個資料庫,`pg_dump` 是整庫工具,切不出單一公司;把整庫產物交給單一店家會把別家資料一起給出去。只掃「有 tenant 欄位的表」會在新增表時靜默漏掉,漏備份要到還原那天才發現。

**未採用**:`pg_dump` + 表名篩選(做不到列層級隔離);每家公司一個資料庫(要重建整套隔離,超出 MVP);讓使用者上傳 SQL 直接執行(不可能安全)。

## 2026-10-02:備份加密與復原憑證

**選擇**:每家公司一組伺服器產生的復原憑證(160 bits,寫成 `MP-XXXX-…`),管理員抄下來跟硬碟分開保管;伺服器存的是用 `SECRET_KEY` 包過的密文,平常備份不用每次輸入。檔案用 HKDF-SHA256 導出金鑰、AES-256-GCM 分塊加密(STREAM 做法),都出自 `cryptography` 套件。

**理由**:備份含會員與維修資料,硬碟遺失不能等於資料外洩;原伺服器壞掉時備份仍要打得開,所以憑證不能只存在伺服器上。伺服器留一份(包過的)是為了讓「按一下就備份」與日後的無人值守備份可行。

**取捨**:伺服器資料庫外洩時憑證也會外洩 —— 但那時資料本身已經外洩了;憑證要防的是「硬碟離開店家之後」。換掉 `SECRET_KEY` 後伺服器讀不出憑證,要管理員重新輸入。

## 2026-10-02:還原 — 整家公司、照搬帳本、新主鍵、號碼只往前

**選擇**:還原單位是整家公司。流程:上傳 → 預檢(不改資料)→ 輸入「還原」確認(**確認當下就上維護鎖**)→ 等寬限時間 → 還原前安全備份 → 在**一個交易**裡:鎖住公司那一列、再比一次資料指紋、刪掉該公司資料、照備份寫回(每列給新主鍵、外鍵照對照表換)→ 逐列核對 → 解鎖 → 提交。工作標成「已完成」、解鎖與資料取代在同一個交易,所以不會有半套,也不會留下解不開的鎖。

- **不重播交易**:庫存餘額、異動、付款、成本快照原樣寫回,不呼叫進貨 / 銷貨的過帳程式。
- **不採信檔案裡的數字 id 與公司 id**:寫到哪家公司由「誰在還原」決定。
- **只能往前的號碼**(客戶 / 會員 / 品號流水、發票字軌、單號)取現況與備份較大者;單號另外用 `DocNumberFloor` 記下已用過的最大號(`apps/core/numbering.py`)。
- **帳號不還原**:沿用現有帳號與密碼;單據的經手帳號用 `UserProfile.account_uuid` 對回「現在還在這家公司的同一個人」,對不回來留空。不用帳號名稱(會改、會被別人拿去用)也不用數字 id(換伺服器就不同)。帳號綁的門市用門市代碼對回新的那一筆,對不回來就留空且維持鎖定。
- **版本要完全相同**(比對每個 app 全部已套用的 migration)才還原,不猜跨版本欄位。
- **寫入屏障分三層**:(1) 維護鎖擋所有經過網頁的請求 —— 一般 API 在登入驗證擋、平台後台照實際要改的那一筆擋、Django 管理後台在任何公司還原時只能看;(2) 上鎖後等滿寬限時間(比網頁伺服器的請求逾時長),上鎖前放行的請求不是做完就是被砍掉;(3) 取代資料的交易對公司那一列下 `FOR UPDATE`,每一筆公司資料新增時資料庫都會對那一列上共享鎖,所以任何來源的新增都要等還原提交。不經過網頁、只修改既有列的管理指令不在這三層內,列為操作限制。
- **「還原有沒有在跑」看鎖不看時間**:worker 執行時握著 PostgreSQL 的 session 層級 advisory lock,行程一死就放掉。只用時間租約的話,跑得久的還原會被誤判成中斷、管理員可能在它還在跑的時候解除維護。

**理由**:共用資料庫下主鍵序列是各公司共用的,不能把備份裡的舊 id 寫回去;單店回溯會讓跨店共用的商品 / 成本 / 調撥失去一致。

**未做**:跨版本還原;單一門市回溯;跨公司合併;固定設備自動備份。


## 2026-10-04:舊系統資料 — 原文不改、對照另一層、只供查詢

**選擇**:`apps/legacy/`。舊 POS(歐睿)十年會員消費封存照原文匯入(會員 / 快照 / 單據 / 版本 /
明細 / 待核),另建「舊店名 / 舊品號 / 舊業務員 / 舊會員 → MP 門市 / 商品 / 業務員 / 會員」的對照表,
由人確認。明細透過不佔欄位的 ForeignObject(公司 + 來源系統 + 原文代號)串到對照,查詢時才連起來。

**理由**:
- 十年資料要能跟新系統一起出報表(門市、品類、業務員、會員),但舊代號跟 MP 的編碼邏輯完全不同,

- 品號對照是庫存搬家與十年報表共用的地基,做一次兩邊用。
- 「電話相同就自動歸戶」會把舊單掛錯人;一律只出候選、人確認、留紀錄。
- 匯入是查詢用資料,不能觸發任何營運副作用;來源金額有差異的另存待核,不混進已核對合計。

**未採用**:擴充既有 `LegacyPurchase`(必須關聯現有商品、數量只收正整數、金額用數量 × 單價重算,

## 2026-10-04:帳本補強 — 每行存未稅 / 稅額、銷退存沖回成本、每日庫存快照與對帳

**選擇**:
- 銷貨 / 銷退明細在存檔當下存死 `untaxed_amount` / `tax_amount`(零頭補在金額最大那一行,
  整單加總正好等於單頭);銷退明細另存 `cost_at_post`(沖回成本:序號 = 退回那幾台的進貨成本,
  配件 = 原行成本按數量比例,最後一次退用餘數,分幾次退完加總等於原行成本)。既有資料用 migration 回填。
- `apps/ledger/`:每天收店後(預設 23:30,`LEDGER_DAILY_AT`)由已常駐的備份背景程式順便拍
  「每日庫存快照」再跑「每日對帳」,結果存表,管理員在「設定 → 每日對帳」看。

**理由**:
- 毛利原本是報表畫面拿金額除以 1.05 回推;稅別規則一改,舊報表數字就變,而且不同畫面可能算法不同。
  存死之後「未稅金額」只有一個答案,之後的語意層 / 自然語言查詢都從這裡取。
- 銷退原本不記成本,毛利報表沒辦法扣回退貨的成本。
- 過去某一天的庫存金額事後倒推不準(成本會被之後的進貨改掉),只能每天記。漏拍的那天不補,只提醒。
- 不新增常駐程式:沿用已在 mini 上常駐的備份背景程式,部署後就會自動開始。

- 既有銷退的沖回成本:舊資料當初沒算過、也沒有作廢時間,不假裝重播當時的存檔;改用固定規則回填
  (目前有效的銷退把一行全部退完時加總 = 原行成本,作廢的只按比例)。
- 每天「拍過了沒」記在 `StockSnapshotDay`(零庫存也有一列);對帳若早於當天的還原就重做;
  同一家公司的快照 / 對帳用 advisory lock 一次只做一個。

**未採用**:另開一支排程(要再設一個常駐項目);快照漏拍時用異動倒推補拍(成本不準,寧可留空);
對帳發現不一致時自動修正(對帳只負責講出來,修正要人決定)。

## 2026-10-04:銷退只能整張退

**選擇**:一張銷退 = 原銷貨單整張退回(每一行、全部數量、每一台)。明細由系統照原單帶入,
畫面不再勾選要退哪幾行。退款 = 原單實收總額。一張銷貨單同時只能有一張有效的銷退。

**理由**:
- 原本可以只退一部分,退款用「數量 × 單價」重算;原行有打折時會退得比實收多。整張退之後,
  退款一定等於當初收的錢,沒有分攤問題。
- 店頭實際作法:要換貨就整張退掉再重開一張。規則單純,帳也單純(毛利、成本一進一出完全對沖)。
- 部分退的分攤(金額、稅額、成本的零頭)全部不需要了。

**未採用**:保留部分退、退款改按實收比例分攤(規則複雜,零頭要再處理一次)。
舊資料裡已經存在的部分退貨不動。

## 2026-10-04:跨公司防護做成共用規則

**選擇**:所有給公司用的序列化器一律掛 `TenantScopedRelatedFieldsMixin`(外鍵欄位只認
`request.tenant`);有門市鎖的建單一律呼叫 `check_create_warehouse()`;兩者各有一支測試掃全系統,
新功能漏掉會紅。過帳邏輯(銷貨、銷退、進貨、調撥、維修完工)再用 `same_company()` 核對一次。

**理由**:DRF 的外鍵欄位預設接受整張表的編號;多家公司共用資料庫時,猜到別家的編號就能把別家的
門市 / 商品 / 序號掛進自己的單,甚至改到別家的庫存。逐支補會漏,所以做成「預設安全 + 測試把關」。

另外三條「不靠送編號也看得到別家」的路一起關掉:
- API 只回 JSON:DRF 內建的 API 瀏覽頁會把篩選與表單的下拉選單整張表列出來(所有公司的客戶、
  供應商、序號)。唯一的畫面是前端,瀏覽頁不需要。
- 外鍵篩選的來源限縮到自己公司(別家編號與不存在的編號同樣回 400,不能拿來試探)。
- 沒綁公司的帳號:只有平台管理員與 superuser 可以指定要看哪一家;其他一律在登入驗證擋下
  (原本任何沒綁公司的帳號都能用 `?tenant=` 切到任何一家,或落到預設公司)。

**未採用**:只在 service 層檢查(欄位仍會接受別家編號,錯誤訊息晚、也容易漏掉沒有 service 的簡單單據)。

## 2026-10-04:改庫存一律「先鎖再檢查、再改」

**選擇**:`apps/inventory/locking.py` 定一套共用規則,銷貨、銷退、進貨、調撥、維修全部照做:
先鎖單據自己那一列並重讀 → 照固定順序鎖這張單會動到的商品 / 序號 / SIM 卡 / 庫存餘額 → 鎖完才檢查、才改。
全部在同一個交易內。

**理由**:庫存數量、序號狀態、單據狀態都是「讀出來 → 判斷 → 存回去」。兩個人同一瞬間動到同一個東西時,
不先鎖就會各自讀到同一個舊值:同一支 IMEI 被賣兩次、庫存少算一次、同一張調撥被確認兩次(庫存加兩次)、
同一張進貨被作廢兩次。平常店裡不容易同時按,但一旦發生,帳就永遠錯下去,只能靠每日對帳事後發現。
- 上鎖順序固定(單據 → 商品 → 序號 → 卡 → 餘額,各照編號):明細順序相反的兩張單才不會互相等到死結。
- 商品 / 序號 / 卡用不擋外鍵的鎖:別張單只是新增一列指到它時不用等。

維修完工原本沒有包在交易裡,缺料時庫存只扣到 0、異動卻記全部數量(重開又加回全部,等於憑空多出庫存)。
改成:領用照實記全部,帳上不夠的差額另記一筆盤點調整入庫 —— 行為不變(缺料仍可完工),但帳對得起來、看得到。

維修單另外補上入口限制(原本一般的修改就能把狀態改成「已完成」而不扣料、完工後還能改門市與零件、
作廢與完工互不相干):狀態唯讀,只有完工 / 重開會動庫存;已完工或已作廢的單不能改;重開依異動紀錄
歸還實際領出去的零件。規則跟畫面原本的行為一致(已完工的單畫面本來就鎖住,只有管理員能重開)。

**未採用**:用資料庫的原子加減(`F("qty") + n`)取代上鎖(加權平均成本要先讀再算,而且「夠不夠扣」的檢查
仍然需要鎖);缺料時直接擋下不給完工(會改變現場流程,帳上數量常常落後現場)。

## 2026-10-04:報表只有一套定義(指標 × 角度),不再一張報表寫一次

**選擇**:`apps/analytics/catalog.py` 是指標與角度的唯一定義;報表畫面(報表 → 自由組合)與之後的自然語言
都只能送「查詢單」(要哪些指標、怎麼分組、期間、條件、要不要比較),由 `engine.py` 照定義驗證、查詢、合併。
新的報表需求 = 在定義裡加一個指標或一個角度,不是寫新的報表頁或新的查詢。

**理由**:每張報表各寫各的查詢,同一個「毛利」在不同頁面會算出不同數字,而且每個新需求都要開發者動手。
把「怎麼算」收在一個地方之後,組合由使用者自己選;AI 也只能產生同一種查詢單,翻譯錯了會被驗證擋下,
不會產生錯的數字,也碰不到資料庫指令。

幾個寫死在定義裡的規則:
- 「銷售」類指標只算**計入毛利**的明細。收購二手那一類(只算現金、不算毛利)不是營收,另外一欄
  (不計毛利金額)看。這樣 銷售額 − 成本 = 毛利 是同一批明細,三個數字對得起來。
- 毛利有兩種:銷貨毛利(未扣銷退,對得上銷貨日報)與毛利(扣銷退)。銷退記在退的那一天。
- 庫存不能跨日加總:一段期間的庫存 = 期間內最後一次快照;按月看就是每個月最後一次。
  「最後一次是哪一天」看的是那天有沒有拍過快照(`StockSnapshotDay`),跟條件無關:數量是 0 的商品在快照裡
  沒有明細,如果用「篩完之後還有明細的最後一天」去找,賣到歸零的東西會一直報最後一次有貨的數量。
- 一個指標背後有好幾張事實表時(淨銷售額 = 銷貨 − 銷退),條件與分組要每一張都支援才能用;
  不支援就明講(例如「收款」不能按商品分),不默默給 0。
- 舊 POS 只用跟封存核對過的金額(原始額 / 淨額)。舊系統的「未稅額」欄位多數等於金額、少數是金額 ÷ 1.05,
  退貨類又自帶負號,語意不一致,不採用。門市 / 商品 / 業務員沒有人確認過對照的,歸「未對照」。
- 合計另外算,不是把列加起來:不受筆數上限影響,銷貨單數也不會因為按商品分而重複算。
- 代碼型的角度(付款方式、課稅別…)條件只接受列得出來的代碼;清單是空的就是全部不接受,不是不檢查。
  付款方式主檔可以刪,但收款 / 退款的單據上還留著當時的代碼,所以可選的代碼 = 現在的主檔 + 單據上用過的
  (主檔已刪的顯示「代碼(已刪除)」)。只看主檔的話,刪掉一個用過的付款方式,那些錢就篩不到、存好的報表也打不開。

存起來的報表,條件存的是那筆資料的**代碼**(門市代碼、品號…),不是資料編號:還原備份後每一列都換新編號,
照編號存會查錯對象而且看不出來。打開時換回現在的編號;代碼找不到(資料被刪、付款方式沒用過就刪掉)就把那個值拿掉並講出來,
不悄悄變成「全部」。內容形狀不對的(條件那一欄不是物件、值是空清單)整份標成壞掉,不當成「沒有條件」。

**權限**:目前不鎖(2026-10-04 決定):店員也看得到全公司與毛利。每個指標的定義留了「誰看得到」,
之後要鎖填那一欄,不用改報表。
存起來的報表預設只有自己看得到,管理員也看不到別人私下存的;要全公司共用由管理員自己存一份並勾共用。
共用的報表能不能改,看的是**現在**是不是管理員,不是看當初是誰存的。

**進貨金額**用的是記進庫存的成本(未稅單位成本 × 數量),跟庫存金額、加權平均成本同一個數字。
單位成本存到分,有贈品或除不盡時,跟進貨單頭的未稅小計可能差幾分錢。之後要完全一致,
進貨明細要像銷貨一樣把每行未稅金額存死(後續追蹤)。

**未採用**:讓 AI 直接寫資料庫查詢(數字沒有唯一定義、會讀到別家公司或個資、錯了看不出來);
買現成的 BI 工具接資料庫(同樣沒有唯一定義,權限與公司隔離要另外再做一次)。

## 2026-10-04:一台設備兩個碼(IMEI / SN),刷哪一個都是同一台

**背景**:手機有 IMEI,有些店家(與沒有 IMEI 的平板 / 手錶 / 耳機)記的是 SN。原本每台只有一個 `serial_no`,
入庫時只能擇一,之後拿另一個碼刷不到。

**選擇**:
- 每台可以登記 IMEI、SN 兩個碼:可以都有,也可以只有一個。`serial_no` 留著當**主碼**(有 IMEI 用 IMEI,沒有才用 SN),
  標籤、單據、所有既有程式照舊讀它,不用跟著改。
- 兩個碼各存一列在既有的 `ProductSerialIdentifier`(原本只有拍照入庫在用)。**同一家公司裡一個碼只屬於一台**,
  IMEI 與 SN 一起比(一台的 SN 不能等於另一台的 IMEI),比對前去掉空白 / 破折號 / 點、轉大寫。
  資料庫的唯一限制在識別碼表上,所以「每一台都有登記」是前提:新增設備只有 `create_serial()` 一個入口
  (測試掃全專案),既有設備由 migration 補登記,漏掉的由每日對帳講出來。
- 沒講是哪一種的單一個碼(舊格式、匯入、拍照入庫的主序號):15 碼數字且檢查碼(Luhn)正確的當 IMEI,其餘當 SN。
  畫面上明講放哪一格的就照放;IMEI 檢查碼不對**只提醒、不擋**(有些設備的碼本來就不合規)。
- 進貨頁每台兩格,刷條碼自動分格(`frontend/src/lib/deviceCodes.ts` 的 `routeCodes`,有測試)。
  手機盒上通常有 IMEI、IMEI2、SN 三個條碼,IMEI2 也是檢查碼正確的 15 碼,**光看碼分不出「下一台的 IMEI」
  還是「同一台的 IMEI2」**。原本想做成不用設定(每個碼放到往下第一個空格),紅隊指出同一支手機連刷
  IMEI、IMEI2、SN 會被拆成兩筆庫存而且存得進去。所以改成序號側欄一個開關「每台刷 IMEI 與 SN」(記在瀏覽器):
  關 = 一個碼就是一台;開 = 先把這一台補齊,這一台已有 IMEI、還缺 SN 時再刷到 IMEI 就不放並提示。
  刷在種類不對的那一格會還原原本的內容;游標當下就移到下一個空格;條碼槍結尾送 Enter 或 Tab 都一樣。
- 銷貨掃碼只在「碼完全相同、整家公司剛好一台、在庫、在這個出貨倉」時自動掛那一台。對到兩台以上
  (舊資料去掉符號後撞在一起)擋下來;那一台已賣出或在別的門市就講出它在哪,不加一行空的讓人挑同款別台。
  下拉用的「包含」比對不拿來自動掛:同商品另一台的碼剛好包含這串字時會賣錯實機。
- 用碼找設備:序號搜尋(挑序號的下拉、庫存查詢)比對每一個碼,可以打末幾碼;商品搜尋只收**完全相同**的碼
  (避免「18 pro 256」誤中含 18 的 IMEI 那一類問題),刷到的那一台的商品排最前面。
- 事後補登 / 修改:空的那一格誰都可以補;已經登記的碼只有管理員能改;作廢的設備不能改;
  鎖在自己門市的帳號只能動自己門市的。每次改動留一筆 `ProductSerialCodeChange`(誰、何時、從什麼改成什麼)。
  改碼等於改這一台「是哪一台」,沒有紀錄的話換機查不出來。

**未採用**:
- 在 `ProductSerial` 上加 `imei` / `sn` 兩欄:要在兩個欄位之間互相擋重複,資料庫做不到一個唯一限制管兩欄;
  而且識別碼表已經存在(拍照入庫用),兩套並存會對不起來。
- 把 `serial_no` 改成正規化後的值:既有資料、單據快照、測試都用原文,改了會對不起來;正規化只用在比對。

**不做**(owner 2026-10-04 決定):雙卡機第二組 IMEI 的一般入庫。一台就記 IMEI 與 SN 兩個碼;開著「每台刷 IMEI 與 SN」時刷到 IMEI2 會擋下不放。
(識別碼表有 IMEI2 的位置,拍照入庫原本就會存,那部分照舊。)

**還沒做**:調撥 / 銷貨單據上同時印兩個碼。

**作廢的設備不佔碼**(owner 2026-10-04 決定):進貨單打錯整張作廢重開是常見情境,以前 `serial_no` 在公司內唯一、
不看狀態,作廢過的碼永遠不能再入庫。現在作廢進貨單時把那幾台登記的碼釋放(`release_codes()`),`serial_no` 的唯一限制改成
不算作廢的(migration 0014,既有作廢設備的登記一併拿掉)。作廢的那一筆留著 `serial_no` 當紀錄:用關鍵字查序號清單還看得到(狀態是作廢),
但用碼找設備(刷條碼)不會找到它,所以重新入庫之後刷同一個碼只會對到現在那一台。

**主碼多存一份去掉符號後的值(`ProductSerial.serial_key`)**:主碼 `serial_no` 存原文,以前比對主碼只能拿輸入的幾種寫法
(原文 / 大小寫 / 去符號)去碰,舊設備當初寫成 `AB--12` 這種就比不到 —— 這個洞在複審被不同模型以不同樣子指出好幾次
(擋不住重複、刷條碼只找到其中一台、釋放作廢的碼時連在用那一台的保護一起拿掉)。改成每台存 `serial_key`(存檔時自動算),
找設備與檢查重複都比這一欄,不再猜寫法。沒有在這一欄上加唯一限制:舊資料可能有兩台在用的設備碼相同,加了升級會失敗;
這種資料用碼找會兩台都回來(畫面不自動挑),每日對帳會列出來。

**釋放時的接手**:釋放的碼如果還有一台在用的設備(主碼去掉符號後相同)沒登記到,碼改登記給最舊的那一台。
作廢一開始就把「這張單的設備」和「可能接手的設備」(`twin_ids()`)交給 `lock_stock_rows` 照編號順序一次鎖住,
在改任何設備之前(兩張作廢單的設備互為對方的接手者時才不會互相等到死結);鎖住之後才看現況:
碼還登記在別台身上就不交接,沒有人登記才交給最舊的那一台。

**複審**(作廢釋放 + `serial_key`):紅隊 1 輪(Grok)+ Codex 3 輪,第三輪結論「可以上線」(無 P0 / P1)。
後續追蹤(不急):`release_codes()` 的前提(同一家公司、都已作廢、呼叫端已鎖)只寫在說明裡,函式本身沒有檢查,
現在唯一的呼叫點符合;migration 0014 一次把全部識別碼讀進記憶體、一次寫入,資料量大的環境要改成分批。

**複審**(雙序號 + 整張調撥一起審):紅隊兩輪(deepseek、Grok)+ Codex 三輪。第三輪沒有 P0,但還有 3 項 P1,結論仍是「不可上線」。
其中兩項已修(掃到某一台之後只能加那一台、商品不能賣就講;畫面上是哪一個碼的順序固定 + 拍照入庫同一台同一種碼只能一個),
**這兩項修正沒有再送審**。第三項(批次貼上沒貼序號也要擋)沒有照改:批次貼上可以只帶商品與數量、序號回主畫面再刷,
沒刷齊存檔時本來就會擋。
owner 要求加審第四輪:第三輪五項全部確認處理好,沒有 P0;新提 1 項 P1(以前拍照入庫、SN 被標成主碼的設備,升級後主碼沒換成 IMEI)
→ 加 migration `0013_main_code_prefers_imei`(正式機沒有這種資料,會是空跑;隔離測試庫跑過,46 台沒有變動)。**這支 migration 沒有再送審**。

**後續追蹤(不急)**:
- 前端的分格測試(`npm test`)要 Node 22.6 以上才跑得起來;Mac mini 是 Node 20,只影響跑測試,不影響建置與部署。
- 銷貨下拉手打「只對到一部分」的自動掛,只看查回來的前 10 筆;選項上會寫出那一台的碼,由人挑。
- 整張調撥帶好之後可以把配件數量改得比這張進貨單多(照一般調撥檢查庫存),不會再提醒多的是別批的貨。

## 2026-10-04:整張進貨單一次調撥到分店

**背景**:總部進貨後要把整批貨調到分店,原本要在調撥單逐筆挑商品、逐台挑序號。

**選擇**:進貨單頁「整張調撥」→ 開一張已經帶好內容的調撥單,選目的倉就能派發。之後完全照既有調撥
(派發 → 目的倉確認 → 可作廢),沒有新的庫存異動路徑。
- 帶出來的內容由 `GET /purchase-orders/{id}/transferable/` 算(只讀):序號商品只列這張單進來、現在還在進貨門市且在庫的;
  已賣 / 已調走 / 已退 / 作廢的不帶,並在畫面上講出來是哪幾台。配件不分批,數量 = 這張單進的數量但不超過進貨門市現有庫存。
- 它只是「建議的內容」。帶出來到按下派發之間東西可能被賣掉,真正能不能調由調撥存檔時鎖住庫存再檢查(既有規則)。

**未採用**:按一下就直接建立調撥單(不經過調撥單頁)。少一個畫面,但使用者看不到哪些被略過,也不能先拿掉某一行;
而且會多一條建立調撥單的路徑,要另外維護一次權限與鎖。

## 2026-10-05:工作台版型 — 調撥、庫存查詢改成「一個畫面、掃一下加一行」

**背景**:owner 在舊系統上自己做的瀏覽器套件(Ored 快速工作台)用了一段時間,明講比較習慣那個介面。
跟原本錄入頁的差別:原本是「清單頁 → 按新增 → 另一頁 → 按新增明細 → 在那一行裡找商品 → 序號到右邊側欄逐格挑」;
套件是「一進來就是空白單、游標在掃碼框、掃一下加一行(新的在最上面)、序號列成小標籤直接點」。

**選擇**:加第四種版型「工作台」,先用在調撥與庫存查詢;進貨、銷貨之後照同一套改。**只換畫面,後端規則一行都沒動。**
- 共用零件在 `frontend/src/components/workbench/`:`ScanBox`(掃碼框)、`toast`(畫面下方的訊息條,可帶「復原」)、
  `ArmButton`(兩段式按鈕)、`errors`;樣式全部收在 `styles.css` 的 `.wb` 底下,不影響其他頁,日 / 夜間模式各一組顏色。
- **不開彈出視窗**:要確認的動作(入庫、作廢)第一次按只換字成「再按一次」,4 秒內再按才真的做;
  移除一行、清空明細不問,改成訊息條上給「復原」。清空之後又掃了新的,復原就不動(不拿舊的蓋掉新的)。
- 掃碼框一格同時收條碼與手打品名。條碼槍打得比搜尋快:按下 Enter 當下輸入框就清空,刷進來的碼排隊一個一個處理,不會漏也不會黏在一起。
  **只有「品號 / 條碼完全相同剛好一筆」才自動加入**;其他的把字放回去、列出來給人挑,不替人猜
  (人看著下拉按 Enter 才是取反白那一筆)。套件原本是一律取第一筆,這裡刻意比較保守:相似度搜尋的第一筆不一定是刷的那個。
- 調撥:刷到設備的碼 → 走 `findDevicesByCode`(完全相同才算);對到兩台以上擋下,不在調出分店 / 不是在庫就講它在哪。
  序號商品把調出分店在庫的每一台列成小標籤(後 6 碼),只有一台就直接選起來。清單、新增、待確認三個畫面併成一頁:
  下面的「最近調撥」點一列展開明細,待入庫的直接在列上按入庫。`/transfers/編號` 會展開那一張。
- 調撥的「直接入庫」(只有不鎖倉的帳號看得到,預設不勾,勾了會記住)= 送出後接著按一次入庫,是原本兩個動作連著做,沒有新的規則。
- 庫存查詢:點一列就地展開每家分店在庫的每一台(原本是點數字跳視窗);點分店、點類別直接重查;常用類別可以釘起來(記在瀏覽器)。

## 2026-10-06:金額一律整數元、四捨五入(顯示、輸入、存檔都是)

**背景**:owner 在維修單看到費用帶兩位小數(1500.00),要求全站金額都是整數、四捨五入。清查後發現不只是顯示:

- 後端的小計 / 稅額 / 總額算到分,而且 `Decimal.quantize` 預設是「四捨六入五成雙」(4.5 → 4),不是四捨五入。
  **應稅外加時總額會出現 115.50**,畫面只收整數,付款 116 對不上、這張單存不進去(小計不是 20 的倍數就會中)。
- 營業日報的加總用 `int()`,是無條件捨去。
- 順帶發現:維修單編輯頁改任何一格都會立刻被存檔的內容蓋回去(載入用的 effect 依賴了每次都是新物件的 `defaultWh`),既有的單在這一頁根本改不了。

**選擇**:
- 規則各一份:後端 `apps/core/money.py`(`round_money` 整數元、`ROUND_HALF_UP`;`money_int` 給報表加總;`money_text` 給訊息),
  前端 `frontend/src/lib/money.ts`(`roundInt` / `money` / `intStr` / `splitTax`)。前端先收到小數六位再進位,
  擋掉 1.255 × 100 = 125.49999999999999 這種差一點點的一半。
- **單據金額存檔就是整數**:明細金額、未稅小計、稅額、含稅總額(銷貨 `_calc_tax`、進貨 `_calc_doc_tax`、每行的未稅 / 稅額、個人收購金額、維修建議報價)。
  含稅:未稅 = 加總 ÷ 1.05 四捨五入、稅額 = 總額 − 未稅;外加:稅額 = 加總 × 5% 四捨五入、總額 = 未稅 + 稅額。跟發票上的算法一樣。
- **成本照舊算到分**(落地成本、加權平均成本、銷貨當下成本):那是平均值,收成整數會越算越偏;只在畫面上顯示成整數。
- **以前存的單不回頭改寫**。`_calc_tax(..., unit=CENTS)` 保留舊算法只用來「認得」舊單:每日對帳走 `matches_tax_rule()`(新舊符合一種就一致),
  `split_tax_by_line` 先看單頭是照哪一套算的、每行就照同一套分。migration 0016 的回填本來就帶一份凍結的舊算法,不受影響。
- 前端:所有金額顯示換成 `money()`(30 幾個檔);金額輸入框換成 `components/MoneyInput`(26 格:小數點打不進去、貼上帶小數的會四捨五入、
  資料庫的 "1500.00" 顯示成 1500、拿掉上下箭頭);表單載入與送出都過 `intStr()`;開單頁的試算改用 `splitTax()`,跟伺服器同一套算法;
  營業日報與自訂分析的 CSV 匯出也是整數。舊系統(歐睿)的金額存的是「分」、原文不改,只有顯示收成整數元。
- 維修單編輯頁的 effect 依賴改成編號 / 名稱,既有的單可以改了。
