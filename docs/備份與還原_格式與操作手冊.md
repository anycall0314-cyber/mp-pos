# 公司備份與還原：格式說明與操作手冊

> 對應 `docs/MP_POS_MVP_商品防重複與多店集中備份_Claude開發計畫.md` 第 5–7 節。
> 程式在 `backend/apps/backup/`。本文寫的是「目前程式實際的行為」，不是規劃。

## 1. 一句話

一次備份＝**一家公司全部門市的資料＋附件**，包成一個加密檔（`.mppos-backup`），由公司管理員下載到自己保管的硬碟；之後可以用它把整家公司還原回那個時間點，或在原伺服器不能用時，在另一台相容的系統上把公司建回來。

還原單位是整家公司。不提供只回溯某一家門市——商品、成本、調撥是跨店共用的，只回一家店帳會對不起來。

## 2. 誰可以做什麼

| 動作 | 誰 |
|---|---|
| 備份、下載、驗證本機檔案、上傳還原、確認還原、看憑證 | 這家公司的**管理員**（`tenant_admin`） |
| 以上任何一項 | 一般店員：不行 |
| 以上任何一項 | 平台管理員：不行（不能因為平台角色就從一般網址跨進別家公司）。平台維運走主機上的管理指令 |
| 新環境復原（把公司建到一台新伺服器） | 主機上的維運人員，用管理指令 |

每一次查工作、下載、驗證、還原，後端都重新檢查身分與公司；別家公司的工作編號猜中了也只會得到「找不到」。

## 3. 店家操作流程

### 3.1 第一次：產生復原憑證

設定 → 備份與還原 → 「產生憑證」。畫面會顯示一組 `MP-XXXX-XXXX-…`（8 組 4 碼）。

- **抄下來，跟硬碟分開放**（例如硬碟放店裡、憑證放家裡）。
- 伺服器壞掉時，只有這組憑證能解開備份。弄丟憑證＋伺服器也壞了＝備份打不開。
- 之後還能在同一頁按「再看一次」（每看一次都會留紀錄）。

### 3.2 備份

1. 接上硬碟，用任何一台電腦登入（Windows／macOS 的瀏覽器都可以，不用裝任何東西、不綁哪一台）。
2. 設定 → 備份與還原，確認「包含門市」列出全部門市。
3. 按「備份全部門市」。可以離開這一頁、關掉瀏覽器、換一台電腦，工作會繼續。
4. 狀態變成「已驗證，可下載」後按「下載檔案」，存到硬碟。
5. 按「驗證檔案」，重新選取剛剛存到硬碟的那個檔。出現「已驗證本機檔案」才代表硬碟上那份是完整的。

狀態的意思（照實寫，不冒充成功）：

| 畫面上的狀態 | 意思 |
|---|---|
| 排隊中／產生中 | 伺服器正在做，還沒有可用的檔案 |
| 已驗證，可下載 | 伺服器上的檔案封裝好、再解開核對過，而且**通過跟還原時同一套檢查**（這份檔現在拿去還原，檢查會過） |
| 已開始下載 | 伺服器回應過下載請求。**不能證明**檔案已經寫進硬碟 |
| 已驗證本機檔案 | 使用者重新選取檔案，內容與伺服器那份完全相同 |
| 失敗 | 沒有產生檔案，原因寫在下面（例如附件遺失） |
| 已過期 | 伺服器上那份已清掉（預設 72 小時）。店家已下載的檔案不受影響，仍可驗證 |

### 3.3 回到較早的備份（既有公司回溯）

1. 設定 → 備份與還原 → 還原區選檔 →「上傳檢查」。**這一步不會改任何資料。**
2. 畫面顯示：備份來源公司、備份時間、包含門市、資料筆數，以及「會被取代」的範圍，還有注意事項（例如哪些帳號的門市對不回來）。
3. 輸入「還原」兩個字，按「確認還原」。**按下去的那一刻全公司就暫停操作**（不是等背景程式接手才鎖）。
4. 還沒開始執行前可以按「取消還原」，取消就解鎖，資料沒有動。
5. 系統依序：等一小段時間（預設 75 秒，讓上鎖前一刻送出的操作做完）→ **先把現況完整備份一份（還原前安全備份）** → 擋住這家公司所有新增資料的動作 → 再確認一次「從按下確認到現在資料沒有變」→ 整批取代 → 逐列核對、附件寫回後讀回來核對 → 解鎖。
6. 完成後狀態為「已完成」。還原前安全備份會留在同一頁，可以下載。

還原之後：

- 單據、庫存、序號、成本、付款、調撥、別名、附件都回到備份那個時間點。
- **號碼只會往前**：備份之後開過的銷貨單／進貨單號碼、發票字軌、客戶／會員／品號流水不會被重用。備份之後才申請的發票字軌會照現況留著（連同已經開到第幾號）。還原前各種號碼用到哪裡，記在那一次還原的紀錄裡。
- 帳號與密碼不動（沿用現在的）。舊單據的經手帳號照「帳號識別碼」對回原本那個人——不看帳號名稱，所以備份之後有人改了名稱、名稱又被別人拿去用，也不會掛錯人。已經不在這家公司的帳號對不回來，那一欄留空，預檢時會列出來。備份之後才新增、綁在「備份裡沒有的門市」的店員，會變成沒有門市可用（仍然鎖著，不會變成能看全部），要管理員重新指定。
- 每一筆資料的內部編號都換新。還原前開著沒存的畫面（進貨單草稿等）請重新整理。

### 3.4 出問題時

| 情況 | 系統怎麼處理 |
|---|---|
| 憑證不對、檔案壞了、沒下載完、被改過 | 上傳檢查階段就拒絕，資料沒有任何變動 |
| 拿別家公司的備份 | 拒絕 |
| 備份是不同版本的系統產生的 | 拒絕（見第 6 節限制） |
| 檔案裡有寫不進去的值、重複的編號、多出來或少掉的附件、清單形狀不對 | 上傳檢查階段就拒絕（不會等到鎖了公司才失敗） |
| 預檢之後、確認之前有人又開了單 | 要求重新上傳檢查 |
| 確認之後資料還是變了（例如有人在主機上跑管理指令） | 不還原，資料不動，自動解鎖 |
| 別的作業卡著不放，等超過 60 秒 | 不還原，資料不動，自動解鎖；稍後再試 |
| 還原前安全備份做不出來 | 停止，不還原 |
| 還原途中任何錯誤 | 整批不算數，資料維持還原前的樣子；自動解鎖 |
| 還原途中伺服器被關掉 | 資料維持還原前的樣子，但**不會自動解鎖**；管理員到備份頁看過說明後按「解除維護」 |
| 還原跑很久 | 只要背景程式還活著就不會被當成中斷，也不能被解除維護 |
| 上傳檢查後沒有按確認就離開 | 30 分鐘後自動取消，暫存檔由背景程式清掉 |
| 上傳到一半斷線、伺服器磁碟滿了 | 留一筆「沒收成」的紀錄，半個檔不留 |
| 還原期間平台管理員想從平台後台改這家公司的門市／帳號／公司資料 | 擋下（503）；查看不擋，別家公司不受影響 |
| 還原期間平台管理員沒指定公司就操作一般畫面（系統會讓他落到「預設公司」） | 預設公司正在還原就擋下 |
| 任何一家公司還原期間，有人想從 Django 管理後台（/admin/）改資料 | 擋下（503），只能看；還原結束就恢復 |
| 還原失敗、或中斷後管理員解除維護 | 上傳的那份檔從伺服器刪掉，要再還原請重新上傳 |
| 檔案裡的清單檔或項目數大到不合理 | 上傳檢查階段就拒絕 |

## 4. 新環境復原（原伺服器不能用）

在一台「相同版本」的 MP POS 上，由維運人員執行：

```sh
cd backend
python manage.py restore_company_backup /路徑/備份檔.mppos-backup --code 公司代碼 --admin 復原管理員帳號
```

會提示輸入復原憑證與復原管理員的密碼（不會留在指令紀錄裡）。完成後：

- 公司以備份裡的識別碼建立。同一個識別碼已經在這台伺服器上會被拒絕（那是「既有公司回溯」，要走有安全備份的那條流程）。
- 建立一個復原管理員；備份裡的店員帳號照角色與門市重建，但**沒有密碼**，要管理員逐一重設才能登入。舊的登入狀態不在備份裡，不會復活。帳號名稱已被別人用掉的會加上公司代碼並列出來。
- **發票字軌全部先停用**：這台伺服器不知道備份之後原本那邊又開了幾張。核對後到設定頁啟用。
- 進貨／銷貨／調撥單號會接著備份裡最後一張往下編。備份之後原本那邊如果還開過單，請先確認不會重號。

## 5. 備份檔格式

副檔名 `.mppos-backup`。外層是加密外殼，裡面是一個 zip。

### 5.1 加密外殼（`apps/backup/container.py`）

```
8 bytes   魔術字 "MPPOSBK\x01"
4 bytes   檔頭長度 N（big-endian）
N bytes   檔頭 JSON：container 版本、cipher、kdf、salt、chunk_size、key_fingerprint
重複：    4 bytes 密文長度 ＋ 密文（含 16 bytes 驗證碼）
```

- 金鑰：`HKDF-SHA256(復原憑證, salt)`；每個檔案自己的隨機 salt。
- 內容：`AES-256-GCM`，每 1 MiB 一塊。nonce＝11 bytes 區塊序號＋1 byte「是不是最後一塊」；整段檔頭當 AAD 綁進每一塊。
- 效果：憑證不對、任何一個位元被改、區塊被調換、檔案被截斷、尾巴被接上別的東西，解密都會失敗，而且不會留下半份明文。
- 檔頭只有解密需要的東西。哪一家公司、哪些門市、幾筆資料都在加密的內容裡。
- 演算法都來自 `cryptography` 套件；分塊做法是文獻上的 STREAM（age、Tink 的串流加密同一種）。沒有自己設計演算法。

### 5.2 內容（zip）

| 路徑 | 內容 |
|---|---|
| `manifest.json` | 格式版本、每個 app **全部**已套用的 migration 清單與指紋、備份編號、公司識別碼／名稱／代碼、公司設定與流水號、門市清單、快照時間與時區、資料分類清單、各表筆數、每個附件的大小與雜湊 |
| `accounts.json` | 帳號對照：**只有這家公司自己的帳號**（帳號識別碼、名稱、姓名、角色、預設門市、鎖倉）。**沒有密碼、沒有登入 token**。平台管理員或別家公司的人經手過的單據，經手帳號那一欄在備份裡是空的，他們的帳號名稱不會出現 |
| `data/<app>.<Model>.jsonl` | 每張表一個檔、每列一行 JSON（原始欄位值；不含公司欄位） |
| `files/<n>` | 附件本體（目前是進貨單原圖） |

不放：資料庫連線字串、主機絕對路徑、平台金鑰、API token、登入 session、其他公司的任何資料、平台管理員帳號、復原憑證本身。

### 5.3 哪些表會進備份

`apps/backup/registry.py` 逐張表登記：公司資料（60 張）／帳號（只留對照）／公司本身那一列／不備份（附理由）。**沒登記的表存在時，備份直接拒絕執行**——新增 model 後跑測試會被擋下來，要到 registry 決定它算哪一類。帶檔案的欄位另外登記在 `FILE_FIELDS`。

### 5.4 同一個時間點

整個匯出在一個 PostgreSQL `REPEATABLE READ` 唯讀交易裡完成，所以備份途中有人開單，備份裡要嘛整張單都在、要嘛整張都不在。附件與資料同一批清單，逐檔複製並核對雜湊；少一個就整個備份失敗。

## 6. 已知限制

- **版本要相同**：備份只能還原到「資料結構完全相同」的系統版本（比對每個 app 全部已套用的 migration，要一模一樣）。系統升級（有 migration）之後，舊備份在新版本會被拒絕。**每次升級後請馬上再備份一次。** 要讓舊備份在新版本可用，需要另外做版本相容處理，目前沒有。
- **背景 worker 要常駐**：備份與還原由 `python manage.py run_backup_worker` 執行。這支沒在跑的話，工作會一直停在「排隊中」。正式環境要另外設定常駐（launchd），這次沒有改動任何系統排程。
- **還原時會擋住這家公司的所有操作**：從按下確認開始，到還原結束（至少 75 秒的等待，加上資料量決定的執行時間）。別家公司不受影響。
- **維護鎖擋的是網頁操作**（一般畫面、平台後台、Django 管理後台都擋）。直接在主機上跑的管理指令（匯入舊資料等）不經過登入，不會被維護鎖擋下；還原執行時它們「新增資料」的動作會被資料庫擋住等還原做完，但**還原期間請不要在主機上跑任何會改這家公司資料的指令**。
- **驗證本機檔案**是瀏覽器一段一段讀檔計算，不吃記憶體、用區網 http 連線也能用；1 GB 的檔大約要十幾秒到一分鐘（看電腦）。
- 還原時被中途強制關機，媒體目錄可能多留幾個沒人用的附件檔（不影響資料正確性，只佔空間）。還原後清舊附件時，如果剛好有人在存進貨單據，這一次就先不清（同樣只是多佔空間）。
- 類別的品號流水、電信商的方案流水：備份之後才新增的類別／電信商在還原後會消失，它們用過的流水號沒有另外保存。
- 沒有：固定設備無人值守自動備份、排程、保留份數管理、遠端提醒（計畫第 8 節，下一階段）。
- 沒有：單一門市回溯、跨公司合併。
- 平台整庫備份（`ops/backup.sh`）是另一回事，給平台維運救災用，不能拿去給單一店家。它的清理規則實際是「刪 30 天前的檔」，跟註解寫的「保留最近 30 份」不一樣，這次沒有改它。

## 7. 給維運的備忘

- 備份檔存放位置：環境變數 `MPPOS_BACKUP_DIR`（預設 `backend/backup_store/`，已加進 `.gitignore`）。**不可**放在 `media/` 或任何會被網頁伺服器直接送出的目錄。
- 伺服器上的備份檔保留時數：`MPPOS_BACKUP_RETENTION_HOURS`（預設 72）。還原前安全備份不自動清。
- 還原上鎖後的等待秒數：`MPPOS_BACKUP_RESTORE_GRACE_SECONDS`（預設 75）。**要比網頁伺服器的請求逾時長**（gunicorn 目前 60 秒）；調高 gunicorn 逾時的話這個也要跟著調。
- 啟動時會檢查備份目錄沒有跟 `MEDIA_ROOT`／`STATIC_ROOT` 重疊，重疊就拒絕啟動（`backup.E002`）。
- 背景程式每一輪會順手收拾：結束了卻沒解開的維護鎖、過期的預檢、暫存區超過一天的孤兒檔。
- 復原憑證一旦產生就不能從網頁換成另一組（系統金鑰換過、伺服器讀不出來時，只能重新輸入**原本那一組**）。認的是憑證的完整雜湊，不是畫面上那 8 碼核對碼。真的要換，要由維運處理。
- 新環境復原時帳號名稱被用掉：加上公司代碼；還是被用掉就再加流水（`名稱-代碼-2`…），太長會截掉前段。改了哪些會列出來。
- 復原憑證在資料庫裡是用系統金鑰（`DJANGO_SECRET_KEY`）包過的密文。**換掉 `DJANGO_SECRET_KEY` 之後伺服器會讀不出憑證**，備份與還原會要求管理員重新輸入手上那份。
- 新增套件：`cryptography`（已加進 `requirements.txt`），部署時要 `pip install -r requirements.txt`。
- 新增 migration：`tenants 0016`（公司識別碼、單號下限）、`tenants 0017`（帳號識別碼）、`backup 0001`、`backup 0002`（復原憑證的完整雜湊）。
- `settings` 的 `MIDDLEWARE` 多了 `apps.backup.auth.AdminMaintenanceGuard`（有公司在還原時 Django 管理後台只能看）。
- 新環境復原重建的帳號沿用備份裡的帳號識別碼（這台伺服器上沒人用的話），之後拿更早的備份回溯仍認得出誰是誰。
- 操作紀錄在 `backup_backupauditlog`；它與還原前安全備份都不會被還原蓋掉。
