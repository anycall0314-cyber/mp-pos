## 1. 目標與本次範圍

先提供少數友好店家試用的 MVP，優先解決兩個實際問題：

1. 同一商品因店員命名習慣不同、零庫存或停用而找不到，導致重複建檔。
2. 同一家公司有多家門市，老闆要在單一位置，使用任一可登入的電腦，把全部門市資料備份到自己保管的硬碟，並能還原。

### 1.1 已確認需求

- UI 全繁體中文，不使用裝飾性 emoji；操作以一般店員能理解為準。
- 一個實際商品保留一個商品身分，可以有多個名稱／別名。
- 零庫存不代表未建檔；入庫與新增前防重複查詢必須找得到既有商品。
- 多門市可以集中備份；手動備份不可綁定某一台門市電腦。
- 店家負責保管地端備份媒介，規劃販售搭配備份／還原功能的硬碟。
- 本文件交給 Claude 開發；本次不執行正式資料異動、部署、commit 或 push。

### 1.2 本計畫採用的設計基準

下列是把需求落實的建議方案，不表示目前已具備：

- POS 主資料集中於伺服器，各門市連線操作；先沿用現有 tenant 架構，不為本次 MVP 重建整套資料庫隔離方式。
- 「公司／經營者」對應一個 tenant；「門市」對應該 tenant 旗下 warehouse。
- 一次公司備份包含全部門市及公司共用主檔；還原單位也是整家公司。
- 不同試用店家若屬不同經營者，必須是不同 tenant，各自只能下載自己的資料。
- 第一版必做：商品防重複、任意電腦手動下載完整備份、可驗證的備份還原。
- 下一階段：固定設備無人值守備份、硬碟接收程式與排程；保留介面，不作第一版前置條件。

若實際部署是「各門市各自一個離線資料庫」，須先回報差異與集中收集方案，不能沿用本文件而宣稱已做到全店同一時間點備份。需求仍是集中備份，不應自行改成各店各自處理。

### 1.3 本次不擴張的範圍

- 不開發完整 AI／OCR 商品辨識、跨公司共用商品平台、供應商大資料庫。
- 不自動合併歷史重複商品，不重算既有帳本或改變加權平均成本規則。
- 不新增門市離線交易同步、多主資料庫或跨公司資料整併。
- 不把備份檔當成隨插即用的 POS；還原仍須相容的 POS 程式與資料庫環境。
- 不把既有大型文件 `docs/AI助理與智慧入庫_架構修改實作計畫.md` 的所有期程納入此次 MVP；其中已實作或必要的安全邊界仍須沿用。

## 3. 商品防重複：店員流程

### 3.1 必須通過的原始案例

使用者確認以下四種叫法，在此案例指的是同一款商品：

```text
reno16 皮套 藍色
reno-16 側翻皮套 藍
reno16/側翻/藍
reno16/皮套/側翻藍
```

建議標準顯示名稱：`Reno16 側翻皮套／藍`。

| 屬性 | 案例內容 | 備註 |
|---|---|---|
| 適用機型 | Reno16 | 沿用既有機型／相容關係；共用多機型配件仍只有一個商品與庫存 |
| 類別 | 皮套 | 沿用類別主檔 |
| 款式 | 側翻 | 不足以區分款式時再補材質、品牌或款式碼 |
| 顏色 | 藍 | 藍／藍色可作同義詞；深藍／淺藍不能直接消去差異 |

不能把「機型＋類別＋款式＋顏色」直接當成所有商品的唯一鍵。品牌、材質、孔位、磁吸功能、包裝數量等可能代表不同實物；來源供應商不同也不必然代表不同商品。

### 3.2 第一次建檔

1. 店員輸入習慣名稱，系統嘗試帶出機型、類別、款式、顏色。
2. 機型等已存在欄位採選取主檔，避免自由文字再產生一套名稱；只顯示該類商品需要的欄位。
3. 由已確認欄位產生簡潔顯示名稱，原始稱呼保留；未知欄位標示未確認，不補猜測值。
4. 搜尋並展示可能相同的既有商品；真正不同才新增。
5. 不要求先回填全部舊商品，也不自動改名所有歷史商品；舊資料可用別名與名稱候選繼續查找。

### 3.3 之後進貨查找

店員輸入上述任一叫法，都應看到同一既有商品候選，即使本店庫存為 0：

```text
Reno16 側翻皮套／藍
本店庫存：0　已建檔
符合原因：機型、顏色相符／已確認的其他叫法
【選用並入庫】
```

- 有照片、款式、供應商識別碼時，可輔助辨認；不可把新增照片模組列為本次必做。
- 不強迫店員背品號或輸入系統自動產生的代碼。
- 已停用商品另標示「已停用」，可查看並由有權限者恢復；搜尋與入庫選用不能偷偷啟用它。
- 他店庫存、成本與歷史進價僅在原有權限允許時顯示，不能因防重複搜尋而放寬鎖倉權限。

### 3.4 新增前再確認

即使前一次搜尋沒有選到商品，按新增／儲存前仍應檢查：

```text
找到可能相同的商品：Reno16 側翻皮套／藍
本店庫存：0
【就是這個，直接入庫】　【不同款，繼續新增】
```

- 「就是這個」：沿用既有商品；提供「記住這個叫法」的明確確認。
- 「不同款」：補充款式差異或原因，再提交；不能只提供一個無理由的忽略按鈕。
- 完全相同的已確認商品識別碼不得用「不同款」繞過；有疑義先處理識別碼衝突。
- 只有名稱相似時不強制合併，也不永遠禁止建立不同實物。
- 後端儲存時重新檢查；直接 API、批次新增、匯入與智慧入庫建新品不能繞過。

## 4. 商品比對與資料規則

### 4.1 共用辨識，不混淆各作業的可選條件

將名稱正規化、別名與候選排序收斂為共用後端 service；各入口套用自己的作業條件：

| 作業 | 查找範圍 | 選用規則 |
|---|---|---|
| 進貨搜尋／新增防重複 | 同公司完整商品檔，包含零庫存；停用列為可辨認候選 | 啟用商品可入庫；停用須先經授權恢復 |
| 商品管理 | 同公司主檔，依管理篩選 | 依既有管理權限 |
| 銷貨 | 共用名稱／別名辨識 | 保留現行 `sales_pickable`、倉別、序號及實體零庫存不可售規則 |
| 批次貼上／Intake | 共用候選與衝突規則 | 模糊候選須確認，不能自動挑第一筆 |

所有候選按 Product ID 去重，一個商品的多個別名或多機型相容關係不能讓庫存重複計算。

### 4.2 比對順序與判斷

1. 條碼、供應商＋料號、既有已確認別名等可靠識別；多來源互相矛盾時回傳衝突。
2. 已知機型、類別、款式、顏色等結構化特徵；完整且一致的候選優先。
3. 名稱拆詞、同義詞與模糊候選；僅作推薦，不自動合併或建單。
4. 完整條件沒有結果時，退回同機型的相關商品，標明缺少／不同的特徵，不直接讓畫面只剩「新增」。

具體要求：

- 支援大小寫、全半形、空白、斜線與 `Reno-16`／`Reno16` 等已知機型寫法，詞序不影響基本候選召回。
- 支援案例中的連寫「側翻藍」；以可測試的詞典／解析規則處理，不靠大型模型猜測。
- `Reno16 Pro`、其他代數、不同顏色／材質／包裝不得判成同商品；若列作相關候選，要明示差異。
- 「皮套」未寫側翻時視為資訊不足，不把所有皮套自動等同側翻。
- 原始字串保留。名稱正規化不可直接套用到所有條碼、供應商料號並抹去可能有意義的符號。
- 調整既有 `normalized_value` 演算法時，要盤點舊別名碰撞、規劃 migration／相容查詢，不可直接改函式造成原別名失聯。
- 搜尋結果回傳符合原因、停用狀態、可否選用及必要差異；用分頁與合理上限，不下載全表到前端。

### 4.3 記住叫法與衝突處理

- 店內叫法是同 tenant 的別名；供應商特有叫法／料號限定該供應商。
- 學習須有明確的人為確認；只輸入 `reno16`、`皮套`、`藍` 等廣泛搜尋詞，不得直接學成單一商品的唯一別名。
- 若叫法本來就不足以區分多款，只能作候選關鍵字，不能取得下次自動對應資格。
- 同一作用範圍的別名已指向不同商品時，回報衝突；不得 `.first()` 任選或靜默改指。
- 記錄操作者、來源、建立／變更時間；支援停用、修正及查看影響。既有錯誤對應不應改寫已完成單據。
- Product／supplier 外鍵必須屬於授權 tenant；建立、確認、改指與停用都有後端權限檢查。
- 一般店員的確認能力依既有建檔／入庫授權政策；改指既有別名與恢復停用商品預設限公司管理員。
- `supplier=NULL` 的通用別名要有有效的條件唯一約束；不能認為目前包含 nullable supplier 的複合唯一鍵就一定能防重複。
- 加約束前先列既有衝突，不自動刪除／合併；使用 transaction、識別碼唯一約束及冪等處理同時提交。
- 模糊文字無法保證完全消除重複；硬性攔截只用已確認識別，模糊結果以提示與人工辨識處理。

### 4.4 API／前端接入方式

- 優先擴充既有查詢與 identity service，避免兩套辨識結果；需要新增 resolve／duplicate-check endpoint 時，路徑由 Claude 依既有 router 提案。
- 回應至少表達 `existing`、`candidates`、`conflict`、`none`，並給符合原因與授權動作；不得把搜尋「選中」等同入庫已完成。
- 儲存端回傳可理解的重複／衝突回應，例如 409 與候選，前端保留表單內容供修正。
- 單筆、批次、型號展開及匯入均經過相同的新品建立規則；匯入可先產生待確認列，不能自動批次按「不同款」。
- API 呼叫包在既有 `api/hooks.ts`／`api/search.ts`，遵守 `docs/ui-patterns.md` 的錄入效率與鍵盤操作。

## 5. 多店集中備份：使用者流程

### 5.1 任意電腦手動備份

範例：同公司有湳雅、民生兩店，老闆在家裡的電腦操作。

1. 接上備份硬碟，登入 POS。
2. 進入「設定 → 備份與還原」。
3. 系統顯示目前公司、包含的全部門市、最近成功產生的備份及最近還原驗證。
4. 按「備份全部門市」，伺服器建立工作；切換頁面不取消工作。
5. 完成封裝與驗證後提供下載，店家透過瀏覽器存到硬碟。
6. 可從另一台授權電腦重新登入，查看同一工作並下載尚未過期的檔案。

「任意電腦」指支援的 Windows／macOS 瀏覽器、有網路且通過帳號授權；不要求安裝資料庫，不綁 MAC 位址、不限定門市 IP。

### 5.2 狀態必須誠實

| 狀態 | 意義 |
|---|---|
| 排隊中／產生中 | 伺服器正在處理，尚無完整可用檔案 |
| 已驗證，可下載 | 備份封裝已完成且通過資料／檔案完整性檢查 |
| 已開始下載 | 已回應下載請求，不能證明使用者硬碟已寫入 |
| 已驗證本機檔案 | 使用者重新選取檔案，由系統完成可執行的完整性驗證；記錄驗證時間 |
| 失敗／已過期 | 顯示原因與下一步，不冒充成功 |
| 已完成還原演練 | 在隔離相容環境實際還原並核對，與單純檔案雜湊檢查分開 |

一般瀏覽器下載不保證程式知道硬碟位置或寫入結果。第一版採一般下載與選檔驗證作基線；`showSaveFilePicker()` 只能作支援瀏覽器的加強功能，必須有 fallback，不能綁死主要流程。[MDN 相容性與使用條件](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker)

### 5.3 公司範圍與還原單位

- 公司備份不受當前畫面選到的單一門市影響，必須包含該公司全部門市。
- 公司管理員可備份／下載／驗證自己的公司；一般店員預設無權限。
- 平台管理員維運入口與公司入口分開授權，不因平台角色就從一般 URL 隱式跨公司。
- 每次查工作、下載、驗證、還原都重新檢查權限及 tenant；不能只在按下建立時檢查。
- 不同公司共用一顆硬碟可分開存放獨立加密檔案，但一般店家帳號不得列出或取得別家公司資料。
- MVP 整家公司還原，包含共用商品、會員、成本與跨店調撥；不提供任意單店覆蓋式回溯，避免跨店資料失去一致性。

## 6. 備份格式與一致性

### 6.1 平台救災與公司可攜備份

| 類型 | 對象 | 用途 |
|---|---|---|
| 平台整庫備份 | 平台維運人員 | 整個服務災難復原，沿用並檢查 `ops/backup.sh` |
| 公司可攜備份 | 該公司管理員 | 全部門市業務資料＋附件，能由另一套相容 POS 還原 |

`pg_dump` 是資料庫層級工具，不提供直接依每張表 `tenant_id` 匯出的公司備份；不能用表名篩選或前端隱藏來取代列層級隔離。共享資料庫下建議實作明確公司範圍的可攜資料封裝。也不能讓使用者上傳任意 SQL 並直接執行。[PostgreSQL pg_dump 文件](https://www.postgresql.org/docs/16/app-pgdump.html)

既有 `ops/backup.sh` 實際清理依 30 天前檔案，與「最近 30 份」註解不同；開工時核對，勿將它當成新功能已存在的保留策略。

### 6.2 備份資料清單

先建立明確 registry，逐 model 標註「公司資料」「由關聯歸屬的子資料」「共享主檔」「權限／帳號」「可重建衍生資料」「排除」，不可只掃有 `tenant_id` 的表。

至少覆蓋：

- 公司設定、全部門市、單號／SKU／會員等流水設定、發票字軌及付款方式。
- 商品、類別、機型與相容關係、品牌／款式、零庫存與停用商品、別名、供應商來源對照。
- 會員、客戶、供應商、業務員、門號相關業務資料與歷史匯入紀錄。
- 進銷貨、銷退、調撥、維修、現金相關單據與所有明細、付款、作廢狀態。
- 序號、逐台機況與成本、StockBalance、StockMovement、成本快照。
- 待確認入庫、來源／辨識紀錄及該公司引用的圖片、PDF 等實體檔案。
- 業務資料引用的歷史經手人、權限設定的復原對照資訊；登入憑證另依第 7.3 節處理。

新增 model／欄位後需更新格式或分類測試。未知且未分類的業務模型不能被靜默漏掉；只存相對媒體路徑不算備份附件。衍生報表可重建，但須有說明；既有帳本、成本及歷史快照不可當成可任意重算資料。

### 6.3 封裝與私密性

建議副檔名 `.mppos-backup`；使用固定 schema 的結構化資料、manifest 與附件，不使用可執行序列化格式。

manifest 至少記錄：格式版本、POS schema／migration 版本、備份 ID、公司穩定識別、包含門市、快照時間與時區、資料分類清單、各表筆數、各附件大小與雜湊。不要把資料庫連線字串或主機絕對路徑放入檔案。

- 現有 Tenant 只有本機數字 PK、名稱與 code；新增不可由一般 CRUD 任意修改的持久公司 UUID，migration 為既有公司逐筆回填不同值。新環境經授權認領後保留來源 UUID，不以名稱、code 或數字 PK 代替；UUID 相同本身也不是授權證明。
- 使用成熟的驗證式加密封裝，涵蓋敏感 manifest 與內容；不得自行設計加密算法。
- 復原密碼／金鑰有獨立保管方式，不能只存在原伺服器，否則原主機壞掉時備份也無法還原。
- 提供繁中復原憑證說明；密碼或金鑰不寫入日誌、不與備份明文放在一起。
- 備份可能包含會員及維修敏感資料，不可放 public media 目錄；下載必須授權。
- 不匯出平台金鑰、API token、登入 session、其他公司資料與平台管理員帳號。
- 後端暫存檔採有限保留期限並顯示到期日。店家下載的歷史檔不由伺服器擅自刪除。

### 6.4 同一時間點與背景工作

公司資料匯出應在同一個 PostgreSQL `REPEATABLE READ` 唯讀 transaction／快照內完成；不能每張表各開連線、各取當下結果。一般預設隔離的 `atomic()` 不足以保證多次讀取使用同一快照。[PostgreSQL 交易隔離說明](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-REPEATABLE-READ)

- 快照同時固定附件引用清單；使用不可變附件／保留鎖等方式避免打包期間檔案被覆寫或刪除，逐檔驗證。必要附件缺失時，完整備份工作失敗並列原因。
- 保留資料與業務流水欄位；資料庫 sequence 的還原另依實際目標最大 ID 與共享範圍處理，不靠檔內舊 sequence 直接倒退。
- 業務單號與發票字軌另處理：既有公司回溯須保留還原前已用號碼／下一可用值的高水位，與備份及還原資料核對後取不會重複使用的安全值，不能直接倒退 `InvoiceTrack.next_number`。新環境若無法確認備份後的開票／用號情形，先停止相關自動取號，完成核對再開放。
- 工作狀態持久化於資料庫；背景 worker 重啟後可辨認中斷、重試或失敗，不依賴 web process 的記憶體 thread。
- 每公司限制並行備份數；重複點擊以冪等鍵去重，失敗不留下可下載的半份檔案。
- 先確認是否已有可沿用 worker；若沒有，採最小持久工作佇列與 management worker，具租約／逾時回收與有限重試，不為 MVP 強制引入新基礎設施。
- 排隊、快照匯出與完成狀態的寫入要分清交易邊界；狀態更新不能破壞唯讀快照。

## 7. 還原流程與失敗處理

### 7.1 第一版必須包含的兩條還原路徑

1. **隔離／新環境復原**：在相容 POS 空環境，憑備份檔與獨立復原憑證恢復公司資料；這是證明硬碟有用的必要驗收。
2. **既有公司回溯**：管理員上傳備份、完成預檢、查看日期與覆蓋範圍，再明確確認；正式切換必須有維護鎖、安全備份及失敗回復能力。

第一版僅支援明確列出的相容格式／schema 組合；不支援的版本直接拒絕並給可理解原因，不猜測跨版本欄位。

### 7.2 還原步驟

1. 上傳至隔離暫存區，限制大小／解壓總量，拒絕路徑穿越、符號連結及不允許的內容型別。
2. 解密並驗證 manifest、版本、完整性、FK、公司歸屬、檔案清單與必要主檔。
3. 顯示來源公司、包含門市、備份時間、資料筆數摘要，以及本次還原會取代哪些資料。
4. 預檢不改正式資料。確認操作綁定這份備份、這個目標與此次預檢結果；過期或變更後重新驗證。
5. 正式覆蓋前啟用該公司的寫入維護鎖，等待在途交易完成，擋所有相關 API、背景工作與業務匯入；先建立可用的當前狀態安全備份，失敗就不往下執行。
6. 資料與附件先暫存、驗證，再以可回復的方式切換；DB transaction 不會自動回滾檔案系統，必須另外設計附件暫存與引用切換。
7. 依來源 PK 建立明確映射，維持 FK／歷史單號／序號關係；目標 tenant 由授權程序決定，不採信檔案內的 tenant 數字 ID。
8. 恢復既有帳本狀態，不呼叫進貨／銷貨 commit service 重播交易，避免庫存、現金、發票再次發生。
9. 驗證各表筆數、數量、序號狀態、付款／成本快照、調撥關係、附件、登入與倉別限制；核對業務流水高水位及備份後已對外使用的號碼／狀態，再解除對應限制。不能以「目前資料庫內沒有撞號」取代對外已用號碼的核對。
10. 失敗不得留下可用的半套資料；保留原資料與失敗紀錄。若因中斷無法證明一致性，持續維護狀態並給復原步驟，不自動開放營業。

既有公司還原原則上要求公司穩定識別相同。新環境首次載入須經明確的管理員復原／認領流程，不能藉修改檔內識別將資料匯入任意既有公司。跨公司合併不在範圍內。

### 7.3 帳號、權限與操作紀錄

- 不直接還原過期 token、session、平台管理員或全域密鑰。
- 既有公司回溯保留現有登入控制；歷史經手人建立顯式映射，不能遺失單據歸屬或任意賦予權限。
- 明確處理 `UserProfile.default_warehouse`、`SalesPerson.user` 等映射。備份後新增的帳號、門市或無法對回的關聯列入預檢；無合法目標時維持鎖定／明確停用並待管理員處理，不可為通過 FK 檢查而解除鎖倉或提升角色。
- 新環境先建立復原管理員，再依備份內的業務人員對照重建需要的店員帳號、重設密碼及倉別限制；不能只還原業務資料卻無人可登入。
- 備份／下載／還原操作日誌與還原前安全備份不隨業務資料回溯一起被抹掉；記錄操作者、目標公司、檔案 ID、時間與結果。
- 後端要驗證角色與目標資源歸屬，不能只靠前端隱藏按鈕。

## 8. 下一階段：固定設備自動備份

此段保留設計方向，不在第一版自動安裝、建立排程或修改店家電腦設定。

- 任意授權電腦可以發起手動備份；無人值守寫入硬碟需要一台常開、連線且可存取硬碟的接收設備。
- 接收程式使用可撤銷、限該公司備份功能的憑證，不保存資料庫管理員密碼。
- 自動接收完成須檢查檔案大小／雜湊、完成寫入再回報；磁碟滿、未接硬碟、斷線、睡眠與逾時有明確失敗狀態。
- 保留多日期版本；只管理指定備份目錄，不能掃描／清理店家的其他檔案。
- 自動排程頻率、保留數量、固定設備種類及遠端提醒方式，於進入本階段時再與使用者確認。
- 若改用各店獨立資料庫，必須另設各店上傳／收齊狀態，不能把部分門市備份標成全部成功。

## 10. 驗收清單

### 10.1 商品與入庫

- [ ] 只先建立一筆標準商品，四種原始寫法皆能召回它；不依賴先手動輸入全部四個別名才通過。
- [ ] 換字序、大小寫、斜線、Reno-16、藍色／藍、側翻藍連寫均有測試。
- [ ] 資訊不足時回傳可解釋候選；兩款藍皮套同時存在時不自動挑第一款。
- [ ] 零庫存、只有他店有庫存、本店無 StockBalance 列、停用商品都能在正確情境找到。
- [ ] 停用商品不因搜尋或選用偷偷啟用；未授權人不能恢復。
- [ ] Reno16／Reno16 Pro、藍／深藍、不同材質／品牌／包裝不被合併。
- [ ] 確認具體叫法後下次可找到；`reno16` 等廣泛詞不會變唯一別名。
- [ ] 別名衝突會提示；通用別名並發寫入不產生多筆互相矛盾的自動對應。
- [ ] 一般進貨、Picker、批次貼上、Intake 手動改對應與商品管理結果一致；模糊批次候選未經確認不能入庫。
- [ ] 單筆、批次建檔、型號展開、匯入、Intake 新品與直接 API 均無防重複繞過。
- [ ] 同請求重送與同識別碼並發不產生重複商品；合法不同款仍可建立。
- [ ] 租戶 A 不可引用租戶 B 的 product／supplier／alias，也看不到其候選與庫存。
- [ ] 銷貨仍遵守實體零庫存不可選、虛擬商品規則、IMEI 與中文搜尋安全閥。
- [ ] 進貨確認後只增加既有商品庫存，不新增 Product；可追溯該次入庫與別名確認者。

### 10.2 備份與還原

- [ ] 以兩家公司、其中一家公司兩門市作測資；公司備份完整包含兩店且不含另一家公司資料／附件／憑證。
- [ ] Windows 與 macOS 的支援瀏覽器各完成一次登入、建立／查看工作、下載；清楚記錄實際驗證的瀏覽器與版本。
- [ ] 不支援檔案選擇器 API 的瀏覽器仍可走一般下載；畫面不冒稱已存入硬碟。
- [ ] 備份工作在頁面關閉後可繼續，換電腦可查看；逾時、重啟、重送有可預期結果。
- [ ] 備份期間同時銷貨／調撥，匯出結果是同一個一致快照，沒有單頭／明細／庫存時間錯位。
- [ ] 附件缺失、內容變動、磁碟滿或工作中斷不產生假成功；錯誤訊息可供處理。
- [ ] 檔案具版本、完整性與加密保護；在原伺服器不可用時，仍可用獨立保管的復原憑證還原。
- [ ] 新隔離環境實際還原後，核對庫存、序號、成本／付款快照、作廢、跨店調撥、流水、原圖及已學別名。
- [ ] 還原後四種 Reno16 叫法仍可查到同商品；再入庫不重建料號。
- [ ] 還原後下一張單號／新商品與序號建立不撞號，不重複產生現金或庫存異動。
- [ ] 舊備份的發票字軌／單號不退回已使用區間；新環境無法確認對外用號時，取號維持停用直到核對完成。
- [ ] 還原後管理員可登入、店員鎖倉有效；舊 token 不因備份重新生效。
- [ ] 備份後新增帳號或其門市不在備份時，預檢列出映射問題，還原不造成解除鎖倉或越權。
- [ ] 錯誤密碼、損毀檔、路徑穿越、不支援版本、竄改公司與 FK 均在正式異動前拒絕。
- [ ] 既有公司還原前安全備份成功、所有寫入入口受鎖；故障注入證明沒有部分覆寫或附件與 DB 不一致。
- [ ] 還原公司 A 不修改公司 B 的帳本、帳號、附件或共享 sequence 的安全範圍。
- [ ] 操作紀錄、還原前安全備份保留；未授權下載、過期下載與猜測工作 ID 均被拒絕。

### 10.3 測試執行與證據

後端用隔離 PostgreSQL 測試，包含真正 transaction／並發測試；SQLite 結果不能取代 PostgreSQL 約束與還原驗收。`backend/manage.py` 會載入根目錄 `.env`，先明確指定並核對隔離測試的連線與設定，不能直接依工作目錄設定對正式庫執行。

確認上述測試環境後，可從 `backend/` 執行既有相關測試，並納入新備份模組測試：

```sh
python manage.py test apps.catalog apps.identity
```

從 `frontend/` 執行：

```sh
npm run typecheck
npm run build
```

依實際修改補充相關 regression；前端缺 test runner 時，可先用可重現的瀏覽器驗收與必要的小型測試，不為低價值實作鏡像測試擴張工具鏈。

證據須區分：程式碼推論、隔離測試、實際瀏覽器操作、還原演練、正式部署；報告不能互相替代。
