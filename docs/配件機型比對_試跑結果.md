# 配件 → 相容機型比對:實作結果與結論

> 試跑 2026-09-26、實作 2026-09-27
> 目的:評估並實作「配件品名 → 相容機型」比對,並判斷 Jev(TypeSafe 判斷模型)該接在哪
> 資料:正式 `inventory_3c` 的真實型錄(dev 機;正式機是 Mac mini 的 `mppos`)
> 相關:[AI 助理與智慧入庫架構修改實作計畫](AI助理與智慧入庫_架構修改實作計畫.md)

## 一句話結論

**規則查表做掉三分之一,Jev 只留著出建議、一筆都不自動寫。**
瓶頸從頭到尾是機型主檔涵蓋範圍,不是判斷能力。主檔從 4 筆補到 168 筆之後,
規則就把 1071 筆配件掛上 1337 筆相容關聯——這段完全沒用到 AI。

## 零、先修正前一版文件的四個錯誤

第一版試跑(2026-09-26)有幾個結論是錯的,原因都是**查詢沒帶租戶過濾**:

| 前一版說 | 實際 |
|---|---|
| 機型主檔「大量重複」(iPhone 15 Pro ×3),造成 664 次歧義 | **不是重複**。`PhoneModel` 的唯一約束是 (tenant, code),那是三個不同租戶各有一筆。歧義是我的腳本沒過濾租戶造成的 |
| 主檔有測試垃圾(`Galaxy S 99 Test` 等 4 筆) | 那 4 筆全在 `CATTEST`(型錄測試)租戶,不影響真實資料 |
| 主檔有 213 筆現役機 | 那是三個租戶加起來。**真實資料所在的 `default` 租戶只有 4 筆** |
| 老料件是呆料,不值得掛機型 | 只有 HTC / LG / SONY 那批成立(458 品項總庫存 828)。老 iPhone 配件平均庫存 2.6 個,跟現役 iPhone 13-18 的 2.2 個一樣,**不是呆料** |

教訓:這個系統所有主檔都是 per-tenant,任何分析都要先 `for_tenant`。

## 二、為什麼模糊比對跨不過去

型錄裡同一台機有三套寫法,全都在 `default` 租戶裡:

| 來源 | 寫法 |
|---|---|
| `import_taiwan_catalog` 建的手機 | `iPhone 15 Pro Max 256GB 黑色鈦金屬 台版 全新` |
| 店家自己手打的手機 | `iPhone17 Pro 1TB 藍色`、`三星 A17 6/128G 追浪藍` |
| 歐睿匯入的配件料號 | `IMOS/IP15PM/透` |

`identity.services._candidate_search` 是逐詞 AND 模糊比對。拿 8 句跨慣例的廠商寫法
打真實 DB,**候選 8/8 全部 0 筆**:

```
iPhone 15 Pro Max 鋼化玻璃貼 透明  → 0 筆
IP15PM 256G 黑鈦                 → 0 筆
三星 A57 滿版玻璃貼               → 0 筆
Samsung S24 Ultra 空壓殼 透明     → 0 筆
```

對照組用型錄自己的寫法就撈得到(`IMOS/IP15PM/透` → 1 筆),證明測法無誤。
**候選 0 筆時 Jev 連題目都拿不到**——它只能從候選裡選,不能無中生有。

## 三、店內縮寫慣例:由頻率數據解出來,不需要 AI

數 2953 筆配件品名的斜線片段頻率:

```
IP16 37   IP16+ 32   IP16PRO 33   IP16PM 33
IP15 36   IP15+ 30                IP15PM 38
IP14 30   IP14+ 35   IP14P  26    IP14PM 29
```

- `+` = Plus、`PRO` = Pro、`PM` = Pro Max、`U` = Ultra
- **`P` 的意思取決於那一代有沒有 Pro**:iPhone 6/7/8 沒有 Pro,所以 `IP7P` = 7 Plus;
  iPhone 11 之後有 Pro,所以 `IP11P` = 11 Pro。
  程式裡**不寫死**,而是查該租戶主檔有沒有「iPhone N Pro」那一筆——主檔補了新機,判斷自動跟著變。
- 連字號兩種用法都有:`S4-MINI` / `ZF4-PRO` / `PIXEL-8` 是型號的一部分,
  `IP6SP-軟質邊框` / `IP6-4.7-亮` 是分隔符。兩種都試,取對得到的那個。
- 一條列多款機時,後面幾款會省略前綴(`IP16E/17E`、`IP13P/13PM`)。
  只收「有後綴」的裸寫法;裸數字(`8`、`7`)在品名裡多半是吋數或代數,收進來會亂對。

程式:`apps/catalog/accessory_model_match.py`。測試:`apps/catalog/tests.py`(13 條)。

## 四、做了什麼

### 步驟 1:把機型主檔建起來(4 → 168 筆)

`import_taiwan_catalog` 會連「型號 × 容量 × 顏色」的商品 SKU 一起建,
`default` 租戶已經有自己的商品,灌整份型錄會憑空多出幾百個不存在的商品。
所以新增一支只建機型、不建商品的指令:

```bash
python manage.py sync_phone_models --tenant default --data apps/catalog/data/taiwan_catalog --confirm
# → 新建 111 筆(型錄 JSON 只涵蓋 iPhone 13 以後)

python manage.py sync_phone_models --tenant default --data apps/catalog/data/phone_models_extra.json --confirm
# → 新建 53 筆(補充清單)
```

補充清單 `apps/catalog/data/phone_models_extra.json` 只有機型身分,沒有價格顏色。
每一筆後面都有真實配件在指它(清單裡 `_why` 欄註明出現次數),不是憑印象列的:

- **老 iPhone 全家族**(5 / 6 / 7 / 8 / X / XS / XR / 11 / 12 / SE 系列,24 筆)
  `IP6` 在配件品名出現 52 次、`IP11P` 26 次。這些機不賣了,但配件還在賣。
- **JSON 還沒更新的現役機**:Galaxy S26 系列、Galaxy A57、Reno 15、Reno 13 Pro、iPhone 17e
- **主檔漏掉的 Plus 線**:Galaxy S 8+ / 9+ / 10+ / 20+ / 22+ / 23+ / 24+ / 25+
  (主檔本來只有本體與 Ultra)
- **老三星**:Galaxy S4 / S4 mini / S5 / S6 / S8 / S20 Ultra、Note 2/3/4/8/10

命名慣例沿用既有主檔,不自己發明:iPhone XS 寫成 `iPhone 10 S`、6s 寫成 `iPhone 6 s`、
S24+ 的後綴是 `+`(組字時 `+` 不加空格)、16e / 17e 是「世代留空、後綴寫整串」。

### 步驟 2:規則查表掛相容關聯

```bash
python manage.py match_accessory_models --tenant default --confirm
```

結果(`default` 租戶,2777 筆需要掛機型的配件):

| | 筆數 | 占比 |
|---|---|---|
| 規則對到機型 | **1071** | 39% |
| 通用配件(不需要機型) | 406 | 15% |
| 對不到(留給人看,沒有硬湊) | 1300 | 47% |

→ 建立 **1337 筆 `ProductRelation`**(一個配件可對多台,例
`IMOS/IP7/IP8/SE2/SE3/點膠/黑` 掛 4 筆)。

目標表是 `ProductRelation` 而不是 `Product.phone_model`:實測 333 筆品名含 2 個以上
機型,單一外鍵掛不了。

### 步驟 3:哪些類別不用掛機型,改成類別設定

原本指令裡寫死「手機 / 平板 / 手錶」三個類別名。改成 `Category.needs_host_model`
(migration `0027`,預設 True),類別設定頁可勾。預設關掉的:

```
手機、平板、手錶            ← 主機本身,是被掛的那一方
掛繩/吊飾、支架/車架        ← 整類跟機型無關
家電、包膜、虛擬            ← 風扇 / 刮鬍刀 / 電視盒 / 包膜服務 / 虛擬商品
```

**刻意沒關「充電/線材」與「耳機/音訊」**:整體看像通用品,但實測裡面確實有機型專屬的
(`IP5/副廠/2M`、`SAM/S10/S10+` 耳機、`SAM/NOTE4` 充電線)。整類關掉會漏掉這些;
留著讓逐件品名的通用判斷處理——那兩類 165 / 68 筆裡已正確認出 133 / 46 筆是通用品。

### 步驟 4:Jev 只出建議,一筆都不寫

```bash
python manage.py suggest_accessory_models --tenant default --limit 200 --out /tmp/建議.csv
python manage.py suggest_accessory_models --tenant default --name-contains IPAD --out /tmp/平板.csv
```

## 五、為什麼 Jev 不能自動寫入:信心值不是正確率

兩個實測加起來就是理由。

### 手機那組:唯一一筆高信心是錯的

送 60 筆規則對不到的配件,只有 1 筆信心 >= 0.93,而它是錯的:

```
半/SAM/M53(5G)  →  Galaxy A 53 5G   信心 0.98   ✗
```

Galaxy M53 跟 A53 是兩支不同的手機,殼不通用。錯的原因很明確:
**主檔沒有 M53,而候選裡「A 53」看起來壓倒性地最接近**。
機型主檔缺一款,信心就會高得很篤定地指錯。

同一批另外兩筆也錯,但信心低(`SAM/A25(5G)` → Galaxy S 25,0.44),會被擋下。

### 平板那組:答得幾乎全對,但信心全部低於 0.9

送 40 筆,判出 20 筆,人工看過幾乎都對:

```
平板/IPAD/PRO/11吋(2024)       → iPad Pro 11吋 (M4)   0.68   ✓
平板/IPAD/PRO/13吋(2024)       → iPad Pro 13吋 (M4)   0.79   ✓
平板/DAP/IPAD/AIR4/5/10.9      → iPad Air 5 (M1)      0.72   ✓
平板/IPAD/10代                 → iPad 10              0.86   ✓
平板/IPAD/10.2                 → iPad 9               0.49   ✓
```

**最高只有 0.86**,任何 0.9 以上的門檻都會全部擋掉。

### 結論

高信心會錯、對的會低信心。**信心量的是「機率分佈有多集中」,不是「答案對不對」。**
所以 `suggest_accessory_models` 不提供任何自動寫入路徑,只輸出 CSV 給人判讀。

### 那它的價值在哪

把「規則對不到」細分成三種,人只要看真正需要處理的那一種:

- **判出具體機型**:多半是平板尺寸世代對不上,人看一眼就能確認
- **說是通用配件**:不用掛也不用再問(實測 7 筆全對,信心 0.74–0.98)
- **說主檔沒這款**:實測占規則殘留的九成以上,而且抽查全對
  (`Galaxy A 57`、`Galaxy S 20`、`Galaxy Note`、`Reno 7`、`X 21`、`Nokia`、`iPhone 5`
  在主檔的筆數都是 0)

第三種占九成,**這正是「該補主檔」而不是「該接 AI」的證據**。

## 六、殘留的 1300 筆是什麼(步驟 5:不動)

| 類別 | 對不到 | 占該類 | 對不到的主要品牌 |
|---|---|---|---|
| 保護貼 | 403 | 81% | HTC 78、SONY 57、ASUS 33、INF 25、LG 23、華為 17 |
| 玻璃貼 | 336 | 57% | 同上 |
| 空壓殼 | 226 | 69% | HTC 31、SONY 30、ASUS 9、華為 8 |
| 皮套 | 168 | 58% | 同上 |

一半以上是**主檔沒收錄的老品牌機**(HTC D601 / SONY Z1 / ASUS ZD552KL / LG L7…)。
這批 458 品項總庫存只有 828 個(平均 1.8),是真呆料——放著就好,
真的再進貨時走待確認區逐筆處理,不必事先掛。

剩下的是平板那組尺寸世代寫法(`IPAD` 55 次、`TAB` 29、`PRO` 24、`11吋(2024)` 7…),
約 150 筆,用 `suggest_accessory_models --name-contains IPAD` 出建議給人確認即可。

## 七、如果之後要把 Jev 接進 `identity.match_line` 的階梯⑤

`services.py` 開頭註解本來就留了這一格(「⑤ AI 語意 → 這版不做」)。依這輪實測,
接的話要守住:

1. **不准自動對應,任何信心都不行**。第五節的 M53 案例證明門檻保護不了——
   主檔缺一款就會高信心指錯。只能排候選順序、標「AI 建議」,由人點選。
2. **硬屬性衝突永遠否決 AI**。容量 128 對 256,Jev 回 0.99 也不准自動。
   `services.py` 開頭那條紀律不因接 AI 放寬。
3. **AI 信心與規則分數分開存**,不要混成同一個 0–100。
4. **打不通就退回規則**。進貨不可以因為外部服務掛掉而卡住。
   `~/runphone-match/apps/api/src/lib/jev.ts` 已經是這個寫法。
5. **候選必須先依品牌縮小**:實測 215 個候選一次只能問 5 題(再多回
   `max_tokens_exceeded`),縮到 40 個候選就能一次問 25 題。

## 八、還沒做的

- **1300 筆殘留沒有後台介面**。目前只能用管理指令看,沒有「待補相容機型」的頁面。
  要做的話 `match_accessory_models --show-unresolved` 的輸出就是資料來源。
- **`suggest_accessory_models` 的建議沒有地方存**。只出 CSV;人確認後要手動處理。
- **舊歐睿料號還沒變成別名**:25 筆品名帶 `(T29SAMS801)` 這種舊碼,
  應該進 `ProductAlias` 當 `vendor_sku`,是現成的比對材料。
- **舊系統匯入的庫存量是垃圾**:`平板7至8吋(包膜)` 100 萬個、`JB` 19 萬個、
  `單包邊條 (T25008)` 10 萬個。這些是包膜服務被當成料件匯入,跟本文無關但該清。
- **另兩個租戶沒跑**。`dealer-a` 與 `CATTEST` 的配件沒掛機型;要跑同樣兩支指令即可。
