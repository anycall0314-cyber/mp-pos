# MP 買賣串接規格 v2(草稿)

> 2026-10-14 草稿(同一天第二版:加了賣家的操作、中古機、維修串接)。**owner 同一天定了第 12 節的八件事,開始施工。**
> owner 的方向(原話):「使用POS的經銷，身份會是買家（採購手機，配件等），也可能是賣家（批發手機，配件），我想要制定API規格，彼此串接」;
> 對象「兩個都會有」(平台內的經銷商、外面的系統);「錢完全不需要經過平台，只管帳」。
> 「賣家角度，你要讓批發可以簡潔方便快速操作…例如中古機我要快速進貨與上架，以及平台販售等」;
> 「未來智盛（專修同行的手機）加入後，我也想要讓維修系統可以串接，比如報價，進度等，或是維修材料庫存有無」。
>
> 這一份是現有「標準格式」(膜總裁 B2B 對外下單 API v1,`~/moceo-b2b/docs/api-v1.md`;POS 當買家的那一半已經照它做好)的延伸:
> **v1 的每一支在 v2 都照舊能用**,v2 只是多了賣家需要的東西。標了「要定」的是還沒有決定的。

## 1. 管什麼、不管什麼

**管**:誰可以跟誰買 → 看商品與價錢 → 下單 → 賣家接單 → 出貨 → 買家收貨入庫 → 對帳(哪幾張單、多少錢、標記收了沒)。

**不管**:
- **錢**。不收款、不付款、不代收、不抽成。單上的「月結 / 匯款 / 貨到付款」只是雙方講好的方式,「已收款」是賣家自己按的記號。
- 物流的叫車與追蹤(只帶託運單號)。
- 發票的開立(只帶買方要的抬頭與統編給賣家)。
- 退貨、瑕疵換貨(這一版不做,見第 12 節)。

## 2. 兩種身分、兩種接法

| | 是誰 | 做什麼 |
|---|---|---|
| **賣家** | 提供商品與價錢、接單、出貨的一方 | 一家經銷商(批發手機、配件)、一家廠商(膜總裁) |
| **買家** | 看商品、下單、收貨的一方 | 一家經銷商的一間門市 |

同一家經銷商可以同時是賣家與買家。**買家以「門市」為單位**(一間門市一個收貨地點、一份往來)。

| 接法 | 什麼時候用 | 怎麼認人 |
|---|---|---|
| **平台內** | 買賣雙方都用這套 POS | 不用金鑰。賣家在 POS 裡核准這個買家,平台替雙方搬資料;資料的樣子跟對外的一模一樣 |
| **對外** | 有一方不在這套 POS(別人的 POS、廠商自己的系統) | 金鑰。賣家發一把金鑰給買家的一間門市;一把金鑰只認得那一間門市 |

兩種接法走同一份規格:平台內只是省掉「貼金鑰」與「網路上傳送」。

## 3. 一張單的一生

```
買家:看商品 ──→ 下單 ─────────────────────────→ 收貨入庫(可以分好幾次)
                  │                                  ↑
賣家:           待接單 ─→ 已接單 ─→ 部分出貨 ─→ 已出貨 ─→ 已完成
                  │         │
                  └→ 已拒絕  └→ 已取消(雙方講好之後)
```

- 賣家可以設成「下單就算接單」(膜總裁現在就是這樣),這時候沒有「待接單」這一步。
- 一張單可以分好幾次出貨;每一次出貨是一筆「出貨單」,買家照出貨單收貨。
- **手機、平板等帶序號的商品,出貨單上有每一台的序號(IMEI / SN)**,買家收貨時直接變成自己庫存裡的那幾台,不用再刷一次。
- 事實只有一份:訂單現在的樣子以賣家那邊為準(賣家事後改單、改價,買家再查一次就是新的)。

## 4. 誰看得到什麼(平台上的經銷商是互相競爭的)

- 買家只看得到**賣家開放給他的**商品與**他自己的**價錢;看不到賣家的成本、別的買家的價錢、賣家賣給別人的單。
- 賣家只看得到**下給他的**單、那張單的收貨資料與聯絡方式;看不到買家的庫存、買家跟別家買了什麼、買家賣多少錢。
- 庫存:賣家決定露多少 —— 只露「有貨、缺貨」(預設)/ 露可以訂的數量。
- 沒有核准的買家:連這個賣家有沒有在賣都不知道(跟「廠商只給指定的公司」同一個做法)。

## 5. 共同語言:商品怎麼認

- **手機、平板、穿戴**:用平台的標準機型(`docs/development/M1_標準機型清單/`,之後的共用資料池)。商品上帶 `standard`(機型代碼、規格、顏色)——
  買賣雙方講的是同一支,買家這邊**不用連品名**,直接對到自己的品號。
- **配件與其他**:沒有共同語言。賣家給自己的料號與品名,買家用「品名連連看」連到自己的商品(連一次,之後自動)。
  賣家可以另外給 `fits`(這個配件適用哪幾個標準機型),買家連品名、查相容機型時用得上。
- **中古機**(每一台的機況、價錢都不一樣):**一台一筆上架**(owner 點名要能快速進貨與上架)。商品上除了 `standard` 還帶 `unit`:
  這一台的編號、成色、電池、備註、價錢;買家訂的是「這一台」。見第 7 節。

## 6. 管帳(錢不經過平台)

- 每張單有金額(貨款、運費、合計)、付款方式(雙方講好的文字)、**收款狀況(未收款 / 收了一部分 / 已收款)**:
  賣家對某一個同行記一筆「收到多少」,系統由舊到新把他的單銷掉(第 7 節紅隊第 3 條)。
- **對帳單**:某一段期間、某一個往來對象的每一張單 —— 單號、日期、出貨金額、收款記號、合計。買賣雙方各自拉得到自己的那一份,數字來源相同。
- 價錢含不含稅每個賣家講清楚一次(`price_includes_tax`);買家這邊照它記成本(膜總裁是含稅、kcimos 是未稅,兩種現在都有)。
- **不做**:收款沖帳、預收、額度控管以外的信用管理、佣金與抽成。(月結額度是賣家自己的規則,超過就擋單,訊息講原因。)

## 7. 賣家怎麼操作(第一標準:做完一件事要點幾下)

owner 的要求:批發要簡潔、方便、快速;紅隊站在批發商的立場數點擊與步驟。下面是 POS 裡賣家這一側的做法(平台內與對外的買家都一樣)。

**設定(只做一次)**
- 批發價的規則,三選一:門市售價減固定金額 / 門市售價打幾折 / 收購價加固定金額。之後每一台自動算,可以個別改。
- 「中古機進貨就上架」(預設開)。給誰看:只給核准過的同行 / 平台上所有同行(平台販售)。
- 「同行下單就算接單」(預設開)。

**收中古機同時上架**:還是原本那一張收購表單,每一台多一格「批發價」(自動算好)與一個勾「上架」(預設勾著)。按儲存 = 入庫 + 上架。不多一個畫面、不多一顆按鈕。照片不要求。

**在庫的補上架**:庫存查詢篩「中古機 / 還沒上架」→ 全選 → 上架。

**自動下架**:這一台在門市賣掉、調走、送修,自動從批發清單消失;退回來的不自動上架。兩個同行同時訂同一台,先送出的拿到,後送出的當下被告知。

**出貨**:畫面上方「待出貨 N」。**不用先打開哪一張單 —— 直接刷那一台,系統自己找是哪一張單的、打勾。**
單上列的是完整的序號(機身的標籤就是這支序號的條碼)。找不到的那一台按「這台不出」,其餘的照樣出。按「出貨」之後自動:扣庫存、開銷貨單(客戶 = 那個同行)、可以印出貨單。

**全新機與配件**:商品上勾「批發」,或整個類別一次勾。價錢照同行的等級(每一級是門市售價的幾折)。出貨數量預設 = 訂的數量,按「全部出貨」;缺的改數量,沒出的留在單上。

### 紅隊(批發商立場,2026-10-14)挑的三件事與怎麼收

1. **同一台中古機,現場客人與同行搶。** 掛在批發上的那一台被同行訂了(下單就接單),現場客人也要:門市刷這一台要嘛被擋(少賺零售價)、要嘛沒擋(賣兩次),而且要離開結帳畫面去找那張單。
   → **出貨之前,賣家可以把那一台抽回來**:門市開銷貨單刷到「已被同行訂走」的那一台,當下跳一個選擇 ——「賣給現場客人(同行那一台取消)」或「保留給同行」。
   選前者:同行那張單的那一行當下取消、對方馬上被告知;兩邊不會同時算賣出。
2. **出貨要一台一台對序號,少一台整張出不了。** 單上只有序號末 5 碼、同款好幾台要一台台開機對;有一台找不到,整張卡著。
   → 上面「出貨」那一段已經照這個改:直接刷、列完整序號、可以「這台不出」。
3. **月結的同行一次匯一筆、涵蓋十幾張單,要一張一張按已收款。** 少匯或記錯張也看不出來。
   → **對帳改成「記一筆收到的金額」**:對某一個同行輸入收到多少,系統由舊到新把他的單標成已收,看得到還欠多少、或多收多少。
   錢還是不經過平台,這只是記帳。

## 8. 維修串接(未來;智盛加入之後)

智盛是專修同行手機的:同行(送修方)把機器送去修,智盛(維修方)報價、修、回報進度。跟買賣是同一套接法(平台內不用金鑰、對外用金鑰),多的是下面這幾件。

| 步驟 | 送修方(同行的門市) | 維修方(智盛) |
|---|---|---|
| 查料 | 開單之前先查:這個機型的這個維修項目,有沒有料、同行價多少、幾天 | 回 有料 / 缺料 / 要訂(幾天) 與報價 |
| 送修 | 維修單選「委外 → 智盛」,機型、故障描述、序號自動帶過去 | 多一張「同行送修單」,不用再打一次 |
| 報價 | 看到報價,按「同意」或「不修」 | 檢測之後填維修項目、金額、預估天數 |
| 進度 | 自己的維修單跟著變(已送外廠 → 維修中 → 待取件) | 換狀態就好,不用另外通知 |
| 完修 | 實際費用自動填進維修單的委外費用(毛利照現有的算法) | 出貨或交還時按完成 |

- **共同語言**:機型用標準機型;維修項目(螢幕、電池、背蓋、尾插…)也要一份平台共用的清單,不然報價對不起來。
- **不自動帶的**:手機的解鎖密碼 / 圖形鎖。送修方明確勾了才帶,而且只給維修方看得到。客人的姓名電話不帶(維修方的客戶是那家同行,不是他的客人)。
- 能力表多三項:`repair_parts`(查料)、`repair_quote`(報價)、`repair_status`(進度)。
- 錢一樣不經過平台:維修費記在雙方的對帳單上。
- 現有的基礎:POS 的維修單有「委外」與委外實際費用(`repairs/services.py::money_of`);零件是零件倉的商品、有庫存。智盛那一側「收同行送修單」是新的。

## 9. 賣家可以只做一部分:能力表

不是每個賣家都做得到全部(膜總裁現在沒有取消與通知)。每個賣家用 `GET /capabilities` 講自己會哪些,買家的畫面照它顯示(不會的就不給那顆按鈕)。

| 能力 | 意思 | v1(膜總裁現況) |
|---|---|---|
| `products` | 看商品與自己的價錢 | 有 |
| `availability` | 商品帶有貨沒 / 可訂數量 | 沒有 |
| `orders` | 下單、查單 | 有 |
| `accept` | 有「待接單 → 接單 / 拒絕」這一步 | 沒有(下單就成立) |
| `cancel` | 買家可以用 API 取消還沒接的單 | 沒有 |
| `shipments` | 查單帶每一次出貨 | 只有每一行出了幾個 |
| `serials` | 出貨帶每一台的序號 | 沒有 |
| `receipts` | 買家回報收了多少;賣家照它擋取消出貨 | 沒有 |
| `notify` | 訂單有變動主動通知買家 | 沒有(買家自己查) |
| `statements` | 對帳單 | 沒有 |
| `units` | 中古機一台一筆上架、訂的是那一台 | 沒有 |
| `repair_parts` / `repair_quote` / `repair_status` | 維修:查料、報價、進度(第 8 節) | 沒有 |
| `sandbox` | 有測試用的金鑰(下的是測試單) | 有 |

## 10. 規則(v1 原本就有的照舊)

1. **價錢只有賣家算**。買家下單不送價錢;送了也不看。單價、小計、運費以賣家回的為準。
2. **同一張單只成立一次**。買家每張單自己產一把鑰匙(`idempotency_key`):回應沒回來就用同一把再送 —— 上一次成立了回 409 與那張單號,沒成立就正常成立。
   被擋下來的(400)不佔用鑰匙。
3. **金鑰綁一間門市**。只放在標頭,不放網址;只會送到它所屬的那個賣家;作廢立刻失效。
4. **錯誤一律講人話**:`{ "ok": false, "error": "月結額度不足,請改用其他付款方式", "code": "credit_exceeded" }`。`error` 是給店員看的,`code` 是給程式看的(v2 新增,沒有也可以)。
5. **通知只說「有事」,內容以查單為準**。通知裡沒有金額、沒有明細;買家收到之後自己去查那張單。通知沒到也沒關係,查單永遠是對的。
6. **沒有明確的答覆就是不知道**。連不上、逾時、對方出錯:買家不能當成沒成立,只能用同一把鑰匙再送。
7. 一律 HTTPS;時間帶時區;金額是整數元。

## 11. 介面(給寫程式的人;細節等上面幾節定了再補全)

位址 `https://<賣家>/api/v2/…`,標頭 `Authorization: Bearer <金鑰>`。每一個驗過金鑰的回應都帶 `ok` 與 `sandbox`。

| 動作 | 路徑 | 說明 |
|---|---|---|
| 會哪些 | `GET /capabilities` | `{ok, seller: {name, price_includes_tax}, capabilities: [...], payment_methods: [...], delivery_methods: [...]}` |
| 商品 | `GET /products` | v1 的欄位照舊(`sku` `name` `kind` `unit` `pack_qty` `unit_price` `specs` 混合盒);v2 多 `standard` `fits` `requires_serial` `condition` `available` |
| 下單 | `POST /orders` | v1 照舊(`idempotency_key` `items[{sku, spec_id, qty}]` `payment_method` `delivery_method` `ship_to` `invoice` `note`);回 `order_no` `status` `total_amount` `shipping_fee` |
| 查單清單 | `GET /orders?limit=&since=` | v1 照舊;v2 多 `since`(只拿這個時間之後有變動的) |
| 查單 | `GET /orders/{order_no}` | v1 照舊;v2 多 `shipments[{shipment_no, shipped_at, shipping_method, tracking_no, items[{sku, spec_id, qty, serials[{imei, sn}]}]}]`、`payment_status` |
| 取消 | `POST /orders/{order_no}/cancel` | 還沒出的部分;回現在的狀態。不行就回 400 與原因(例:「已經出貨,請聯絡賣家」) |
| 回報收貨 | `POST /orders/{order_no}/received` | 這張單到現在為止每一行收了多少、哪幾台(見第 12 節「實作時補的」) |
| 對帳單 | `GET /statements?from=&to=` | `{orders: [{order_no, ordered_at, shipped_amount, shipping_fee, payment_method, payment_status}], totals: {...}}` |
| 通知(賣家 → 買家) | 買家登記的網址 | `POST {event: "order.updated", order_no, at}`;用雙方共用的密鑰簽章(`X-MP-Signature`);買家回 200 就算收到 |

商品 v2 多的欄位:

```json
{
  "sku": "IP17P-256-OR",
  "name": "iPhone 17 Pro 256GB 宇宙橙",
  "unit": "台", "pack_qty": 1, "unit_price": 36500,
  "requires_serial": true,
  "condition": "全新",
  "available": "有貨",
  "standard": { "model": "apple-iphone-17-pro", "spec": "256GB", "color": "宇宙橙" }
}
```

配件:

```json
{
  "sku": "G02-K43", "name": "高透亮面 iPhone 17 Pro", "unit": "片", "pack_qty": 50, "unit_price": 38,
  "requires_serial": false, "available": "有貨",
  "fits": ["apple-iphone-17-pro"]
}
```

狀態的值(賣家回什麼買家就顯示什麼,不用翻譯;下面是建議的一組):`待接單` `已接單` `部分出貨` `已出貨` `已完成` `已拒絕` `已取消`。

## 12. 這一版不做 / 要定的

**不做(建議)**
- 退貨、瑕疵換貨(先用備註與人工;之後另開一版)。
- 報價單、議價、競標。
- 買家之間、賣家之間互相看到對方。

**owner 2026-10-14 定了**(原話:「上面除了中古機，要照我的，其他的照你建議一路開工做完」)
1. 誰可以跟我買:**中古機 = 平台販售**(平台上每一家同行都看得到、訂得到;賣家可以改成只給核准的同行)。
   全新機與配件只給核准過的同行(價錢是照每一個同行講好的折數算的,沒有往來就沒有價錢)。
2. 庫存露多少(按數量賣的商品):只露「有貨 / 缺貨」;賣家可以改成露數量。
3. 同一台中古機被同行訂了、現場客人也要:出貨之前賣家可以抽回來賣給現場客人(同行那一台當下取消、對方看得到)。
4. 管帳:記一筆收到的金額、由舊到新自動銷單、看得到還欠多少。錢不經過平台。
5. 買家取消:賣家出貨之前買家可以自己取消還沒出的部分。
6. 對外的金鑰:賣家自己在 POS 後台發給買家的一間門市。
7. 平台內的買賣:賣家出貨自動開銷貨單(客戶 = 那個買家)、扣庫存;買家收貨開進貨單(手機的序號直接帶進來)。
8. 維修串接:等智盛加入再排;方向照第 8 節。

**施工分三批**(每一批做完上測試站):賣家那一半(平台內)→ 買家那一半(平台內)→ 對外的接法(金鑰、通知)。進度在 `docs/development/CURRENT_TASK.md`。

**線上的格式補一條(中古機一台一筆)**:一個商品底下每一台是一個規格(`specs[]`),商品帶 `per_unit: true`;
規格的 `code` = 成色、`name` = 電池與備註、`unit_price` = 這一台的批發價。下單照 v1 的寫法帶 `spec_id`(= 那一台)、數量 1。
出貨之前不露序號;出貨單上才有 `serials[{imei, sn, grade, battery, note}]`。

**實作時補的幾條(2026-10-14;平台內的那一半已經照這樣做)**
- 付款方式是賣家跟這個買家講好的那一種(賣家定的):買家下單送什麼都不看;下單與查單的回應帶 `payment_method`,買家的紀錄照它寫。
- 一張單的 `items[]` 只有還算數的(數量已經扣掉不出的);整行不出的放在 `cancelled_items[]`。`total_amount` = 現在的貨款 + 已經出的運費。
- 賣家設成不往來、關掉批發之後:看商品與下單回 403;**買家自己已經有的單、對帳單、取消照樣可以用**(貨可能已經在路上)。
- **買家要跟賣家回報收了多少**(能力 `receipts`):`POST /orders/{order_no}/received`,內容是這張單**到現在為止**每一行收進庫存幾個、哪幾台
  `{items: [{sku, spec_id, received_qty, serials: [{imei, sn}]}]}`(整張單現在的樣子,不是這一次多收的;沒列到的行 = 0)。收的不能比算數的已出多。
  賣家照它擋「取消出貨」與整張銷退:**買家收進去的貨,賣家不能再變回自己的庫存**。要退貨 → 買家先把那一次的入庫作廢(回報變少),賣家才取消 / 銷退。
  每一行的 `shipped_qty` 只算現在算數的出貨(取消的、整張退掉的不算),另外帶 `received_qty`;有給 `shipments` 的賣家,買家這邊還沒出的不能先入。
- 「誰可以跟我買」的入口是**賣家發的一次性往來代碼**(八碼、七天、只能用一次),不是讓買家從名單上挑(平台上的經銷商互相競爭,不公開名單)。
