# MP 買賣串接規格 v2(草稿)

> 2026-10-14 第一版草稿。**還沒有實作,內容等 owner 逐項定。**
> owner 的方向(原話):「使用POS的經銷，身份會是買家（採購手機，配件等），也可能是賣家（批發手機，配件），我想要制定API規格，彼此串接」;
> 對象「兩個都會有」(平台內的經銷商、外面的系統);「錢完全不需要經過平台，只管帳」。
>
> 這一份是現有「標準格式」(膜總裁 B2B 對外下單 API v1,`~/moceo-b2b/docs/api-v1.md`;POS 當買家的那一半已經照它做好)的延伸:
> **v1 的每一支在 v2 都照舊能用**,v2 只是多了賣家需要的東西。標了「要定」的是還沒有決定的。

## 1. 管什麼、不管什麼

**管**:誰可以跟誰買 → 看商品與價錢 → 下單 → 賣家接單 → 出貨 → 買家收貨入庫 → 對帳(哪幾張單、多少錢、標記收了沒)。

**不管**:
- **錢**。不收款、不付款、不代收、不抽成。單上的「月結 / 匯款 / 貨到付款」只是雙方講好的方式,「已收款」是賣家自己按的記號。
- 物流的叫車與追蹤(只帶託運單號)。
- 發票的開立(只帶買方要的抬頭與統編給賣家)。
- 退貨、瑕疵換貨(這一版不做,見第 10 節)。

## 2. 兩種身分、兩種接法

| | 是誰 | 做什麼 |
|---|---|---|
| **賣家** | 提供商品與價錢、接單、出貨的一方 | 一家經銷商(批發手機、配件)、一家廠商(膜總裁) |
| **買家** | 看商品、下單、收貨的一方 | 一家經銷商的一間門市 |

同一家經銷商可以同時是賣家與買家。**買家以「門市」為單位**(一間門市一個收貨地點、一份往來)。

| 接法 | 什麼時候用 | 怎麼認人 |
|---|---|---|
| **平台內** | 買賣雙方都用這套 POS | 不用金鑰。賣家在 POS 裡核准這個買家,平台替雙方搬資料;資料的樣子跟對外的一模一樣 |
| **對外** | 有一方不在這套 POS(別人的 POS、廠商自己的系統) | 金鑰。賣家發一把金鑰給買家的一間門市;一把金鑰只認得那一間門市 |

兩種接法走同一份規格:平台內只是省掉「貼金鑰」與「網路上傳送」。

## 3. 一張單的一生

```
買家:看商品 ──→ 下單 ─────────────────────────→ 收貨入庫(可以分好幾次)
                  │                                  ↑
賣家:           待接單 ─→ 已接單 ─→ 部分出貨 ─→ 已出貨 ─→ 已完成
                  │         │
                  └→ 已拒絕  └→ 已取消(雙方講好之後)
```

- 賣家可以設成「下單就算接單」(膜總裁現在就是這樣),這時候沒有「待接單」這一步。
- 一張單可以分好幾次出貨;每一次出貨是一筆「出貨單」,買家照出貨單收貨。
- **手機、平板等帶序號的商品,出貨單上有每一台的序號(IMEI / SN)**,買家收貨時直接變成自己庫存裡的那幾台,不用再刷一次。
- 事實只有一份:訂單現在的樣子以賣家那邊為準(賣家事後改單、改價,買家再查一次就是新的)。

## 4. 誰看得到什麼(平台上的經銷商是互相競爭的)

- 買家只看得到**賣家開放給他的**商品與**他自己的**價錢;看不到賣家的成本、別的買家的價錢、賣家賣給別人的單。
- 賣家只看得到**下給他的**單、那張單的收貨資料與聯絡方式;看不到買家的庫存、買家跟別家買了什麼、買家賣多少錢。
- 庫存:賣家決定露多少 —— 不露 / 只露「有貨、缺貨」/ 露可以訂的數量。**(要定:預設哪一種。建議只露有貨、缺貨。)**
- 沒有核准的買家:連這個賣家有沒有在賣都不知道(跟「廠商只給指定的公司」同一個做法)。

## 5. 共同語言:商品怎麼認

- **手機、平板、穿戴**:用平台的標準機型(`docs/development/M1_標準機型清單/`,之後的共用資料池)。商品上帶 `standard`(機型代碼、規格、顏色)——
  買賣雙方講的是同一支,買家這邊**不用連品名**,直接對到自己的品號。
- **配件與其他**:沒有共同語言。賣家給自己的料號與品名,買家用「品名連連看」連到自己的商品(連一次,之後自動)。
  賣家可以另外給 `fits`(這個配件適用哪幾個標準機型),買家連品名、查相容機型時用得上。
- **中古機**(每一台的機況、價錢都不一樣):這一版先不做逐台上架。**(要定,見第 10 節。)**

## 6. 管帳(錢不經過平台)

- 每張單有金額(貨款、運費、合計)、付款方式(雙方講好的文字)、**收款狀況(賣家按的記號:未收款 / 已收款)**。
- **對帳單**:某一段期間、某一個往來對象的每一張單 —— 單號、日期、出貨金額、收款記號、合計。買賣雙方各自拉得到自己的那一份,數字來源相同。
- 價錢含不含稅每個賣家講清楚一次(`price_includes_tax`);買家這邊照它記成本(膜總裁是含稅、kcimos 是未稅,兩種現在都有)。
- **不做**:收款沖帳、預收、額度控管以外的信用管理、佣金與抽成。(月結額度是賣家自己的規則,超過就擋單,訊息講原因。)

## 7. 賣家可以只做一部分:能力表

不是每個賣家都做得到全部(膜總裁現在沒有取消與通知)。每個賣家用 `GET /capabilities` 講自己會哪些,買家的畫面照它顯示(不會的就不給那顆按鈕)。

| 能力 | 意思 | v1(膜總裁現況) |
|---|---|---|
| `products` | 看商品與自己的價錢 | 有 |
| `availability` | 商品帶有貨沒 / 可訂數量 | 沒有 |
| `orders` | 下單、查單 | 有 |
| `accept` | 有「待接單 → 接單 / 拒絕」這一步 | 沒有(下單就成立) |
| `cancel` | 買家可以用 API 取消還沒接的單 | 沒有 |
| `shipments` | 查單帶每一次出貨 | 只有每一行出了幾個 |
| `serials` | 出貨帶每一台的序號 | 沒有 |
| `notify` | 訂單有變動主動通知買家 | 沒有(買家自己查) |
| `statements` | 對帳單 | 沒有 |
| `sandbox` | 有測試用的金鑰(下的是測試單) | 有 |

## 8. 規則(v1 原本就有的照舊)

1. **價錢只有賣家算**。買家下單不送價錢;送了也不看。單價、小計、運費以賣家回的為準。
2. **同一張單只成立一次**。買家每張單自己產一把鑰匙(`idempotency_key`):回應沒回來就用同一把再送 —— 上一次成立了回 409 與那張單號,沒成立就正常成立。
   被擋下來的(400)不佔用鑰匙。
3. **金鑰綁一間門市**。只放在標頭,不放網址;只會送到它所屬的那個賣家;作廢立刻失效。
4. **錯誤一律講人話**:`{ "ok": false, "error": "月結額度不足,請改用其他付款方式", "code": "credit_exceeded" }`。`error` 是給店員看的,`code` 是給程式看的(v2 新增,沒有也可以)。
5. **通知只說「有事」,內容以查單為準**。通知裡沒有金額、沒有明細;買家收到之後自己去查那張單。通知沒到也沒關係,查單永遠是對的。
6. **沒有明確的答覆就是不知道**。連不上、逾時、對方出錯:買家不能當成沒成立,只能用同一把鑰匙再送。
7. 一律 HTTPS;時間帶時區;金額是整數元。

## 9. 介面(給寫程式的人;細節等上面幾節定了再補全)

位址 `https://<賣家>/api/v2/…`,標頭 `Authorization: Bearer <金鑰>`。每一個驗過金鑰的回應都帶 `ok` 與 `sandbox`。

| 動作 | 路徑 | 說明 |
|---|---|---|
| 會哪些 | `GET /capabilities` | `{ok, seller: {name, price_includes_tax}, capabilities: [...], payment_methods: [...], delivery_methods: [...]}` |
| 商品 | `GET /products` | v1 的欄位照舊(`sku` `name` `kind` `unit` `pack_qty` `unit_price` `specs` 混合盒);v2 多 `standard` `fits` `requires_serial` `condition` `available` |
| 下單 | `POST /orders` | v1 照舊(`idempotency_key` `items[{sku, spec_id, qty}]` `payment_method` `delivery_method` `ship_to` `invoice` `note`);回 `order_no` `status` `total_amount` `shipping_fee` |
| 查單清單 | `GET /orders?limit=&since=` | v1 照舊;v2 多 `since`(只拿這個時間之後有變動的) |
| 查單 | `GET /orders/{order_no}` | v1 照舊;v2 多 `shipments[{shipment_no, shipped_at, shipping_method, tracking_no, items[{sku, spec_id, qty, serials[{imei, sn}]}]}]`、`payment_status` |
| 取消 | `POST /orders/{order_no}/cancel` | 還沒接的單才行;回現在的狀態。不行就回 400 與原因(例:「已經出貨,請聯絡賣家」) |
| 對帳單 | `GET /statements?from=&to=` | `{orders: [{order_no, ordered_at, shipped_amount, shipping_fee, payment_method, payment_status}], totals: {...}}` |
| 通知(賣家 → 買家) | 買家登記的網址 | `POST {event: "order.updated", order_no, at}`;用雙方共用的密鑰簽章(`X-MP-Signature`);買家回 200 就算收到 |

商品 v2 多的欄位:

```json
{
  "sku": "IP17P-256-OR",
  "name": "iPhone 17 Pro 256GB 宇宙橙",
  "unit": "台", "pack_qty": 1, "unit_price": 36500,
  "requires_serial": true,
  "condition": "全新",
  "available": "有貨",
  "standard": { "model": "apple-iphone-17-pro", "spec": "256GB", "color": "宇宙橙" }
}
```

配件:

```json
{
  "sku": "G02-K43", "name": "高透亮面 iPhone 17 Pro", "unit": "片", "pack_qty": 50, "unit_price": 38,
  "requires_serial": false, "available": "有貨",
  "fits": ["apple-iphone-17-pro"]
}
```

狀態的值(賣家回什麼買家就顯示什麼,不用翻譯;下面是建議的一組):`待接單` `已接單` `部分出貨` `已出貨` `已完成` `已拒絕` `已取消`。

## 10. 這一版不做 / 要定的

**不做(建議)**
- 退貨、瑕疵換貨(先用備註與人工;之後另開一版)。
- 報價單、議價、競標。
- 買家之間、賣家之間互相看到對方。

**要 owner 定的**
1. 開通:賣家核准每一個買家才看得到商品與價錢(建議),還是可以設成公開批發價。
2. 庫存露多少:預設只露「有貨 / 缺貨」(建議),還是露數量。
3. 取消:賣家接單之前買家可以自己取消,接了要聯絡賣家(建議)。
4. 中古機批發:每一台機況與價錢不同。第一版先做全新機與配件(建議),中古機逐台上架另開一版;還是一起做。
5. 管帳做到哪:每張單的收款記號 + 對帳單(建議);不做沖帳。
6. 對外的金鑰誰發:賣家自己在 POS 後台發給買家(建議)。
7. 平台內的買賣:賣家出貨之後,賣家那邊自動開一張銷貨單(客戶 = 那個買家)、扣庫存;買家收貨開進貨單 —— 兩邊各按一次(像調撥的派發與確認)。

## 11. 跟現有程式的關係(施工時要對的)

- 買家那一半:`backend/apps/vendor_orders/`(`standard.py` 客戶端、`services.py` 叫貨與重送、`receiving.py` 到貨變進貨單、`mapping.py` 品名連連看)。
  v2 要補:能力表、出貨單與序號入庫、取消、通知、對帳單;手機用標準機型直接對品號。
- 賣家那一半:全新。要有:往來對象與價格等級、開放的商品、收到的訂單、接單 / 出貨(接銷貨與序號)、金鑰的發放與作廢、對外的端點。
- 共用的機型:M1(`docs/development/CURRENT_TASK.md`)。沒有它,手機只能像配件一樣連品名。
- 膜總裁那一邊(`~/moceo-b2b`)是另一個專案:它照 v1 就好,不用因為這一份而改;它要多做哪一項能力由 owner 決定。
